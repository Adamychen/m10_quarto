Demo — MCP en dos minutos

Compara cuántas integraciones hacen falta con y sin MCP, y recorre mensaje a mensaje la conversación entre un cliente y el servidor Chinook del HPD 4.

Demo que acompaña a Model Context Protocol y prepara el HPD 4. Se ejecuta en el navegador y no necesita clave de API.

MCP (Model Context Protocol) es un protocolo estándar para que una aplicación con LLM descubra y use herramientas externas. Esta demo responde a dos preguntas: para qué sirve (parte A) y qué se dicen exactamente la aplicación y el servidor (parte B).

@reactive.effect
@reactive.event(input.next)
def _n():
    pos.set(min(pos() + 1, len(STEPS) - 1))


@reactive.effect

    pos.set(max(pos() - 1, 0))


@reactive.effect

    pos.set(next(i for i, s in enumerate(STEPS) if s[0] == input.phase()))

def pretty(msg, step_id):
    """JSON coloreado, con el id resaltado para ver qué respuesta corresponde a qué petición."""
    if isinstance(msg, str):
        return html.escape(msg)
    out = html.escape(json.dumps(msg, ensure_ascii=False, indent=2))
    out = out.replace("&quot;", '"')
    out = re.sub(r'"([^"]+)":', r'<span class="k">"\1"</span>:', out)
    out = re.sub(r': "([^"]*)"', r': <span class="s">"\1"</span>', out)
    out = re.sub(r': (\d+|true|false)', r': <span class="n">\1</span>', out)
    out = re.sub(r'(<span class="k">"id"</span>: <span class="n">\d+</span>)', r'<span class="idk">\1</span>', out, count=1)
    return out

Qué observar

  1. Parte A. Con el interruptor apagado, sube aplicaciones y herramientas al máximo: 6 × 8 = 48 adaptadores, uno por pareja. Enciende «Usar MCP»: 6 + 8 = 14. Cada aplicación implementa un cliente MCP una vez, y cada herramienta, un servidor MCP una vez.
  2. Parte B, fase «Presentarse» (mensajes 1-3). El cliente y el servidor acuerdan la versión del protocolo y el servidor declara qué ofrece. Fíjate en el id resaltado: la respuesta lleva el mismo que la petición. Así se emparejan en JSON-RPC.
  3. Fase «Descubrir» (4-5). Tu aplicación no sabe de antemano qué herramientas hay: las pide con tools/list. Cada una llega con nombre, descripción y esquema de argumentos, lo mismo que escribes en el docstring de @mcp.tool() en el HPD 4.
  4. Fase «Usar» (6-9). Los mensajes en cursiva (6 y 9) no son MCP: ocurren dentro de tu aplicación, entre el usuario y el LLM. El LLM solo propone la llamada; el cliente la convierte en tools/call, y es el servidor quien ejecuta la función.

Qué has visto

  • MCP resuelve un problema de integración: pasa de N × M adaptadores a N + M, y una herramienta nueva sirve al momento para todas las aplicaciones.
  • Es un protocolo pequeño: mensajes JSON-RPC para presentarse, descubrir herramientas y llamarlas. No hay magia.
  • El LLM no habla MCP. Lo habla tu aplicación (el cliente), que hace de intermediaria entre el modelo y el servidor.
WarningQué es real y qué está simplificado
  • Los mensajes siguen el formato real de MCP (versión del protocolo 2025-06-18), pero se han omitido campos opcionales.
  • Las herramientas y el resultado de cliente_por_id(1) son los del servidor «Facturación Chinook» que construyes en el HPD 4.
  • En la parte A, «adaptador» simplifica mucho: cada integración real tiene autenticación, formatos y errores propios, y por eso el ahorro de MCP es aún mayor de lo que sugieren los números.

def pretty(msg, step_id):
    """JSON coloreado, con el id resaltado para ver qué respuesta corresponde a qué petición."""
    if isinstance(msg, str):
        return html.escape(msg)
    out = html.escape(json.dumps(msg, ensure_ascii=False, indent=2))
    out = out.replace("&quot;", '"')
    out = re.sub(r'"([^"]+)":', r'<span class="k">"\1"</span>:', out)
    out = re.sub(r': "([^"]*)"', r': <span class="s">"\1"</span>', out)
    out = re.sub(r': (\d+|true|false)', r': <span class="n">\1</span>', out)
    out = re.sub(r'(<span class="k">"id"</span>: <span class="n">\d+</span>)', r'<span class="idk">\1</span>', out, count=1)
    return out

## Qué observar

1. **Parte A.** Con el interruptor apagado, sube aplicaciones y herramientas al máximo: 6 × 8 = 48 adaptadores, uno por pareja. Enciende **«Usar MCP»**: 6 + 8 = 14. Cada aplicación implementa un cliente MCP una vez, y cada herramienta, un servidor MCP una vez.
2. **Parte B, fase «Presentarse» (mensajes 1-3).** El cliente y el servidor acuerdan la versión del protocolo y el servidor declara qué ofrece. Fíjate en el `id` resaltado: la respuesta lleva el mismo que la petición. Así se emparejan en JSON-RPC.
3. **Fase «Descubrir» (4-5).** Tu aplicación no sabe de antemano qué herramientas hay: las pide con `tools/list`. Cada una llega con nombre, descripción y esquema de argumentos, lo mismo que escribes en el docstring de `@mcp.tool()` en el HPD 4.
4. **Fase «Usar» (6-9).** Los mensajes en cursiva (6 y 9) no son MCP: ocurren dentro de tu aplicación, entre el usuario y el LLM. El LLM solo **propone** la llamada; el cliente la convierte en `tools/call`, y es el servidor quien ejecuta la función.

## Qué has visto

- MCP resuelve un problema de **integración**: pasa de N × M adaptadores a N + M, y una herramienta nueva sirve al momento para todas las aplicaciones.
- Es un protocolo pequeño: mensajes JSON-RPC para presentarse, descubrir herramientas y llamarlas. No hay magia.
- El LLM no habla MCP. Lo habla tu aplicación (el cliente), que hace de intermediaria entre el modelo y el servidor.

::: {.callout-warning}
## Qué es real y qué está simplificado

- Los mensajes siguen el formato real de MCP (versión del protocolo `2025-06-18`), pero se han omitido campos opcionales.
- Las herramientas y el resultado de `cliente_por_id(1)` son los del servidor «Facturación Chinook» que construyes en el HPD 4.
- En la parte A, «adaptador» simplifica mucho: cada integración real tiene autenticación, formatos y errores propios, y por eso el ahorro de MCP es aún mayor de lo que sugieren los números.
