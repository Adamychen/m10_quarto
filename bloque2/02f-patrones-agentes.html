Patrones de diseño de agentes

Construir agentes efectivos requiere más que un buen modelo y un conjunto de herramientas: la arquitectura —cómo se orquesta el LLM, cómo se descompone la tarea y cómo fluye el control— determina si un sistema es fiable, depurable y rentable. Este tema presenta los patrones canónicos que han surgido de despliegues de producción en Anthropic, OpenAI, Google y la comunidad de código abierto (Anthropic, 2024).

Workflows frente a Agentes

ImportantTres niveles de orquestación

Antes de elegir entre workflows y agentes hay un nivel cero:

  1. Cadena simple (chain): una o dos llamadas al LLM encadenadas en código (LCEL), sin ramas ni herramientas. Es el baseline de cualquier sistema.
  2. Workflow: flujo de control predefinido, con llamadas al LLM en pasos concretos, ramas y validaciones. Predecibles, testables, baratos. Úsalos cuando la estructura de la tarea es conocida.
  3. Agente: el LLM decide dinámicamente qué hacer a continuación (qué herramienta, cuándo parar). Flexibles, manejan situaciones nuevas. Úsalos cuando la tarea requiere decisión adaptativa o exploración abierta.

Empieza con la cadena más simple que funcione. Escala a un workflow y luego a agente solo cuando la tarea lo requiera genuinamente.

La siguiente taxonomía —adaptada de la guía de Anthropic (Anthropic, 2024) y del capítulo “Agent Design Patterns” de Roitman (2026)— distingue dos familias: patrones de workflow (el sistema decide el orden) y patrones de agente autónomo (el LLM controla el flujo). Los ejemplos en código de este tema son workflows (prompt chaining y routing); los agentes autónomos ya se implementan en 02e y en el HPD 2.

Workflow patterns

Estos patrones usan LLM dentro de un flujo de control predefinido. El sistema (no el modelo) decide el orden de ejecución.

Prompt Chaining

El patrón más simple: dividir una tarea compleja en una secuencia fija de llamadas al LLM, encadenando la salida de un paso como contexto del siguiente. Entre pasos se pueden insertar validaciones (programáticas o con LLM) que detectan errores pronto, antes de que se propaguen.

Cuándo usarlo: tareas naturalmente secuenciales — generación de contenido, transformación de datos, análisis multietapa.

Ventaja clave: cada paso puede usar un prompt, modelo o temperatura distintos; los resultados intermedios son inspeccionables y depurables.

Routing

Un clasificador (LLM o tradicional) examina la entrada y la envía a un manejador especializado (prompt, herramienta o modelo óptimo para ese tipo de entrada).

Cuándo usarlo: tipos de tarea distintos con prompts, herramientas o modelos óptimos diferentes — triaje de soporte, entrada multimodal, preguntas factuales frente a analíticas.

Parallelization

Múltiples llamadas al LLM se ejecutan en paralelo, con una capa programática que combina sus salidas. Dos sub-patrones:

  • Sectioning (fan-out): se particiona la entrada en trozos disjuntos y cada uno se procesa independientemente — p. ej. auditorías de seguridad, rendimiento y estilo sobre el mismo código.
  • Voting (redundancia): se lanza el mismo prompt N veces con seeds o temperaturas distintas y se selecciona el mejor resultado por mayoría, score de reward model o LLM-as-judge (X. Wang et al., 2023).

La latencia resultante es \(\max\) de las llamadas individuales, no su suma.

Orchestrator-Workers

Aquí el LLM decide cómo dividir el trabajo: un orquestador analiza la tarea, produce un plan de subtareas, las despacha a workers (posiblemente con prompts o herramientas distintas) y finalmente fusiona sus salidas en un resultado coherente. La diferencia clave con parallelization: la descomposición es generada por el modelo, no hardcodeada.

Cuándo usarlo: problemas abiertos donde el número y naturaleza de subtareas no pueden enumerarse en diseño — p. ej. “refactoriza este codebase” requiere primero entender el grafo de dependencias antes de decidir qué archivos modificar.

Evaluator-Optimizer

Un bucle de retroalimentación de dos modelos: un generador produce candidatos mientras un evaluador separado los puntúa contra criterios explícitos. Si el score no alcanza el umbral, la crítica del evaluador se añade al contexto del generador y el ciclo se repite hasta cumplir el umbral de calidad o agotar un presupuesto de reintentos (Madaan et al., 2023).

Cuándo usarlo: tareas con criterios de calidad claros — código que debe pasar tests, traducciones que deben preservar significado, escritura que debe ajustarse a una guía de estilo.

Patrones de agente autónomo

Estos patrones ceden al LLM el control del flujo de ejecución.

ReAct (Reasoning + Acting)

El patrón fundacional (Yao et al., 2023), ya implementado en 02e — Agentes. El LLM alterna razonamiento (Thought), acción (Action) y observación (Observation) en un bucle hasta producir la respuesta final. Es la base de create_agent en LangChain y del HPD 2.

Planning: Plan-and-Execute

En lugar de decidir un paso cada vez, el agente genera primero un plan completo y luego lo ejecuta (L. Wang et al., 2023):

  1. Fase de planificación: dado el objetivo, generar un plan estructurado (lista de subtareas con dependencias).
  2. Fase de ejecución: ejecutar cada subtarea, posiblemente con un modelo más barato.
  3. Revisión del plan: si un paso falla o produce resultados inesperados, re-planificar desde el estado actual.

El plan es un documento vivo: da estructura pero se adapta a las observaciones. Cuatro estrategias de replanning:

Cuándo usarlo: tareas de horizonte largo con muchos pasos. Más eficiente que ReAct para ese tipo de tareas (menos llamadas al LLM), pero menos adaptativo a observaciones inesperadas.

Reflection y Reflexion

El agente se pausa para evaluar su propia trayectoria y corregir el rumbo:

  1. Validación de salida: “¿es correcto esto? ¿me he dejado algo?”
  2. Revisión de trayectoria: Revisar los últimos k pasos e identificar errores o ineficiencias
  3. Revisión de estrategia: Reconsiderar el enfoque global (“¿estoy resolviendo el problema correcto?”)
NoteReflexion: aprender del fracaso

El patrón Reflexion (Shinn et al., 2023) mantiene una “memoria de reflexión” persistente: tras cada intento fallido, el agente escribe una reflexión en lenguaje natural (“fallé porque no comprobé el caso límite”). En el siguiente intento, estas reflexiones se incluyen en el prompt — aprendizaje entre episodios sin actualizar pesos.

El nested (agent-as-tool) merece atención: una herramienta invoca a un agente completamente separado, con su propio prompt, tools y contexto. El agente padre trata al sub-agente como una caja negra. El patrón Swarm (OpenAI, 2024) lo generaliza mediante handoffs entre agentes especializados.

Human-in-the-loop

Los agentes de producción deben saber cuándo pausar y pedir intervención humana:

  • Gates de aprobación: antes de acciones irreversibles (enviar emails, borrar archivos, comprar), requerir confirmación humana explícita.
  • Criterios de escalado: escalar cuando la confianza es baja, la tarea está fuera de alcance o se dispara una regla de seguridad.
  • Integración de feedback: las correcciones humanas se insertan en el contexto y pueden actualizar el plan del agente.
  • Aprobación asíncrona: en tareas largas, el agente pausa, notifica (email/Slack) y reanuda al aprobarse.

Este patrón conecta directamente con la gobernanza del Bloque 4.

Workflow graphs

Para workflows complejos, la lógica de orquestación se expresa como un grafo dirigido acíclico (DAG) o máquina de estados:

  • LangGraph (LangChain, 2024): extiende LangChain con ejecución basada en grafos. Los nodos son pasos del agente; las aristas, transiciones condicionales. Soporta ciclos (para bucles ReAct) y ramas paralelas. Ya lo usamos en 02e para el pipeline RAG supervisado.
  • AutoGen (Wu et al., 2023): framework de Microsoft para grafos de conversación multi-agente: nested chats, group chats y human-in-the-loop.
  • Máquinas de estado: estados explícitos (PLANNING, EXECUTING, WAITING_FOR_HUMAN, DONE) con transiciones definidas. Más fáciles de razonar y testear que bucles implícitos.

Principios de diseño

Los siguientes principios, destilados de la guía de Anthropic (Anthropic, 2024), aplican a todos los patrones:

  1. Manténlo simple. Usa la arquitectura más simple que funcione. Añade complejidad solo cuando se demuestre necesaria. Una cadena de prompts que resuelve el problema es siempre preferible a un sistema multi-agente que podría resolverlo.
  2. Transparencia sobre ingenio. Cada paso debe ser inspeccionable. Evita estado oculto o razonamiento implícito: cuando un agente falla, necesitas entender por qué.
  3. Proporciona buenas herramientas. Herramientas bien documentadas, bien tipadas y con mensajes de error claros son multiplicadores de fuerza.
  4. Planifica para el fallo. Toda llamada a tool puede fallar. Construye reintentos, fallbacks y degradación elegante a nivel del harness, para que el modelo no tenga que razonar sobre fallos de infraestructura.
  5. Usa salidas estructuradas. La generación restringida (JSON schema, function calling) evita fallos de parseo.
  6. Testea con entradas diversas. El comportamiento del agente es más variable que el chat de un solo turno: el mismo prompt puede producir secuencias de tool calls distintas en ejecuciones diferentes.

Guía de selección de patrones

Elegir el patrón correcto depende de tres factores: (1) lo predecible que es la estructura de la tarea, (2) cuántas llamadas al LLM puedes permitirte en latencia y coste, y (3) si la calidad requiere iteración. Usa esta matriz como punto de partida — empieza por arriba (lo más simple) y baja solo cuando el patrón simple falle demostrablemente:

TipLos patrones se componen

Un agente de planificación puede usar prompt chaining para pasos individuales, un evaluator-optimizer dentro de su fase de revisión y routing para despachar subtareas a especialistas. El arte está en saber cuándo dejar de añadir capas.

Doble llamada: primero un borrador, luego una revisión que lo mejora. El resultado del primer paso es el contexto del segundo.

### Conclusión y Recomendaciones del Editor

Para elegir la opción correcta, debe evaluar el **canal de comunicación** y el **nivel de la audiencia**:

1.  **Use el Formato Narrativo** si el documento será leído en su totalidad (ej. una memoria anual). Su valor reside en la capacidad de contar una historia de éxito y dar fluidez a la lectura.
2.  **Use el Formato Ejecutivo** si el destinatario es un directivo con poco tiempo (C-Level). Este formato elimina el "ruido" y se enfoca en la relación directa entre el logro actual y la visión de futuro.
3.  **Use el Formato Técnico** si el resumen forma parte de un anexo, un reporte de métricas o una presentación de diapositivas con mucha carga de datos. Su objetivo es la eficiencia máxima y la consulta rápida de datos clave.

**Sugerencia adicional:** Si el documento es para un mercado internacional, asegúrese de definir si "LATAM" es la terminología aceptada por su audiencia o si prefiere el uso de "América Latina" para mantener la máxima formalidad.

Si el borrador no supera una validación (p. ej. longitud mínima), un paso programático puede reenviarlo al generador antes de pasar al siguiente — ese es el gate del patrón.

Routing con LangChain

Un clasificador decide qué prompt especializado recibe cada pregunta:

# Dos manejadores especializados
prompt_facto = ChatPromptTemplate.from_messages([
    ("system", "Responde con datos concretos y precisos. Si no los sabes, dilo."),
    ("user", "{pregunta}")
]) | llm | StrOutputParser()

prompt_analisis = ChatPromptTemplate.from_messages([
    ("system", "Da una respuesta analítica: causas, tendencias y recomendaciones."),
    ("user", "{pregunta}")
]) | llm | StrOutputParser()

def clasificar(pregunta: str) -> str:
    """El propio LLM decide la ruta: 'factual' o 'analitica'."""
    resp = llm.invoke(
        f"Clasifica la pregunta como 'factual' (pide datos concretos) "
        f"o 'analitica' (pide interpretación). Pregunta: {pregunta}\n"
        "Responde solo con una palabra: factual o analitica"
    )
    ruta = resp.content.strip().lower()
    return "factual" if ruta.startswith("fact") else "analitica"

def router(pregunta: str) -> str:
    if clasificar(pregunta) == "factual":
        return prompt_facto.invoke({"pregunta": pregunta})
    return prompt_analisis.invoke({"pregunta": pregunta})

### 1. Análisis de Causas (El "¿Por qué?")

Podemos dividir las causas en dos grandes grupos: **Factores Internos** (lo que puedes controlar) y **Factores Externos** (lo que el mercado te impone).

#### A. Causas Internas (Controlables)
*   **Degradación del Producto/Servicio:** ¿Ha bajado la calidad? ¿Se ha quedado el producto obsoleto frente a nuevas tecnologías?
*   **Estrategia de Precios:** ¿Un competidor bajó precios o tu producto ahora se percibe como "caro" para el valor que ofrece?
*   **Fallas en el Funnel de Ventas (Conversión):** Quizás recibes la misma cantidad de clientes, pero no cierras la venta. Puede ser por mala atención, procesos de pago complejos o falta de stock.
*   **Marketing Ineficiente:** El costo de adquisición de clientes (CAC) subió o tus campañas dejaron de llegar al público objetivo.
*   **Rotación de Personal:** La pérdida de vendedores clave o la falta de capacitación afecta directamente el cierre de ventas.

#### B. Causas Externas (No Controlables)
*   **Ciclo Económico:** Inflación, pérdida del poder adquisitivo del consumidor o cambios en las tasas de interés.
*   **Nuevos Competidores:** La entrada de un actor con precios agresivos o una propuesta de valor más moderna.
*   **Estacionalidad:** ¿Es una caída esperada por la época del año o es una caída atípica?
*   **Cambios en el Comportamiento del Consumidor:** Un cambio en las preferencias (ej. la gente dejó de comprar X para comprar Y) o un cambio en el canal (de tienda física a e-commerce).

---

### 2. Tendencias Actuales del Mercado (El Contexto)

Si tu caída es generalizada en tu industria, es probable que estés siendo afectado por estas tendencias globales:

1.  **Consumo Consciente y Selectivo:** Los consumidores están filtrando más sus gastos. No solo buscan precio, sino propósito, sostenibilidad y experiencia.
2.  **Omnicanalidad Obligatoria:** Ya no basta con tener una tienda o una web; el cliente espera una experiencia fluida entre el mundo online y offline.
3.  **Economía de la Atención:** El exceso de oferta hace que retener la atención del cliente sea más caro y difícil. Si tu marketing no es disruptivo, simplemente no existes.
4.  **Digitalización del Proceso de Decisión:** El cliente llega a tu negocio ya "educado". Ya investigó en Google, leyó reseñas y comparó precios. Si no tienes una buena reputación digital, la venta se pierde antes de empezar.

---

### 3. Recomendaciones (El "¿Qué hacer?")

Para revertir la situación, te sugiero seguir este plan de acción:

#### Fase 1: Diagnóstico Basado en Datos (Inmediato)
*   **Audita tu Funnel:** Revisa en qué punto exacto se pierden los clientes. ¿Es en el tráfico (nadie llega), en la conversión (llegan pero no compran) o en la retención (compran una vez y no vuelven)?
*   **Análisis de Cohortes:** Mira si la caída viene de clientes nuevos o de la pérdida de clientes recurrentes.
*   **Escucha Activa (Feedback):** Pregunta directamente a los clientes que no compraron o que se fueron. La verdad suele estar en las quejas no atendidas.

#### Fase 2: Ajuste Estratégico (Corto Plazo)
*   **Optimización de la Oferta:** Si el problema es el precio, no necesariamente bajes el precio; añade valor (combos, garantías, servicios adicionales) para mejorar la percepción de valor.
*   **Fidelización (Retention Marketing):** Es mucho más barato venderle a un cliente actual que conseguir uno nuevo. Implementa programas de lealtad o campañas de re-activación.
*   **Revisión de Canales:** Si el tráfico bajó, diversifica tus fuentes de adquisición (Ads, SEO, Redes Sociales, Alianzas).

#### Fase 3: Optimización Operativa (Mediano Plazo)
*   **Capacitación de Fuerza de Ventas:** Asegúrate de que tu equipo no solo "despache", sino que sepa detectar necesidades y resolver objeciones.
*   **Mejora de la Experiencia del Cliente (CX):** Elimina cualquier "fricción" en el proceso de compra (tienda desordenada, web lenta, falta de medios de pago).

1. *¿A qué se dedica tu empresa?*
2. *¿La caída fue repentina o gradual?*
3. *¿Has notado si el problema es que llega menos gente o que los que llegan no compran?*

## Patrones de diseño de agentes {#sec-patrones-agentes}

Construir agentes efectivos requiere más que un buen modelo y un conjunto de herramientas: la arquitectura —cómo se orquesta el LLM, cómo se descompone la tarea y cómo fluye el control— determina si un sistema es fiable, depurable y rentable. Este tema presenta los patrones canónicos que han surgido de despliegues de producción en Anthropic, OpenAI, Google y la comunidad de código abierto [@anthropic2024buildingagents].

### Workflows frente a Agentes {#sec-workflows-vs-agentes}

::: {.callout-important}
## Tres niveles de orquestación

Antes de elegir entre workflows y agentes hay un nivel cero:

1. **Cadena simple (chain)**: una o dos llamadas al LLM encadenadas en código (LCEL), sin ramas ni herramientas. Es el baseline de cualquier sistema.
2. **Workflow**: flujo de control *predefinido*, con llamadas al LLM en pasos concretos, ramas y validaciones. Predecibles, testables, baratos. Úsalos cuando la estructura de la tarea es conocida.
3. **Agente**: el LLM *decide dinámicamente* qué hacer a continuación (qué herramienta, cuándo parar). Flexibles, manejan situaciones nuevas. Úsalos cuando la tarea requiere decisión adaptativa o exploración abierta.

**Empieza con la cadena más simple que funcione.** Escala a un workflow y luego a agente solo cuando la tarea lo requiera genuinamente.
:::

: Cadena simple vs. workflow vs. agente {#tbl-niveles-orquestacion}

| Criterio | Cadena simple | Workflow | Agente |
|---|---|---|---|
| **Quién controla el flujo** | El código, orden fijo | El código, pasos y ramas fijas | El LLM, bucle dinámico |
| **Llamadas al LLM** | 1-2 | 2-10, predecibles | 3-25+, variables |
| **Herramientas** | No | A veces, invocadas por el código | Sí, decididas por el modelo |
| **Predictibilidad** | Muy alta | Alta | Baja (trayectorias no reproducibles) |
| **Depuración** | Trivial | Buena: pasos inspeccionables | Difícil: el LLM decide cada paso |
| **Evaluación** | Fácil | Fácil | Difícil |
| **Cuándo usarlo** | Tareas de 1-2 pasos | Estructura conocida | Estructura desconocida, exploración abierta |

La siguiente taxonomía —adaptada de la guía de Anthropic [@anthropic2024buildingagents] y del capítulo "Agent Design Patterns" de Roitman [-@roitman2026hitchhiker]— distingue dos familias: patrones de workflow (el sistema decide el orden) y patrones de agente autónomo (el LLM controla el flujo). Los ejemplos en código de este tema son workflows ([prompt chaining](#sec-ejemplo-chaining) y [routing](#sec-ejemplo-routing)); los agentes autónomos ya se implementan en [02e](02e-agentes.qmd) y en el HPD 2.

### Workflow patterns {#sec-workflow-patterns}

Estos patrones usan LLM dentro de un flujo de control *predefinido*. El sistema (no el modelo) decide el orden de ejecución.

#### Prompt Chaining {#sec-prompt-chaining}

El patrón más simple: dividir una tarea compleja en una secuencia fija de llamadas al LLM, encadenando la salida de un paso como contexto del siguiente. Entre pasos se pueden insertar validaciones (programáticas o con LLM) que detectan errores pronto, antes de que se propaguen.

::: {#fig-prompt-chaining}
```{mermaid}

    classDef proc fill:#306998,stroke:#1e3a5f,color:#fff,stroke-width:1.5px
    classDef gate fill:#FFD43B,stroke:#b8960f,color:#000,stroke-width:1.5px
    classDef out fill:#2e7d32,stroke:#0d3010,color:#fff,stroke-width:2px

    A[Entrada]:::input --> B[Paso 1<br/>LLM]:::proc
    B --> G1{¿Válido?}:::gate
    G1 -->|No| B
    G1 -->|Sí| C[Paso 2<br/>LLM]:::proc
    C --> G2{¿Válido?}:::gate
    G2 -->|No| C
    G2 -->|Sí| D[Salida final]:::out
```
:::

**Cuándo usarlo**: tareas naturalmente secuenciales — generación de contenido, transformación de datos, análisis multietapa.

**Ventaja clave**: cada paso puede usar un prompt, modelo o temperatura distintos; los resultados intermedios son inspeccionables y depurables.

#### Routing {#sec-routing}

Un clasificador (LLM o tradicional) examina la entrada y la envía a un manejador especializado (prompt, herramienta o modelo óptimo para ese tipo de entrada).

::: {#fig-routing}
```{mermaid}
flowchart LR
    classDef input fill:#4B8BBE,stroke:#1e3a5f,color:#fff,stroke-width:1.5px
    classDef proc fill:#306998,stroke:#1e3a5f,color:#fff,stroke-width:1.5px
    classDef out fill:#2e7d32,stroke:#0d3010,color:#fff,stroke-width:2px

    A[Entrada]:::input --> C[Clasificador]:::proc
    C -->|Tipo 1| B1[Manejador<br/>especializado 1]:::proc
    C -->|Tipo 2| B2[Manejador<br/>especializado 2]:::proc
    C -->|Tipo 3| B3[Manejador<br/>especializado 3]:::proc
    B1 --> R[Respuesta]:::out
    B2 --> R
    B3 --> R
```
:::

**Cuándo usarlo**: tipos de tarea distintos con prompts, herramientas o modelos óptimos diferentes — triaje de soporte, entrada multimodal, preguntas factuales frente a analíticas.

#### Parallelization {#sec-parallelization}

Múltiples llamadas al LLM se ejecutan en paralelo, con una capa programática que combina sus salidas. Dos sub-patrones:

- **Sectioning (fan-out)**: se particiona la entrada en trozos disjuntos y cada uno se procesa independientemente — p. ej. auditorías de seguridad, rendimiento y estilo sobre el mismo código.
- **Voting (redundancia)**: se lanza el mismo prompt N veces con seeds o temperaturas distintas y se selecciona el mejor resultado por mayoría, score de reward model o LLM-as-judge [@wang2022selfconsistency].

::: {#fig-parallelization}
```{mermaid}
flowchart LR
    classDef input fill:#4B8BBE,stroke:#1e3a5f,color:#fff,stroke-width:1.5px
    classDef proc fill:#306998,stroke:#1e3a5f,color:#fff,stroke-width:1.5px
    classDef out fill:#2e7d32,stroke:#0d3010,color:#fff,stroke-width:2px

    A[Entrada]:::input --> P[Particiona<br/>o replica]:::proc
    P --> L1[LLM 1]:::proc
    P --> L2[LLM 2]:::proc
    P --> L3[LLM 3]:::proc
    L1 --> M[Aggregador<br/>combina / vota]:::proc
    L2 --> M
    L3 --> M
    M --> R[Resultado]:::out
```
:::

La latencia resultante es $\max$ de las llamadas individuales, no su suma.

#### Orchestrator-Workers {#sec-orchestrator-workers}

Aquí el LLM decide cómo dividir el trabajo: un orquestador analiza la tarea, produce un plan de subtareas, las despacha a workers (posiblemente con prompts o herramientas distintas) y finalmente fusiona sus salidas en un resultado coherente. La diferencia clave con parallelization: la descomposición es generada por el modelo, no hardcodeada.

::: {#fig-orchestrator-workers}
```{mermaid}
flowchart TD

    classDef proc fill:#306998,stroke:#1e3a5f,color:#fff,stroke-width:1.5px
    classDef out fill:#2e7d32,stroke:#0d3010,color:#fff,stroke-width:2px

    T[Tarea compleja]:::input --> O[Orquestador<br/>descompone y planifica]:::proc
    O --> W1[Worker A]:::proc
    O --> W2[Worker B]:::proc
    O --> W3[Worker C]:::proc
    W1 --> S[Fusión<br/>de resultados]:::proc
    W2 --> S
    W3 --> S
    S --> R[Resultado final]:::out
```
:::

**Cuándo usarlo**: problemas abiertos donde el número y naturaleza de subtareas no pueden enumerarse en diseño — p. ej. "refactoriza este codebase" requiere primero entender el grafo de dependencias antes de decidir qué archivos modificar.

#### Evaluator-Optimizer {#sec-evaluator-optimizer}

Un bucle de retroalimentación de dos modelos: un generador produce candidatos mientras un evaluador separado los puntúa contra criterios explícitos. Si el score no alcanza el umbral, la crítica del evaluador se añade al contexto del generador y el ciclo se repite hasta cumplir el umbral de calidad o agotar un presupuesto de reintentos [@madaan2023selfrefine].

::: {#fig-evaluator-optimizer}
```{mermaid}

    classDef proc fill:#306998,stroke:#1e3a5f,color:#fff,stroke-width:1.5px
    classDef gate fill:#FFD43B,stroke:#b8960f,color:#000,stroke-width:1.5px
    classDef out fill:#2e7d32,stroke:#0d3010,color:#fff,stroke-width:2px

    G[Generador]:::proc --> E[Evaluador<br/>+ criterios]:::proc
    E --> C{¿Calidad<br/>suficiente?}:::gate
    C -->|No + crítica| G
    C -->|Sí| R[Resultado]:::out
```
:::

**Cuándo usarlo**: tareas con criterios de calidad claros — código que debe pasar tests, traducciones que deben preservar significado, escritura que debe ajustarse a una guía de estilo.

### Patrones de agente autónomo {#sec-patrones-autonomos}

Estos patrones ceden al LLM el control del flujo de ejecución.

#### ReAct (Reasoning + Acting) {#sec-react-patron}

El patrón fundacional [@yao2023react], ya implementado en [02e — Agentes](02e-agentes.qmd#sec-react). El LLM alterna razonamiento (Thought), acción (Action) y observación (Observation) en un bucle hasta producir la respuesta final. Es la base de `create_agent` en LangChain y del HPD 2.

#### Planning: Plan-and-Execute {#sec-planning}

En lugar de decidir un paso cada vez, el agente genera primero un plan completo y luego lo ejecuta [@wang2023planandsolve]:

1. **Fase de planificación**: dado el objetivo, generar un plan estructurado (lista de subtareas con dependencias).
2. **Fase de ejecución**: ejecutar cada subtarea, posiblemente con un modelo más barato.
3. **Revisión del plan**: si un paso falla o produce resultados inesperados, re-planificar desde el estado actual.

El plan es un documento vivo: da estructura pero se adapta a las observaciones. Cuatro estrategias de replanning:

: Estrategias de replanning en agentes de planificación {#tbl-replanning}

| Estrategia | ¿Cuándo re-planifica? | Características |
|---|---|---|
| Plan-then-Execute | Nunca | Simple; frágil ante resultados inesperados |
| Adaptativa | Al fallar un paso | Solo cuando un paso falla; coste moderado |
| Continua | En cada paso | Reevaluación completa tras cada observación; cara pero robusta |
| Jerárquica | Al terminar un sub-plan | Plan de alto nivel fijo; sub-planes dinámicos |

**Cuándo usarlo**: tareas de horizonte largo con muchos pasos. Más eficiente que ReAct para ese tipo de tareas (menos llamadas al LLM), pero menos adaptativo a observaciones inesperadas.

#### Reflection y Reflexion {#sec-reflection}

El agente se pausa para evaluar su propia trayectoria y corregir el rumbo:

1. **Validación de salida**: "¿es correcto esto? ¿me he dejado algo?"
2. **Revisión de trayectoria**: Revisar los últimos k pasos e identificar errores o ineficiencias
3. **Revisión de estrategia**: Reconsiderar el enfoque global ("¿estoy resolviendo el problema correcto?")

::: {.callout-note}
## Reflexion: aprender del fracaso

El patrón Reflexion [@shinn2023reflexion] mantiene una "memoria de reflexión" persistente: tras cada intento fallido, el agente escribe una reflexión en lenguaje natural ("fallé porque no comprobé el caso límite"). En el siguiente intento, estas reflexiones se incluyen en el prompt — aprendizaje entre episodios sin actualizar pesos.
:::

#### Tool-use patterns {#sec-tool-use-patterns}

Cómo invoca el agente sus herramientas afecta a fiabilidad, latencia y coste. Cinco patrones canónicos [@schick2023toolformer]:

: Patrones de invocación de herramientas {#tbl-tool-use-patterns}

| Patrón | Descripción | Ejemplo |
|---|---|---|
| Single-turn | Una llamada a tool por respuesta | Q&A simple con búsqueda |
| Multi-tool | Varias llamadas en paralelo en una respuesta | Buscar + calcular + formatear |
| Sequential | La salida de una tool alimenta la siguiente | Buscar → leer → extraer |
| Nested | Una tool invoca a otro agente | Agente de código llama a test-runner |
| Fallback | Si la tool preferida falla, probar alternativa | API → scrape → caché |

El nested (agent-as-tool) merece atención: una herramienta invoca a un agente completamente separado, con su propio prompt, tools y contexto. El agente padre trata al sub-agente como una caja negra. El patrón Swarm [@openai2024swarm] lo generaliza mediante handoffs entre agentes especializados.

### Human-in-the-loop {#sec-human-in-the-loop}

Los agentes de producción deben saber cuándo pausar y pedir intervención humana:

- **Gates de aprobación**: antes de acciones irreversibles (enviar emails, borrar archivos, comprar), requerir confirmación humana explícita.
- **Criterios de escalado**: escalar cuando la confianza es baja, la tarea está fuera de alcance o se dispara una regla de seguridad.
- **Integración de feedback**: las correcciones humanas se insertan en el contexto y pueden actualizar el plan del agente.
- **Aprobación asíncrona**: en tareas largas, el agente pausa, notifica (email/Slack) y reanuda al aprobarse.

Este patrón conecta directamente con la gobernanza del [Bloque 4](../bloque4/04-gobernanza.qmd).

### Workflow graphs {#sec-workflow-graphs}

Para workflows complejos, la lógica de orquestación se expresa como un grafo dirigido acíclico (DAG) o máquina de estados:

- **LangGraph** [@langchain2024langgraph]: extiende LangChain con ejecución basada en grafos. Los nodos son pasos del agente; las aristas, transiciones condicionales. Soporta ciclos (para bucles ReAct) y ramas paralelas. Ya lo usamos en [02e](02e-agentes.qmd#sec-rag-langgraph) para el pipeline RAG supervisado.
- **AutoGen** [@wu2023autogen]: framework de Microsoft para grafos de conversación multi-agente: nested chats, group chats y human-in-the-loop.
- **Máquinas de estado**: estados explícitos (`PLANNING`, `EXECUTING`, `WAITING_FOR_HUMAN`, `DONE`) con transiciones definidas. Más fáciles de razonar y testear que bucles implícitos.

### Principios de diseño {#sec-principios-diseno}

Los siguientes principios, destilados de la guía de Anthropic [@anthropic2024buildingagents], aplican a todos los patrones:

1. **Manténlo simple.** Usa la arquitectura más simple que funcione. Añade complejidad solo cuando se demuestre necesaria. Una cadena de prompts que resuelve el problema es siempre preferible a un sistema multi-agente que *podría* resolverlo.
2. **Transparencia sobre ingenio.** Cada paso debe ser inspeccionable. Evita estado oculto o razonamiento implícito: cuando un agente falla, necesitas entender *por qué*.
3. **Proporciona buenas herramientas.** Herramientas bien documentadas, bien tipadas y con mensajes de error claros son multiplicadores de fuerza.
4. **Planifica para el fallo.** Toda llamada a tool puede fallar. Construye reintentos, fallbacks y degradación elegante a nivel del harness, para que el modelo no tenga que razonar sobre fallos de infraestructura.
5. **Usa salidas estructuradas.** La generación restringida (JSON schema, function calling) evita fallos de parseo.
6. **Testea con entradas diversas.** El comportamiento del agente es más variable que el chat de un solo turno: el mismo prompt puede producir secuencias de tool calls distintas en ejecuciones diferentes.

### Guía de selección de patrones {#sec-guia-seleccion}

Elegir el patrón correcto depende de tres factores: (1) lo predecible que es la estructura de la tarea, (2) cuántas llamadas al LLM puedes permitirte en latencia y coste, y (3) si la calidad requiere iteración. Usa esta matriz como punto de partida — empieza por arriba (lo más simple) y baja solo cuando el patrón simple falle demostrablemente:

: Cuándo usar cada patrón de diseño {#tbl-guia-seleccion}

| Patrón | Complejidad | Llamadas LLM | Mejor para |
|---|---|---|---|
| Cadena simple | Mínima | 1-2 | Baseline, tareas de 1-2 pasos |
| Prompt chaining | Baja | N (fijas) | Tareas secuenciales, pipelines de contenido |
| Routing | Baja | 1 + 1 | Entradas multi-tipo, triaje |
| Parallelization | Baja | N (paralelas) | Subtareas independientes, votación |
| Orchestrator-workers | Media | Variable | Descomposición desconocida |
| Evaluator-optimizer | Media | 2-10 (bucle) | Salidas críticas en calidad |
| ReAct | Media | 3-25 (bucle) | Uso general de tools, exploración |
| Planning | Alta | 5-50+ | Tareas de horizonte largo |
| Reflection | Alta | +50 % overhead | Tareas donde el primer intento suele fallar |
| Multi-agente | Alta | Muchas | Dominios complejos, especialización |

::: {.callout-tip}
## Los patrones se componen

Un agente de planificación puede usar prompt chaining para pasos individuales, un evaluator-optimizer dentro de su fase de revisión y routing para despachar subtareas a especialistas. El arte está en saber cuándo dejar de añadir capas.
:::

## Ejemplos prácticos {#sec-ejemplos-practicos}

Veamos dos patrones de workflow en código: prompt chaining y routing con LangChain.

### Prompt chaining con LCEL {#sec-ejemplo-chaining}

Doble llamada: primero un borrador, luego una revisión que lo mejora. El resultado del primer paso es el contexto del segundo.

```{python}
#| echo: true

from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser

# Paso 1: generar el borrador
paso1 = ChatPromptTemplate.from_messages([
    ("system", "Eres un redactor técnico. Escribe un resumen ejecutivo del texto dado."),
    ("user", "{texto}")
]) | llm | StrOutputParser()

# Paso 2: revisar el borrador
paso2 = ChatPromptTemplate.from_messages([
    ("system", "Eres un editor senior. Mejora el borrador: corrige imprecisiones, "
               "hazlo más conciso y añade una conclusión con recomendaciones."),
    ("user", "Borrador:\n{borrador}")
]) | llm | StrOutputParser()

cadena = paso1 | paso2  # LCEL: la salida del paso 1 alimenta al paso 2

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ejecutar el ejemplo.")
else:
    texto = "La empresa tiene 120 empleados, creció un 15% este año y planea expandirse a LATAM en 2026."
    print("=== Paso 1: borrador ===")
    print(paso1.invoke({"texto": texto})[:200], "...")
    print("\n=== Paso 2: versión final ===")
    print(cadena.invoke({"texto": texto}))
```

Si el borrador no supera una validación (p. ej. longitud mínima), un paso programático puede reenviarlo al generador antes de pasar al siguiente — ese es el *gate* del patrón.

### Routing con LangChain {#sec-ejemplo-routing}

Un clasificador decide qué prompt especializado recibe cada pregunta:

```{python}
#| echo: true

# Dos manejadores especializados
prompt_facto = ChatPromptTemplate.from_messages([
    ("system", "Responde con datos concretos y precisos. Si no los sabes, dilo."),
    ("user", "{pregunta}")
]) | llm | StrOutputParser()

prompt_analisis = ChatPromptTemplate.from_messages([
    ("system", "Da una respuesta analítica: causas, tendencias y recomendaciones."),
    ("user", "{pregunta}")
]) | llm | StrOutputParser()

def clasificar(pregunta: str) -> str:
    """El propio LLM decide la ruta: 'factual' o 'analitica'."""
    resp = llm.invoke(
        f"Clasifica la pregunta como 'factual' (pide datos concretos) "
        f"o 'analitica' (pide interpretación). Pregunta: {pregunta}\n"
        "Responde solo con una palabra: factual o analitica"
    )
    ruta = resp.content.strip().lower()
    return "factual" if ruta.startswith("fact") else "analitica"

def router(pregunta: str) -> str:
    if clasificar(pregunta) == "factual":
        return prompt_facto.invoke({"pregunta": pregunta})
    return prompt_analisis.invoke({"pregunta": pregunta})

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ejecutar el ejemplo.")
else:
    for p in ["¿Cuál es la población de Sevilla?", "¿Por qué crees que bajaron las ventas?"]:
        print(f"\nPREGUNTA: {p}")
        print(f"→ Ruta: {clasificar(p)}")
        print(f"→ Respuesta: {router(p)}")
```

Fíjate en que el routing suele costar solo 1 llamada extra (la clasificación) y evita que un prompt genérico degrade las respuestas especializadas — por eso aparece como complejidad "baja" en @tbl-guia-seleccion.
