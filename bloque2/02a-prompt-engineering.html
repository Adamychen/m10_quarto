Prompt Engineering Avanzado

¿Qué es un prompt?

Un prompt es la instrucción textual que le damos a un LLM. Piensa en ello como la pregunta o la orden que le das a un asistente muy capaz pero muy literal: si la instrucción es ambigua, la respuesta será imprecisa. Si es clara y con contexto, la respuesta será mucho mejor.

El Prompt Engineering consiste en diseñar estas instrucciones de forma sistemática para obtener respuestas fiables, estructuradas y útiles, no solo “texto bonito”.

Primer contacto: llamada a un LLM

Antes de profundizar, veamos cómo invocar un LLM desde Python con la API de OpenAI (compatible con Llamus US, Ollama local, etc.):

Este es el patrón base para todo lo que veremos: model + messages → respuesta. Los messages pueden tener varios roles:

Few-shot prompting

El few-shot consiste en incluir ejemplos dentro del prompt para que el modelo entienda exactamente qué formato y estilo esperamos. Es como enseñarle con el ejemplo.

¿Por qué funciona? Los LLM son excelentes reconociendo patrones. Al darles 2-3 ejemplos, el modelo “aprende” el patrón en contexto (in-context learning) sin necesidad de fine-tuning.

TipRegla de oro del few-shot
  • 2-3 ejemplos suelen bastar
  • Los ejemplos deben cubrir los casos extremos (edge cases)
  • Mantén consistencia exacta en el formato de los ejemplos

Chain-of-Thought (CoT)

El Chain-of-Thought consiste en pedir al modelo que razone paso a paso antes de dar la respuesta final. La clave está en añadir algo como “pensemos paso a paso” o incluir ejemplos donde se muestra el razonamiento.

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    problema = """
    Un tren sale de Madrid a las 08:00 hacia Barcelona (620 km) a 120 km/h.
    Otro tren sale de Barcelona a las 09:00 hacia Madrid a 150 km/h.
    ¿A qué hora se cruzan?
    """

    prompt_cot = f"""
    {problema}

    Resuelve paso a paso:
    1. Calcula cuánto ha avanzado el primer tren cuando sale el segundo
    2. Calcula la distancia restante entre ambos en ese momento
    3. Calcula el tiempo hasta que se cruzan
    4. Suma el tiempo a la hora de salida
    """

    respuesta_cot = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": prompt_cot}]
    )
    print(respuesta_cot.choices[0].message.content)
Aquí tienes la resolución del problema siguiendo los pasos solicitados:

### 1. Calcula cuánto ha avanzado el primer tren cuando sale el segundo
El primer tren sale a las 08:00 y el segundo a las 09:00. Esto significa que el primer tren viaja solo durante **1 hora**.
*   **Velocidad del primer tren:** $120\text{ km/h}$
*   **Tiempo de ventaja:** $1\text{ hora}$
*   **Distancia recorrida:** $120\text{ km/h} \times 1\text{ h} = \mathbf{120\text{ km}}$

### 2. Calcula la distancia restante entre ambos en ese momento
A las 09:00, el primer tren ya ha recorrido $120\text{ km}$. Debemos restarle esto a la distancia total para saber qué distancia separa a ambos trenes en el momento en que el segundo empieza a moverse.
*   **Distancia total:** $620\text{ km}$
*   **Distancia ya recorrida:** $120\text{ km}$
*   **Distancia restante:** $620\text{ km} - 120\text{ km} = \mathbf{500\text{ km}}$

### 3. Calcula el tiempo hasta que se cruzan
A partir de las 09:00, ambos trenes se mueven el uno hacia el otro. Para saber cuánto tardarán en encontrarse, sumamos sus velocidades (velocidad relativa):
*   **Velocidad combinada:** $120\text{ km/h} + 150\text{ km/h} = \mathbf{270\text{ km/h}}$
*   **Tiempo necesario:** $\text{Distancia restante} / \text{Velocidad combinada}$
*   $\text{Tiempo} = 500\text{ km} / 270\text{ km/h} \approx \mathbf{1,8518\text{ horas}}$

**Convertimos ese decimal a minutos para ser exactos:**
*   $1\text{ hora}$ entera.
*   $0,8518 \times 60\text{ minutos} \approx \mathbf{51\text{ minutos}}$
*   El tiempo transcurrido desde las 09:00 es de **1 hora y 51 minutos**.

### 4. Suma el tiempo a la hora de salida
Tomamos la hora en la que ambos estaban en movimiento (09:00) y le sumamos el tiempo que tardaron en encontrarse:
*   $09:00 + 1\text{ hora y } 51\text{ minutos} = \mathbf{10:51}$

**Respuesta:** Los trenes se cruzan a las **10:51**.

¿Por qué funciona? Al obligar al modelo a generar tokens intermedios de razonamiento, cada paso condiciona el siguiente. Es como si el modelo “pensara en voz alta”, reduciendo drásticamente los errores en tareas matemáticas y lógicas.

Tree-of-Thought (ToT)

El Tree-of-Thought extiende CoT: en lugar de un único camino de razonamiento, el modelo explora múltiples ramas y elige la mejor. Es útil para problemas con múltiples soluciones posibles (planificación, puzles, creatividad).

Para un equipo de **Data Science**, es fundamental equilibrar el alto nivel de carga cognitiva y la naturaleza sedentaria de su trabajo con actividades que permitan la desconexión, la interacción social orgánica y, si es posible, el uso de la lógica desde un ángulo lúdico o sensorial.

Aquí tienes la propuesta:

---

### 1. Los tres enfoques

#### Enfoque A: "The Logic Escape" (Intelectual / Gamificado)
**Actividad:** Un *Escape Room* temático o un juego de misterio de "asesinato" basado en pistas. El equipo debe resolver acertijos lógicos, descifrar patrones y utilizar el pensamiento deductivo para "ganar".
*   **Pros:** Muy alto *engagement* para perfiles analíticos; refuerza la resolución de problemas en grupo.
*   **Contras:** Puede sentirse "demasiado parecido al trabajo" si no se gestiona bien el tono; requiere un espacio físico específico.
*   **Coste/Logística:** Coste medio (pago de la sala/servicio); logística sencilla (solo desplazarse).

#### Enfoque B: "Sensory Connection" (Desconexión / Creativo)
**Actividad:** Un taller de cocina colaborativa o de mixología (creación de cócteles/mocktails). El equipo se divide en grupos para crear un "producto" final siguiendo instrucciones que varían según la creatividad que aporten.
*   **Pros:** Desconexión total de las pantallas; estimula otros sentidos; fomenta la comunicación no técnica y relajada.
*   **Contras:** Coste más elevado por los ingredientes y el personal; requiere más logística (espacio con cocina/barra).
*   **Coste/Logística:** Coste alto; logística compleja.

#### Enfoque C: "The Strategy Build" (Construcción / Abstracto)
**Actividad:** *Lego Serious Play*. Utilizando piezas de Lego, los miembros del equipo deben construir modelos que representen conceptos abstractos (ej: "nuestro flujo de trabajo", "un desafío del futuro") para luego compartirlos.
*   **Pros:** Excelente para la comunicación de ideas complejas; es una actividad muy estructurada que los científicos de datos suelen valorar.
*   **Contras:** Puede ser percibido como "demasiado serio" o poco divertido por algunos perfiles; requiere un facilitador experto.
*   **Coste/Logística:** Coste medio (facilitador + material); logística media.

---

### 2. El Ganador: Enfoque B (Sensory Connection - Taller de Cocina/Mixología)

**Justificación:**
Para un equipo de Data Science, el mayor riesgo de *burnout* es la fatiga mental por abstracción constante. Mientras que el Enfoque A y C siguen estimulando el área prefrontal (lógica/estrategia), el **Enfoque B ofrece un "reinicio" sensorial**. Al trabajar con texturas, sabores y procesos manuales, se logra una desconexión real que permite que el *bonding* (la unión del equipo) ocurra de forma natural a través de la conversación informal, sin la presión de "tener que resolver un problema".

---

### 3. Desarrollo detallado: "The Data Chef Challenge" (4 Horas)

Este plan está diseñado para maximizar la interacción y minimizar el estrés.

#### **Cronograma (Total: 4 horas)**

**00:00 - 00:30 | Bienvenida y "Icebreaker" No-Digital**
*   **Actividad:** Llegada con una bebida de bienvenida. Dinámica rápida de "Curiosidades Inesperadas": Cada persona debe decir un dato sobre sí mismo que no tenga nada que ver con la tecnología o los datos (ej: "Sé tocar el ukelele" o "Hice un viaje de mochilero por Vietnam").
*   **Objetivo:** Romper el hielo y humanizar a los compañeros fuera de su rol profesional.

**00:30 - 02:30 | El Desafío Principal: "The Flavor Algorithm"**
*   **Dinámica:** Se divide a las 20 personas en 4 equipos de 5 integrantes.
*   **El Reto:** Cada equipo recibe una "caja misteriosa" con ingredientes base y una lista de restricciones (ej: "un ingrediente ácido", "un elemento crujiente"). Deben crear un plato o un cóctel de autor.
*   **El giro:** No hay un manual estricto. Deben negociar entre ellos qué ingredientes combinar. Esto fomenta la toma de decisiones y la gestión de opiniones divergentes en un entorno de bajo riesgo.
*   **Rol del facilitador:** Un chef o experto que guíe la técnica pero deje la creatividad al equipo.

**02:30 - 03:30 | El Banquete (Socialización Real)**
*   **Actividad:** Se sientan todos juntos a la mesa para degustar lo preparado por todos los equipos.
*   **Dinámica:** Cada equipo presenta su "creación", explicando la "lógica" detrás de sus sabores (esto permite que usen su lenguaje natural de forma divertida).
*   **Objetivo:** Celebración y disfrute compartido. Es el momento donde se crean los vínculos más fuertes.

**03:30 - 04:00 | Cierre y "Debrief" Positivo**
*   **Actividad:** Un cierre breve donde cada uno dice una cosa que haya aprendido de un compañero durante la actividad (ej: "Me ha sorprendido la capacidad de organización de X").
*   **Objetivo:** Reforzar la validación positiva entre compañeros y cerrar la jornada con una nota alta de satisfacción.

#### **Requerimientos para el éxito:**
1.  **Espacio:** Un taller de cocina profesional o un salón de eventos con catering equipado.
2.  **Presupuesto sugerido:** Incluir coste de ingredientes de alta calidad, servicio de chef/barman y el espacio.
3.  **Regla de oro:** **Prohibido el uso de teléfonos móviles** durante las 4 horas para garantizar la presencia plena.
Note

ToT requiere más tokens (y por tanto más coste) que CoT simple, ya que se generan y evalúan múltiples ramas. En la práctica, se implementa con múltiples llamadas al LLM o agentes que evalúan cada rama.

ImportantJSON vía prompt vs. structured output nativo

Pedir JSON en el prompt funciona con cualquier modelo, pero no garantiza que el JSON sea válido (por eso añadimos try/except). Algunos modelos como Qwen 3 ofrecen response_format nativo que fuerza la estructura desde la API. La ventaja del prompting es que es model-agnostic: funciona con Gemma, Llama, Mistral, etc.

De JSON Schema a datos sintéticos: el enfoque intuitivo

Lo que acabas de hacer —extraer 1 registro JSON de un texto— es el mismo mecanismo que permite generar datasets sintéticos completos. La diferencia es de escala: en lugar de pedir 1 registro, pides N. En lugar de extraer de un texto real, pides al modelo que invente datos verosímiles.

La receta es simple:

  1. Define el schema de tus datos (igual que en la sección anterior)
  2. Añade few-shot examples para que el modelo entienda el dominio y los rangos esperados
  3. Controla la diversidad con temperatura: baja produce datos conservadores, alta inyecta variedad
  4. Itera en batch para generar cientos o miles de registros

Aquí te explico el porqué, cuándo es un problema y qué deberías usar en su lugar.

---

### 1. El problema: La falta de "robustez"
La media aritmética es muy **sensible**. Para calcularla, sumas todos los valores y los divides por el total. Esto significa que cada dato, por muy extremo que sea, tiene un peso en el resultado final.

Si tienes un valor extremadamente alto o bajo, la media se "deforma" hacia ese valor, alejándose de lo que la mayoría de los datos representan. A esto se le llama **sesgo**.

#### El ejemplo clásico: Los salarios
Imagina un grupo de 5 personas en una habitación:
*   4 personas ganan \$1,000 al mes.
*   1 persona (un millonario) gana \$1,000,000 al mes.

**Cálculo:**
*   **Media:** \$200,800.
*   **Mediana:** \$1,000.

Si dices: *"El sueldo promedio en esta habitación es de \$200,800"*, estás mintiendo sobre la realidad del grupo. El "promedio" no representa a nadie en la habitación. En este caso, la media es un **mal descriptor de la tendencia central**.

---

### 2. ¿Qué deberías usar en su lugar?

Dependiendo de tu objetivo, tienes varias alternativas:

#### A. La Mediana (La opción más segura)
La mediana es una medida de **tendencia central robusta**. No le importa qué tan grande es el valor más alto, solo le importa qué valor está justo en medio de la lista ordenada. En el ejemplo anterior, la mediana (\$1,000) describe perfectamente al grupo.

#### B. La Media Recortada (Trimmed Mean)
Si no quieres ignorar los datos por completo, puedes usar la media recortada. Consiste en eliminar un pequeño porcentaje de los valores más altos y más bajos (por ejemplo, el 5% superior y el 5% inferior) y luego calcular la media con el resto. Esto elimina el ruido de los outliers sin perder la estructura de los datos.

#### C. La Media Winsorizada
Similar a la anterior, pero en lugar de eliminar los valores extremos, los **reemplazas** por el valor más cercano que no sea un outlier (por ejemplo, el percentil 5 o 95). Esto mantiene el tamaño de la muestra intacto.

---

### 3. ¿Cuándo SÍ es correcto usar la media con outliers?

No siempre debes ignorar los outliers. Hay casos donde el outlier **es** la información más importante:

1.  **Gestión de Riesgos y Seguros:** Si eres una aseguradora, te interesa saber la media de los costos de accidentes, incluyendo los accidentes catastróficos (outliers). Si ignoras los outliers, quebrarás.
2.  **Presupuestos y Totales:** Si quieres saber cuánto dinero necesitas para pagar la nómina de una empresa, necesitas la suma total (y por tanto la media real). El hecho de que el CEO gane mucho es un dato que no puedes omitir de tu presupuesto.
3.  **Detección de Anomalías:** En ciberseguridad o control de calidad, el outlier es precisamente lo que estás buscando. El objetivo es estudiar el valor atípico, no "limpiarlo".

### Resumen rápido

| Situación | ¿Usar la Media? | Recomendación |
| :--- | :--- | :--- |
| Datos simétricos sin outliers | **Sí** | Es la medida más eficiente. |
| Datos con outliers (ej. salarios, precios) | **No** | Usa la **Mediana**. |
| Quieres eliminar el ruido pero mantener la muestra | **A medias** | Usa **Media Recortada**. |
| Estás analizando riesgos o totales financieros | **Sí** | El outlier es parte del costo real. |

En finanzas, donde la gestión del riesgo y la precisión en la estimación de expectativas son vitales, confiar en una media "contaminada" puede ocultar la realidad operativa o, peor aún, inflar artificialmente el rendimiento esperado.

Aquí te presento el desglose técnico de por qué ocurre esto y cuáles son las alternativas robustas que aplicamos en entornos profesionales.

---

### 1. El problema técnico: El "Breakdown Point"
La media aritmética tiene un **punto de ruptura (*breakdown point*) de $1/n$**. Esto significa que un solo valor extremadamente grande o pequeño puede desplazar la media de forma indefinida, independientemente del tamaño de la muestra.

Desde el rigor estadístico, la media es un estimador eficiente para distribuciones normales, pero es extremadamente sensible a la **asimetría (*skewness*)**. Si tienes una distribución con cola larga (como es común en los rendimientos de activos financieros o en la distribución de ingresos), la media no representará el "valor típico", sino que será un valor "atrapado" por el extremo.

### 2. Ejemplo Concreto: El sesgo en el análisis de carteras
Imagina que estás analizando el rendimiento mensual de un fondo de inversión de 10 activos durante un año:
*   9 activos rindieron un **1%** mensual.
*   1 activo (un "Unicornio" o un evento de volatilidad extrema) rindió un **150%**.

**Cálculo:**
*   **Media:** $(9 \times 1\% + 150\%) / 10 = \mathbf{15.9\%}$
*   **Mediana:** $\mathbf{1\%}$

Si presentas el **15.9%** como el rendimiento "típico" del fondo a un comité de riesgos, estás cometiendo un error de reporte. El 15.9% es un valor que ningún inversor promedio experimentó; es una distorsión causada por un evento único. La mediana, en cambio, te da la realidad de la experiencia del fondo.

---

### 3. Alternativas Robustas (Tu kit de herramientas)

Cuando detectamos *outliers*, no simplemente los "borramos" (lo cual también es un error si no se justifica), sino que cambiamos el estimador o tratamos el dato.

#### A. La Mediana (Estimador de posición)
Es la opción más sencilla y robusta. No le importa cuán grande sea el valor máximo, solo le importa cuántos datos hay por encima y por debajo. Es el estándar para reportar salarios o precios de activos con mucha volatilidad.

#### B. Media Truncada (*Trimmed Mean*)
Consiste en eliminar un porcentaje fijo de los valores más altos y más bajos (por ejemplo, el 5% superior y el 5% inferior) y luego calcular la media de los valores restantes.
*   **Uso:** Muy común en modelos de previsión de crecimiento para evitar que un trimestre extraordinario distorsione la proyección de largo plazo.

#### C. Media Winsorizada (*Winsorized Mean*)
A diferencia de la truncada, aquí no eliminamos los datos, sino que los **reemplazamos**. Los valores que están fuera de un percentil específico (ej. el percentil 95) se transforman en el valor de ese percentil.
*   **Ventaja:** Mantienes el tamaño de la muestra ($n$), lo que preserva el poder estadístico de tus pruebas de hipótesis, pero limitas el impacto de los extremos.

#### D. Estimadores M (*M-Estimators*)
En análisis de regresión avanzada, utilizamos estimadores de máxima verosimilitud que asignan pesos menores a los valores que se alejan de la tendencia central. En lugar de tratar a todos los puntos por igual, el algoritmo "castiga" la influencia de los *outliers*.

---

### 4. El matiz de experto: ¿Cuándo SÍ debemos mirar el *outlier*?

Como analista senior, debo advertirte: **No confundas un error de datos con un evento de cola (*tail event*).**

1.  **Si el *outlier* es un error de entrada de datos (Data Entry Error):** Elimínalo o corrígelo inmediatamente. No tiene valor informativo.
2.  **Si el *outlier* es un evento real (ej. un *Flash Crash* o un Cisne Negro):** No lo ignores. En gestión de riesgos (como en el cálculo del **VaR - Value at Risk**), el objetivo no es saber qué es lo "típico", sino precisamente qué tan catastrófico puede ser el extremo.

**Conclusión:** Si tu objetivo es **describir la tendencia central** de una población, usa la **mediana** o la **media winsorizada**. Si tu objetivo es **gestionar el riesgo**, estudia el *outlier* con lupa; ahí es donde se pierde el dinero.

### 1. ¿Qué es un número primo de Mersenne?
Un **número primo de Mersenne** es un número primo que tiene la forma específica:
$$M_n = 2^n - 1$$
Donde $n$ es un número entero. Para que $M_n$ sea un número primo, es una condición necesaria (aunque no suficiente) que el exponente $n$ también sea un número primo.

### 2. ¿Cómo se comprueba si un número es primo de Mersenne?
Para determinar si un número $N$ es un primo de Mersenne, se debe seguir este proceso lógico:

1.  **Verificar la forma:** Intentar resolver la ecuación $N = 2^n - 1$ para encontrar el valor de $n$. Esto se hace sumando 1 al número y verificando si el resultado es una potencia exacta de 2 ($N + 1 = 2^n$).
2.  **Comprobar la integridad de $n$:** Si el valor de $n$ obtenido no es un número entero, entonces el número no pertenece a la familia de los números de Mersenne.
3.  **Verificar la condición de $n$:** Si $n$ es un entero, este debe ser un número primo para que $N$ sea un candidato a primo de Mersenne.
4.  **Prueba de primalidad:** Si se cumplen los pasos anteriores, se debe aplicar un test de primalidad (como el test de Lucas-Lehmer) para confirmar que el resultado de $2^n - 1$ es efectivamente un número primo.

### 3. Aplicación del método a 17 y conclusión

**Paso 1: Intentar expresar 17 en la forma $2^n - 1$**
Planteamos la ecuación:
$$17 = 2^n - 1$$

Sumamos 1 a ambos lados para despejar la potencia:
$$17 + 1 = 2^n$$
$$18 = 2^n$$

**Paso 2: Comprobar si 18 es una potencia de 2**
Buscamos potencias de 2 cercanas a 18:
*   $2^4 = 16$
*   $2^5 = 32$

Como vemos, $16 < 18 < 32$. No existe ningún número entero $n$ que satisfaga la igualdad $2^n = 18$. Si lo calculamos con logaritmos, $n = \log_2(18) \approx 4.17$.

**Conclusión:**
Dado que $n$ no es un número entero, el número 17 no tiene la forma $2^n - 1$. Por lo tanto, **17 no es un número primo de Mersenne.**

## Prompt Engineering Avanzado {#sec-prompt-engineering}

### ¿Qué es un prompt? {#sec-que-es-prompt}

Un prompt es la instrucción textual que le damos a un LLM. Piensa en ello como la pregunta o la orden que le das a un asistente muy capaz pero muy literal: si la instrucción es ambigua, la respuesta será imprecisa. Si es clara y con contexto, la respuesta será mucho mejor.

El Prompt Engineering consiste en diseñar estas instrucciones de forma sistemática para obtener respuestas fiables, estructuradas y útiles, no solo "texto bonito".

```{python}
if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    prompt_few_shot = """
    Clasifica el sentimiento de cada frase como POSITIVO, NEGATIVO o NEUTRAL.

    Ejemplos:
    Frase: "El producto llegó roto y la atención fue pésima" → NEGATIVO
    Frase: "Todo perfecto, entrega rápida y bien embalado" → POSITIVO
    Frase: "El paquete llegó ayer por la tarde" → NEUTRAL

    Ahora clasifica:
    Frase: "El diseño es bonito pero la batería no dura nada"
    """

    respuesta = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": prompt_few_shot}]
    )
    print(respuesta.choices[0].message.content)
```

**¿Por qué funciona?** Los LLM son excelentes reconociendo patrones. Al darles 2-3 ejemplos, el modelo "aprende" el patrón en contexto (*in-context learning*) sin necesidad de fine-tuning.

::: {.callout-tip}
## Regla de oro del few-shot
- 2-3 ejemplos suelen bastar
- Los ejemplos deben cubrir los casos extremos (edge cases)
- Mantén consistencia exacta en el formato de los ejemplos
:::

### Zero-shot vs Few-shot vs One-shot {#sec-zero-one-few-shot}

: Comparativa de estrategias de prompting por número de ejemplos {#tbl-prompt-estrategias}

| Estrategia | Ejemplos en el prompt | Cuándo usarlo |
|---|---|---|
| **Zero-shot** | 0 — solo la instrucción | Tareas sencillas, modelos muy capaces |
| **One-shot** | 1 ejemplo | Cuando necesitas mostrar el formato exacto |
| **Few-shot** | 2-5 ejemplos | Tareas complejas, formatos muy específicos |

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    # ZERO-SHOT: sin ejemplos
    respuesta_zero = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": "Traduce al inglés: 'El gato está en el tejado'"}]
    )

    # ONE-SHOT: un ejemplo
    respuesta_one = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": """
    Traduce español → inglés.
    Ejemplo: "Hola mundo" → "Hello world"
    Ahora traduce: "El gato está en el tejado"
    """}]
    )

    print("Zero-shot:", respuesta_zero.choices[0].message.content)
    print("One-shot:", respuesta_one.choices[0].message.content)
```

### Chain-of-Thought (CoT) {#sec-cot}

El Chain-of-Thought consiste en pedir al modelo que razone paso a paso antes de dar la respuesta final. La clave está en añadir algo como _"pensemos paso a paso"_ o incluir ejemplos donde se muestra el razonamiento.

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    problema = """
    Un tren sale de Madrid a las 08:00 hacia Barcelona (620 km) a 120 km/h.
    Otro tren sale de Barcelona a las 09:00 hacia Madrid a 150 km/h.
    ¿A qué hora se cruzan?
    """

    prompt_cot = f"""
    {problema}

    Resuelve paso a paso:
    1. Calcula cuánto ha avanzado el primer tren cuando sale el segundo
    2. Calcula la distancia restante entre ambos en ese momento
    3. Calcula el tiempo hasta que se cruzan
    4. Suma el tiempo a la hora de salida
    """

    respuesta_cot = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": prompt_cot}]
    )
    print(respuesta_cot.choices[0].message.content)
```

::: {#fig-cot}
```{mermaid}
graph TD
    A[Pregunta compleja] --> B[LLM razona paso a paso]
    B --> C[Paso 1: identifica datos]
    C --> D[Paso 2: calcula intermedio]
    D --> E[Paso 3: combina resultados]
    E --> F[Respuesta final<br/>razonada y verificable]

    style A fill:#4B8BBE,color:#fff
    style F fill:#2e7d32,color:#fff
```
:::

**¿Por qué funciona?** Al obligar al modelo a generar tokens intermedios de razonamiento, cada paso condiciona el siguiente. Es como si el modelo "pensara en voz alta", reduciendo drásticamente los errores en tareas matemáticas y lógicas.

### Tree-of-Thought (ToT) {#sec-tot}

El Tree-of-Thought extiende CoT: en lugar de un único camino de razonamiento, el modelo explora múltiples ramas y elige la mejor. Es útil para problemas con múltiples soluciones posibles (planificación, puzles, creatividad).

::: {#fig-tot}
```{mermaid}

    B2 --> C3[Desarrollo 2A]
    B3 --> C4[Desarrollo 3A]
    B3 --> C5[Desarrollo 3B]

    C3 --> D
    C4 --> D
    D --> E[Solución<br/>óptima]

    style E fill:#2e7d32,color:#fff
    style D fill:#e65100,color:#fff
```
:::

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    prompt_tot = """
    Quiero organizar una jornada de team building de 4 horas para 20 personas de un equipo de Data Science.

    Genera 3 enfoques distintos y para cada uno:
    - Describe brevemente la actividad principal
    - Evalúa pros y contras (coste, engagement, logística)
    - Elige el mejor y justifica por qué

    Al final, desarrolla en detalle solo la opción elegida.
    """

    respuesta = client.chat.completions.create(

```

ToT requiere más tokens (y por tanto más coste) que CoT simple, ya que se generan y evalúan múltiples ramas. En la práctica, se implementa con múltiples llamadas al LLM o agentes que evalúan cada rama.
:::

### Output Structuring con JSON Schema {#sec-output-structuring}

Forzar que el modelo devuelva JSON nos permite integrar el LLM en pipelines automatizados. La API de OpenAI ofrece el parámetro `response_format` para garantizar JSON válido:

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    texto_a_analizar = """
    Reunión del 15/03/2026. Asistentes: Ana (Data), Carlos (ML), Bea (Product).
    Se acordó migrar el pipeline ETL a Spark antes del Q2.
    Presupuesto estimado: 45.000€. Carlos se encarga de la POC.
    """

    system_prompt = f"""Eres un extractor de datos de actas de reunión.
Devuelve ÚNICAMENTE un JSON válido con esta estructura exacta, sin texto adicional:
{{
  "fecha": "string (formato YYYY-MM-DD)",
  "asistentes": ["lista de nombres"],
  "decisiones": ["lista de decisiones tomadas"],
  "presupuesto_euros": 0.0,
  "responsables": [{{"nombre": "string", "tarea": "string"}}]
}}"""

    respuesta = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": texto_a_analizar}
        ],
    )

    try:
        resultado = parse_json_response(respuesta.choices[0].message.content)
        print(json.dumps(resultado, indent=2, ensure_ascii=False))
    except json.JSONDecodeError:
        print("⚠️ El modelo no devolvió JSON válido. Intenta de nuevo o usa un modelo con soporte nativo de structured output.")
        print(respuesta.choices[0].message.content[:200])
```

::: {.callout-important}
## JSON vía prompt vs. structured output nativo

Pedir JSON en el prompt funciona con cualquier modelo, pero no garantiza que el JSON sea válido (por eso añadimos `try/except`). Algunos modelos como Qwen 3 ofrecen `response_format` nativo que fuerza la estructura desde la API. La ventaja del prompting es que es model-agnostic: funciona con Gemma, Llama, Mistral, etc.
:::

### De JSON Schema a datos sintéticos: el enfoque intuitivo {#sec-json-schema-datos-sint}

Lo que acabas de hacer —extraer 1 registro JSON de un texto— es el mismo mecanismo que permite generar datasets sintéticos completos. La diferencia es de escala: en lugar de pedir 1 registro, pides N. En lugar de extraer de un texto real, pides al modelo que *invente* datos verosímiles.

La receta es simple:

1. **Define el schema** de tus datos (igual que en la sección anterior)
2. **Añade few-shot examples** para que el modelo entienda el dominio y los rangos esperados
3. **Controla la diversidad** con temperatura: baja produce datos conservadores, alta inyecta variedad
4. **Itera en batch** para generar cientos o miles de registros

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    import pandas as pd

    system_prompt = """Eres un generador de datos sintéticos de clientes españoles.
Devuelve ÚNICAMENTE un JSON válido con esta estructura exacta, sin texto adicional:
{
  "clientes": [
    {
      "id": 1,
      "edad": 34,
      "ingresos_anuales": 42000.0,
      "provincia": "Madrid",
      "segmento": "premium"
    }
  ]
}
Reglas:
- Edad entre 18 y 80 años
- Ingresos entre 12000 y 120000, correlacionados con la edad
- Provincias: Madrid, Barcelona, Valencia, Sevilla, Bilbao, Málaga, Zaragoza
- Segmentos: premium, estandar, basic
- Genera variedad realista"""

    respuesta = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        temperature=0.8,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": "Genera 10 clientes sintéticos. Usa variedad realista en edades, ingresos y provincias."}
        ],
    )

    try:
        datos = parse_json_response(respuesta.choices[0].message.content)
        df = pd.DataFrame(datos["clientes"])
        print(df.to_string(index=False))
        print(f"\n{len(df)} registros generados")
        print(f"   Edad: {df['edad'].min()}-{df['edad'].max()} (media {df['edad'].mean():.0f})")
        print(f"   Ingresos: {df['ingresos_anuales'].min():.0f}-{df['ingresos_anuales'].max():.0f} (media {df['ingresos_anuales'].mean():.0f})")
    except (json.JSONDecodeError, KeyError) as e:
        print(f"⚠️ Error al parsear respuesta: {e}")
        print(respuesta.choices[0].message.content[:200])
```

::: {.callout-tip}
## ¿Por qué funciona?

El LLM no "conoce" clientes reales, pero ha visto millones de patrones en sus datos de entrenamiento: distribuciones de edad, rangos de ingresos típicos, provincias españolas. El prompt con el schema, el few-shot y la temperatura controlan estructura, dominio y diversidad. Algunos modelos (Qwen, OpenAI) ofrecen además `response_format` nativo para forzar la estructura desde la API.

**Este es el enfoque más intuitivo y accesible para datos sintéticos:**
- Sin entrenar modelos adicionales
- Sin GPU
- En menos de 20 líneas de código
- Funciona con cualquier modelo (Gemma, Qwen, Llama, etc.)
- Ideal para prototipado, testing y aumento rápido de datasets pequeños
:::

::: {.callout-warning}
## Limitaciones del enfoque intuitivo

- No garantiza correlaciones realistas entre columnas (p. ej. ingresos frente a edad pueden no seguir la relación esperada)
- Puede generar valores atípicos no representativos
- Depende de la calidad del prompt y los ejemplos
- No hay garantía de privacidad diferencial

Para datasets de producción donde la fidelidad estadística es crítica, necesitarás modelos generativos especializados (CTGAN, TVAE, TabDDPM) que veremos en el Bloque 3 con SDV.
:::

### Role Prompting {#sec-role-prompting}

Asignar un rol al modelo en el mensaje `system` cambia radicalmente su comportamiento. No es magia: el modelo, entrenado con textos de diversos perfiles, "activa" los patrones asociados a ese rol.

```{python}
#| echo: true

        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,

            {"role": "system", "content": rol},
            {"role": "user", "content": pregunta}

    ).choices[0].message.content

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")

    print(consultar_como("Eres un asistente útil.", "¿Qué opinas de usar la media en datos con outliers?"))

    # Con rol de analista senior
    print("\n=== ANALISTA SENIOR ===")

        "Eres un analista de datos senior con 15 años de experiencia en finanzas. "
        "Respondes con rigor estadístico, mencionas alternativas robustas y das ejemplos concretos.",
        "¿Qué opinas de usar la media en datos con outliers?"
    ))

    # Con rol de profesor divulgador
    print("\n=== PROFESOR DIVULGADOR ===")
    print(consultar_como(
        "Eres un profesor de estadística que explica conceptos a estudiantes de primero de carrera. "
        "Usas analogías cotidianas, evitas jerga innecesaria y pones ejemplos sencillos.",
        "¿Qué opinas de usar la media en datos con outliers?"
    ))
```

### Técnicas adicionales {#sec-tecnicas-adicionales}

: Técnicas avanzadas de prompting y cuándo aplicarlas {#tbl-prompt-tecnicas}

| Técnica | Descripción | Cuándo usarla |
|---|---|---|
| **Self-consistency** | Ejecutar CoT varias veces y votar la respuesta mayoritaria | Razonamiento matemático/lógico |
| **Generated knowledge** | Pedir al modelo que genere contexto antes de responder | Preguntas que requieren conocimiento factual |
| **Re-reading (RE2)** | Hacer que el modelo lea la pregunta dos veces | Mejora comprensión en tareas largas |
| **Emotion prompting** | Añadir estímulos emocionales al prompt | Tareas creativas o subjetivas |
| **Step-back prompting** | Preguntar primero por principios generales | Problemas muy específicos |

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    prompt_step_back = """
    Pregunta original: ¿Es 17 un número primo de Mersenne?

    Antes de responder, contesta:
    1. ¿Qué es un número primo de Mersenne? (definición general)
    2. ¿Cómo se comprueba si un número es primo de Mersenne? (método)
    3. Ahora aplica el método a 17 y concluye.
    """

    print(client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": prompt_step_back}]
    ).choices[0].message.content)
```

### Buenas prácticas resumen {#sec-buenas-practicas-prompt}

1. **Sé específico**: "analiza los datos" → malo. "calcula media, mediana y desviación típica de la columna 'ventas' agrupada por 'región'" → bueno
2. **Muestra, no solo digas**: incluye ejemplos del formato que esperas (few-shot)
3. **Divide y vencerás**: tareas complejas → CoT, desglosa en pasos
4. **Formato forzado**: usa `response_format` / JSON Schema cuando integres con código
5. **Itera**: el primer prompt casi nunca es el óptimo. Prueba, compara, mejora
6. **System prompt**: define el tono, rol y restricciones al inicio
