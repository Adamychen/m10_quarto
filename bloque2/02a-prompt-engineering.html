Prompt Engineering Avanzado

¿Qué es un prompt?

Un prompt es la instrucción textual que le damos a un LLM. Piensa en ello como la pregunta o la orden que le das a un asistente muy capaz pero muy literal: si la instrucción es ambigua, la respuesta será imprecisa. Si es clara y con contexto, la respuesta será mucho mejor.

El Prompt Engineering consiste en diseñar estas instrucciones de forma sistemática para obtener respuestas fiables, estructuradas y útiles, no solo “texto bonito”.

Primer contacto: llamada a un LLM

Antes de profundizar, veamos cómo invocar un LLM desde Python con la API de OpenAI (compatible con Llamus US, Ollama local, etc.):

Few-shot prompting

El few-shot consiste en incluir ejemplos dentro del prompt para que el modelo entienda exactamente qué formato y estilo esperamos. Es como enseñarle con el ejemplo.

    Frase: "El paquete llegó ayer por la tarde" → NEUTRAL

    Frase: "El diseño es bonito pero la batería no dura nada"
    """

    respuesta = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,

Frase: "El diseño es bonito pero la batería no dura nada" → NEGATIVO

¿Por qué funciona? Los LLM son excelentes reconociendo patrones. Al darles 2-3 ejemplos, el modelo “aprende” el patrón en contexto (in-context learning) sin necesidad de fine-tuning.

TipRegla de oro del few-shot
  • 2-3 ejemplos suelen bastar
  • Los ejemplos deben cubrir los casos extremos (edge cases)
  • Mantén consistencia exacta en el formato de los ejemplos

Chain-of-Thought (CoT)

El Chain-of-Thought consiste en pedir al modelo que razone paso a paso antes de dar la respuesta final. La clave está en añadir algo como “pensemos paso a paso” o incluir ejemplos donde se muestra el razonamiento.

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    problema = """
    Un tren sale de Madrid a las 08:00 hacia Barcelona (620 km) a 120 km/h.
    Otro tren sale de Barcelona a las 09:00 hacia Madrid a 150 km/h.
    ¿A qué hora se cruzan?
    """

    prompt_cot = f"""
    {problema}

    Resuelve paso a paso:
    1. Calcula cuánto ha avanzado el primer tren cuando sale el segundo
    2. Calcula la distancia restante entre ambos en ese momento
    3. Calcula el tiempo hasta que se cruzan
    4. Suma el tiempo a la hora de salida
    """

    respuesta_cot = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": prompt_cot}]
    )
    print(respuesta_cot.choices[0].message.content)
Aquí tienes la resolución paso a paso siguiendo tus instrucciones:

### 1. Calcula cuánto ha avanzado el primer tren cuando sale el segundo
*   El primer tren sale a las **08:00**.
*   El segundo tren sale a las **09:00**.
*   El primer tren ha estado viajando solo durante **1 hora**.
*   Distancia = Velocidad $\times$ Tiempo
*   $120\text{ km/h} \times 1\text{ h} = \mathbf{120\text{ km}}$

### 2. Calcula la distancia restante entre ambos en ese momento
*   La distancia total inicial es de **620 km**.
*   Restamos lo que ya recorrió el primer tren:
*   $620\text{ km} - 120\text{ km} = \mathbf{500\text{ km}}$ (Esta es la distancia que separa a ambos trenes a las 09:00).

### 3. Calcula el tiempo hasta que se cruzan
Para saber cuánto tardan en encontrarse una vez que ambos están en movimiento, usamos la **velocidad relativa** (la suma de ambas velocidades, ya que van uno hacia el otro):

*   Velocidad combinada = $120\text{ km/h} + 150\text{ km/h} = \mathbf{270\text{ km/h}}$
*   $\text{Tiempo} = \frac{\text{Distancia restante}}{\text{Velocidad combinada}}$
*   $\text{Tiempo} = \frac{500\text{ km}}{270\text{ km/h}} \approx 1.8518\text{ horas}$

**Convertimos ese tiempo a horas y minutos:**
*   $1\text{ hora}$ completa.
*   $0.8518 \text{ horas} \times 60 \text{ minutos} \approx \mathbf{51 \text{ minutos}}$

### 4. Suma el tiempo a la hora de salida
Tomamos la hora en la que ambos empezaron a moverse hacia el encuentro (las **09:00**) y le sumamos el tiempo calculado:

*   $09:00 + 1\text{ hora y } 51\text{ minutos} = \mathbf{10:51}$

**Respuesta:**
Los trenes se cruzan a las **10:51**.

¿Por qué funciona? Al obligar al modelo a generar tokens intermedios de razonamiento, cada paso condiciona el siguiente. Es como si el modelo “pensara en voz alta”, reduciendo drásticamente los errores en tareas matemáticas y lógicas.

Tree-of-Thought (ToT)

El Tree-of-Thought extiende CoT: en lugar de un único camino de razonamiento, el modelo explora múltiples ramas y elige la mejor. Es útil para problemas con múltiples soluciones posibles (planificación, puzles, creatividad).

Para un equipo de **Data Science**, el perfil suele ser analítico, orientado a la resolución de problemas, con alta capacidad de concentración pero también con una carga cognitiva elevada debido al trabajo con abstracciones y pantallas.

Aquí tienes tres propuestas diseñadas para equilibrar la cohesión de equipo con el tipo de mentalidad de este perfil.

---

### Propuesta 1: "The Logic Escape" (Enfoque Intelectual)
**Actividad:** Un *Escape Room* temático o un juego de pistas basado en lógica y resolución de acertijos. Se divide al equipo en 4 grupos de 5 personas. Deben resolver una serie de retos lógicos, patrones y descifrado de códigos para "escapar" o cumplir una misión.

*   **Pros:**
    *   **Engagement:** Muy alto. Aprovecha sus habilidades naturales de pensamiento lateral y deducción.
    *   **Coste:** Medio (depende de si se contrata un local profesional o se diseña uno *in-house*).
    *   **Logística:** Sencilla si se alquila un espacio profesional.
*   **Contras:**
    *   **Riesgo:** Puede sentirse "demasiado parecido al trabajo" si los retos son puramente matemáticos o de código, generando fatiga mental en lugar de relax.

### Propuesta 2: "The Sensory Lab" (Enfoque Creativo/Sensorial)
**Actividad:** Un taller de cocina colaborativa (ej. hacer sushi, pasta fresca o una cata de vinos/café guiada). El equipo se divide en brigadas donde cada uno tiene un rol (líder de línea, preparación, emplatado) para lograr un resultado final común.

*   **Pros:**
    *   **Engagement:** Muy alto. Rompe totalmente con el entorno digital y obliga a usar los cinco sentidos.
    *   **Coste:** Medio/Alto (ingredientes y profesional).
    *   **Logística:** Requiere un espacio adecuado (cocina profesional o taller).
*   **Contras:**
    *   **Logística:** Puede haber restricciones por alergias o dietas (vegetarianos, celíacos, etc.).

### Propuesta 3: "The Strategy Board Games" (Enfoque Social/Relajado)
**Actividad:** Una tarde de juegos de mesa de estrategia cooperativa (tipo *Pandemic* o *Catan*) o competitiva. Se organizan mesas con diferentes niveles de dificultad y un facilitador que guía las reglas.

*   **Pros:**
    *   **Engagement:** Medio/Alto. Muy cómodo para perfiles introvertidos que prefieren reglas claras.
    *   **Coste:** Muy bajo (solo compra de juegos o alquiler de kits).
    *   **Logística:** Extremadamente sencilla (se puede hacer en la oficina o un café).
*   **Contras:**
    *   **Engagement:** Puede ser poco estimulante para quienes buscan una experiencia "fuera de lo común" o una desconexión total de la lógica.

---

### El Ganador: **Propuesta 2: "The Sensory Lab" (Taller de Cocina Colaborativa)**

**Justificación:**
Los equipos de Data Science pasan la mayor parte del día en un entorno de **abstracción pura** (modelos, código, datos que no se pueden tocar). Para un team building efectivo en este perfil, el mayor beneficio no viene de "usar más el cerebro para la lógica", sino de la **desconexión cognitiva y el anclaje sensorial**. La cocina ofrece una gratificación instantánea y tangible, fomenta la comunicación no verbal y permite la socialización orgánica mientras se comparte el producto final (la comida).

---

### Desarrollo Detallado: "The Data Chef Challenge" (4 Horas)

**Objetivo:** Fomentar la colaboración, la gestión de roles bajo presión y la comunicación efectiva a través de una experiencia táctil y deliciosa.

#### Cronograma de la jornada (Total: 4 horas)

**1. Bienvenida y "Data Warm-up" (30 min)**
*   **00:00 - 00:15:** Recepción con una bebida ligera.
*   **00:15 - 00:30:** Dinámica de integración rápida: "El ingrediente secreto". Cada persona debe decir su nombre y un ingrediente que represente su personalidad (ej. "Soy Juan y soy como la pimienta: aporto energía y un toque picante"). Esto rompe el hielo de forma ligera.

**2. El Desafío Culinario (2 horas)**
*   **00:30 - 00:45:** **Briefing del Chef:** Se presentan los ingredientes y la receta final. Se explican las reglas: "No es una competencia de quién es mejor cocinero, sino de cómo el equipo gestiona los recursos para que todos los platos salgan perfectos".
*   **00:45 - 02:30:** **La Acción:** El equipo de 20 personas se divide en 4 "Brigadas" de 5 personas. Cada brigada debe preparar una parte del menú (ej. Entrantes, Plato Principal, Guarnición, Postre) o trabajar de forma coordinada en un menú completo.
    *   *Roles asignados:* El Chef (líder), el Sous-chef (gestor de tiempos/recursos), los Prep-cooks (ejecución) y el Steward (limpieza/orden). Rotar roles ayuda a entender la importancia de cada función.

**3. El Banquete de Conexión (1 hora)**
*   **02:30 - 03:30:** **Degustación:** Se disponen mesas largas donde todos se sientan juntos. La clave aquí es que no se come por grupos, sino que se mezclan las brigadas. Es el momento de la charla relajada, sin hablar de modelos de regresión o despliegues de producción.

**4. Cierre y Reflexión (30 min)**
*   **03:30 - 03:50:** **Debriefing ligero:** El facilitador hace dos preguntas al grupo:
    1.  "¿Cuál fue el mayor 'bug' (error) que cometieron en la cocina y cómo lo solucionaron?"
    2.  "¿Quién fue el 'líder de datos' (el que mejor organizó los ingredientes/tiempos)?"
*   **03:50 - 04:00:** Entrega de un pequeño detalle (ej. un kit de especias gourmet) y despedida.

#### Requerimientos Logísticos para el Organizador:
1.  **Espacio:** Taller de cocina para 20 personas o un salón con estaciones de cocina portátiles.
2.  **Personal:** 1 Chef profesional y 1 facilitador/coordinador.
3.  **Presupuesto:** Debe incluir: Alquiler de espacio + Ingredientes + Bebidas + Kit de regalo final.
4.  **Gestión de Riesgos:** Formulario previo de alergias alimentarias (obligatorio).
Note

ToT requiere más tokens (y por tanto más coste) que CoT simple, ya que se generan y evalúan múltiples ramas. En la práctica, se implementa con múltiples llamadas al LLM o agentes que evalúan cada rama.

ImportantJSON vía prompt vs. structured output nativo

Pedir JSON en el prompt funciona con cualquier modelo, pero no garantiza que el JSON sea válido (por eso añadimos try/except). Algunos modelos como Qwen 3 ofrecen response_format nativo que fuerza la estructura desde la API. La ventaja del prompting es que es model-agnostic: funciona con Gemma, Llama, Mistral, etc.

De JSON Schema a datos sintéticos: el enfoque intuitivo

Lo que acabas de hacer —extraer 1 registro JSON de un texto— es el mismo mecanismo que permite generar datasets sintéticos completos. La diferencia es de escala: en lugar de pedir 1 registro, pides N. En lugar de extraer de un texto real, pides al modelo que invente datos verosímiles.

La receta es simple:

  1. Define el schema de tus datos (igual que en la sección anterior)
  2. Añade few-shot examples para que el modelo entienda el dominio y los rangos esperados
  3. Controla la diversidad con temperatura: baja produce datos conservadores, alta inyecta variedad
  4. Itera en batch para generar cientos o miles de registros

Aquí te explico el porqué, los riesgos y qué deberías usar en su lugar.

---

### 1. El problema: La sensibilidad de la media
La media aritmética es una medida de tendencia central que **no es robusta**. Esto significa que su valor depende de la magnitud de cada uno de los datos.

Si tienes un conjunto de datos, la media intenta "equilibrar" la suma total. Un solo valor extremadamente alto o bajo "tira" de la media hacia él, desplazándola de la zona donde se concentra la mayoría de los datos.

**Ejemplo clásico:**
Imagina los salarios de 5 personas en una pequeña oficina:
*   Persona A: \$1,000
*   Persona B: \$1,200
*   Persona C: \$1,100
*   Persona D: \$1,300
*   **Persona E (El jefe): \$20,000**

1.  **La Media es: \$4,920.** Si dices "el salario promedio en esta oficina es de casi \$5,000", estás dando una imagen falsa. Nadie gana cerca de eso; la mayoría gana alrededor de \$1,100.
2.  **La Mediana es: \$1,200.** Este valor representa mucho mejor la realidad de la mayoría de los empleados.

### 2. ¿Cuándo SÍ podrías usar la media a pesar de los outliers?
No siempre es un error. Hay casos donde el outlier es el dato más importante:

*   **Análisis de Riesgo o Seguros:** Si eres una aseguradora, no te importa el "cliente promedio"; te interesa el cliente con el accidente más catastrófico (el outlier), porque ese evento determinará tu pérdida.
*   **Gestión de Recursos:** Si estás calculando cuánta electricidad necesita un edificio, el consumo pico (el outlier) es más relevante que el consumo medio para evitar un apagón.
*   **Si el outlier es un error de medición:** Si sabes con certeza que el dato es un error (ej. una persona que midió 5 metros por un error del sensor), debes eliminarlo o corregirlo antes de calcular la media.

### 3. Alternativas recomendadas

Si tu objetivo es describir qué es lo "normal" o "típico" en tus datos, utiliza estas opciones:

1.  **La Mediana (La mejor opción):** Es altamente robusta. No le importa qué tan grande es el valor máximo, solo le importa cuántos datos hay a la izquierda y a la derecha.
2.  **Media Truncada (Trimmed Mean):** Consiste en eliminar un porcentaje de los valores más altos y más bajos (por ejemplo, el 5% superior y el 5% inferior) y luego calcular la media de lo que queda. Es un excelente equilibrio.
3.  **Media Winsorizada:** Similar a la truncada, pero en lugar de eliminar los valores extremos, los "sustituyes" por el valor más cercano que no sea un outlier.
4.  **Uso de la Mediana + Desviación Absoluta de la Mediana (MAD):** Si vas a usar la mediana para el centro, no uses la Desviación Estándar para la dispersión (porque la desviación estándar también es sensible a outliers). Usa el **MAD**, que es la versión robusta de la desviación.

### Resumen de decisión

| Situación | ¿Usar la Media? | Recomendación |
| :--- | :--- | :--- |
| Los datos son simétricos y sin outliers | **SÍ** | Es la medida más eficiente. |
| Los datos tienen outliers y quieres saber lo "típico" | **NO** | Usa la **Mediana**. |
| Los datos tienen outliers y quieres saber el "impacto total" | **SÍ** | La media captura la magnitud total. |
| Los outliers son errores de entrada | **NO** | Limpia los datos primero. |

En estadística, la media es un estimador **no robusto**. Esto significa que su valor es altamente sensible a los valores extremos. Un solo dato atípico puede "arrastrar" la media hacia él, alejándola de la verdadera tendencia central de la masa de datos.

Aquí te detallo el análisis técnico, las alternativas y el protocolo que aplicamos en entornos de alta exigencia.

---

### 1. El Problema: La sensibilidad de la función de pérdida
La media aritmética minimiza la suma de los cuadrados de las desviaciones. Matemáticamente, esto implica que al elevar la diferencia al cuadrado, los valores alejados del centro penalizan la función de manera desproporcionada. 

Si estás analizando retornos de activos y un día ocurre un "Black Swan" (un evento de cola extrema), la media de tus retornos mensuales se verá completamente distorsionada, dándote una falsa sensación de rendimiento (o de riesgo) que no representa la experiencia típica de tu cartera.

### 2. Alternativas Robustas
Cuando detectamos *outliers*, no buscamos "limpiar" los datos para que la media "se vea bien", sino elegir un estadístico que sea **resistente a la influencia de la cola**.

*   **La Mediana (Medida de tendencia central robusta):** Es el estadístico por excelencia cuando hay ruido. Al basarse en la posición y no en el valor absoluto, la mediana ignora la magnitud de los extremos.
    *   *Ejemplo:* En un análisis de salarios, la media suele estar inflada por unos pocos ejecutivos con sueldos astronómicos. La mediana te dice qué gana realmente el "empleado típico".
*   **Media Recortada (*Trimmed Mean*):** Consiste en eliminar un porcentaje fijo de los valores más altos y más bajos (por ejemplo, un 5% en cada extremo) y calcular la media del resto. Es un excelente equilibrio entre la media y la mediana.
*   **Media Winsorizada (*Winsorized Mean*):** En lugar de eliminar los valores, los "capamos". Sustituimos los valores atípicos por el valor más cercano que no sea un *outlier* (por ejemplo, el percentil 95). Esto mantiene el tamaño de la muestra pero limita el sesgo.
*   **Media Geométrica:** Crucial en finanzas para calcular tasas de crecimiento compuesto. Aunque es sensible a valores cercanos a cero, gestiona mejor la naturaleza multiplicativa de los retornos financieros que la media aritmética.

### 3. Ejemplo Concreto: Gestión de Riesgo de Crédito
Imagina que estás modelando la probabilidad de impago (*Probability of Default*) de una cartera de préstamos:

1.  **Escenario A (Media):** Tienes 100 préstamos. 99 se pagan bien y 1 es un fraude masivo de 1 millón de dólares. La media de pérdida te dirá que "en promedio todos somos riesgosos", lo que te llevará a subir las tasas de interés para clientes sanos de forma injustificada.
2.  **Escenario B (Mediana/Robustez):** Al usar medidas robustas, el modelo identifica que la "experiencia típica" del cliente es de riesgo cero, y el evento de 1 millón se trata como un evento de **cola (tail risk)** que se gestiona con capital de reserva, no con una alteración del perfil de riesgo del cliente promedio.

### 4. Protocolo de Decisión (El "Workflow" del Analista Senior)

Antes de decidir qué usar, te sugiero seguir este rigor:

1.  **Detección:** No confíes solo en la intuición. Usa el **Rango Intercuartílico (IQR)** para identificar valores fuera de $[Q1 - 1.5 \cdot IQR, Q3 + 1.5 \cdot IQR]$ o utiliza el **Z-Score** (si la distribución es aproximadamente normal).
2.  **Investigación de la causa:**
    *   ¿Es un **error de entrada de datos**? (Ej: un decimal mal puesto). Si es así, corrígelo o elimínalo.
    *   ¿Es un **error de medición**? (Ej: un sensor falló). Elimínalo.
    *   ¿Es un **evento real pero extremo**? (Ej: un crash de mercado). **¡No lo elimines!** Si lo eliminas, estás ignorando el riesgo de cola (*Fat Tails*). En este caso, usa medidas robustas para la tendencia central, pero usa la media para calcular el riesgo (Varianza/Desviación estándar) porque en finanzas, el riesgo *está* en el outlier.
3.  **Reporte dual:** En un informe profesional, nunca des una sola cifra si hay sospecha de sesgo. Presenta siempre: *"La media es X, pero la mediana (que es más representativa de la tendencia central) es Y"*.

**Conclusión:** Si los datos tienen *outliers*, la media es una mentira estadística si se presenta como la "verdad absoluta". Usa la mediana para entender el centro y usa modelos de cola (como la distribución t de Student) para entender el riesgo.

### El problema: El "Efecto Bill Gates"

Imagina que estamos en un aula con 10 estudiantes. Todos tienen un presupuesto mensual para gastos de 100 euros. Si calculamos la **media**, el promedio es 100 euros. Todo lógico, ¿verdad?

Pero de repente, entra por la puerta **Bill Gates**. 

Si Bill Gates se sienta con nosotros y decimos: *"Vamos a calcular el promedio de dinero que hay en este salón"*, el resultado va a ser de millones de euros. ### La solución: El "Héroe" llamado Mediana

Cuando hay outliers, yo siempre te voy a recomendar que mires también la **mediana**.

Si usamos la analogía anterior: la mediana es como si nos pusiéramos todos en fila por orden de cuánto dinero tenemos y yo simplemente mirara **quién es la persona que está justo en el medio**.

En nuestra clase con Bill Gates, si nos ponemos en fila, Bill Gates estará al final de la fila, pero la persona que está en el centro de la fila seguirá siendo un estudiante con 100 euros. La mediana no se deja engañar por el millonario; ella se queda con el "centro" real de la población.

### Entonces, ¿qué te aconsejo como profesor?

Cuando estés analizando datos, sigue esta regla de oro:

1.  **Si ves que la media y la mediana son muy diferentes**, ¡CUIDADO! Tienes outliers que te están engañando. Es como si la media te dijera que eres rico, pero tu cuenta bancaria te diga que no.
2.  **No ignores el outlier de inmediato.** Antes de borrarlo, pregúntate: ¿Es un error de dedo (alguien escribió 1000 en vez de 10)? Si es un error, bórralo. ¿Es un valor real pero extremo? Entonces no lo borres, pero **no uses solo la media para describir tus datos**.
3.  **Usa la mediana para describir el "centro"** si los datos son rebeldes.
4.  **Usa la media solo si tus datos son "comportados"** (es decir, si la mayoría de los valores están cerca unos de otros y no hay saltos absurdos).

**En resumen:** La media es muy inteligente para hacer cálculos matemáticos avanzados, pero es muy "susceptibles" a los chismes (los outliers). La mediana, en cambio, es más "terca" y prefiere quedarse con la realidad del grupo.

### 1. ¿Qué es un número primo de Mersenne?
Un **número primo de Mersenne** es un número primo que tiene la forma específica:
$$M_n = 2^n - 1$$
donde $n$ es un número entero. 

Es importante destacar una propiedad fundamental: para que $M_n$ sea un número primo, el exponente **$n$ también debe ser un número primo**. Sin embargo, que $n$ sea primo no garantiza automáticamente que $2^n - 1$ sea primo (por ejemplo, $2^{11} - 1 = 2047$, y aunque 11 es primo, 2047 no lo es, ya que es $23 \times 89$).

---

### 2. ¿Cómo se comprueba si un número es primo de Mersenne?
Para determinar si un número $N$ es un primo de Mersenne, se debe seguir este proceso lógico:

1.  **Verificar la forma de Mersenne:** Comprobar si el número puede escribirse como $2^n - 1$. Esto se hace sumando 1 al número ($N + 1$) y verificando si el resultado es una **potencia de 2** (es decir, si es $2, 4, 8, 16, 32, 64, \dots$).
2.  **Identificar el exponente ($n$):** Si es una potencia de 2, encontrar el valor de $n$ tal que $2^n = N + 1$.
3.  **Comprobar si $n$ es primo:** Si el exponente $n$ no es un número primo, el número $N$ no puede ser un primo de Mersenne.
4.  **Verificar la primalidad de $N$:** Si $n$ es primo, se debe confirmar que el número resultante $N$ sea efectivamente un número primo (usualmente mediante pruebas matemáticas avanzadas como el test de Lucas-Lehmer).

---

### 3. Aplicación del método a 17

Vamos a aplicar los pasos al número **17**:

*   **Paso 1: ¿Es de la forma $2^n - 1$?**
    Sumamos 1 al número: $17 + 1 = 18$.
    Ahora, buscamos si 18 es una potencia de 2.
    Las potencias de 2 cercanas son:
    $2^4 = 16$
    $2^5 = 32$
    Como podemos ver, **18 no es una potencia de 2**.

*   **Conclusión:**
    Dado que 17 no puede expresarse de la forma $2^n - 1$ con un exponente entero, **17 NO es un número primo de Mersenne**. (Aunque 17 es un número primo, no cumple con la estructura requerida para ser un primo de Mersenne).

### ¿Qué es un prompt? {#sec-que-es-prompt}

Un prompt es la instrucción textual que le damos a un LLM. Piensa en ello como la pregunta o la orden que le das a un asistente muy capaz pero muy literal: si la instrucción es ambigua, la respuesta será imprecisa. Si es clara y con contexto, la respuesta será mucho mejor.

El Prompt Engineering consiste en diseñar estas instrucciones de forma sistemática para obtener respuestas fiables, estructuradas y útiles, no solo "texto bonito".

```{python}
    print(respuesta.choices[0].message.content)
```

Este es el patrón base para todo lo que veremos: `model` + `messages` → respuesta. Los `messages` pueden tener varios roles:

: Roles de los mensajes en la API de chat {#tbl-roles-chat}

| Rol | Propósito | Ejemplo |
|---|---|---|
| `system` | Instrucción global de comportamiento | "Eres un analista de datos experto" |
| `user` | Pregunta o instrucción del usuario | "Analiza este CSV..." |
| `assistant` | Respuestas previas del modelo (historial) | "La media es 42.3..." |

### Few-shot prompting {#sec-few-shot}

El few-shot consiste en incluir ejemplos dentro del prompt para que el modelo entienda exactamente qué formato y estilo esperamos. Es como enseñarle con el ejemplo.

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    prompt_few_shot = """
    Clasifica el sentimiento de cada frase como POSITIVO, NEGATIVO o NEUTRAL.

    Ejemplos:
    Frase: "El producto llegó roto y la atención fue pésima" → NEGATIVO
    Frase: "Todo perfecto, entrega rápida y bien embalado" → POSITIVO
    Frase: "El paquete llegó ayer por la tarde" → NEUTRAL

    Ahora clasifica:
    Frase: "El diseño es bonito pero la batería no dura nada"
    """

    respuesta = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": prompt_few_shot}]
    )
    print(respuesta.choices[0].message.content)
```

**¿Por qué funciona?** Los LLM son excelentes reconociendo patrones. Al darles 2-3 ejemplos, el modelo "aprende" el patrón en contexto (*in-context learning*) sin necesidad de fine-tuning.

::: {.callout-tip}
## Regla de oro del few-shot
- 2-3 ejemplos suelen bastar
- Los ejemplos deben cubrir los casos extremos (edge cases)
- Mantén consistencia exacta en el formato de los ejemplos
:::

### Zero-shot vs Few-shot vs One-shot {#sec-zero-one-few-shot}

: Comparativa de estrategias de prompting por número de ejemplos {#tbl-prompt-estrategias}

| Estrategia | Ejemplos en el prompt | Cuándo usarlo |
|---|---|---|
| **Zero-shot** | 0 — solo la instrucción | Tareas sencillas, modelos muy capaces |
| **One-shot** | 1 ejemplo | Cuando necesitas mostrar el formato exacto |
| **Few-shot** | 2-5 ejemplos | Tareas complejas, formatos muy específicos |

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    # ZERO-SHOT: sin ejemplos
    respuesta_zero = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": "Traduce al inglés: 'El gato está en el tejado'"}]
    )

    # ONE-SHOT: un ejemplo
    respuesta_one = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": """
    Traduce español → inglés.
    Ejemplo: "Hola mundo" → "Hello world"
    Ahora traduce: "El gato está en el tejado"
    """}]
    )

    print("Zero-shot:", respuesta_zero.choices[0].message.content)
    print("One-shot:", respuesta_one.choices[0].message.content)
```

### Chain-of-Thought (CoT) {#sec-cot}

El Chain-of-Thought consiste en pedir al modelo que razone paso a paso antes de dar la respuesta final. La clave está en añadir algo como _"pensemos paso a paso"_ o incluir ejemplos donde se muestra el razonamiento.

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    problema = """
    Un tren sale de Madrid a las 08:00 hacia Barcelona (620 km) a 120 km/h.
    Otro tren sale de Barcelona a las 09:00 hacia Madrid a 150 km/h.
    ¿A qué hora se cruzan?
    """

    prompt_cot = f"""
    {problema}

    Resuelve paso a paso:
    1. Calcula cuánto ha avanzado el primer tren cuando sale el segundo
    2. Calcula la distancia restante entre ambos en ese momento
    3. Calcula el tiempo hasta que se cruzan
    4. Suma el tiempo a la hora de salida
    """

    respuesta_cot = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": prompt_cot}]
    )
    print(respuesta_cot.choices[0].message.content)
```

::: {#fig-cot}
```{mermaid}
graph TD
    A[Pregunta compleja] --> B[LLM razona paso a paso]
    B --> C[Paso 1: identifica datos]
    C --> D[Paso 2: calcula intermedio]
    D --> E[Paso 3: combina resultados]
    E --> F[Respuesta final<br/>razonada y verificable]

    style A fill:#4B8BBE,color:#fff
    style F fill:#2e7d32,color:#fff
```
:::

**¿Por qué funciona?** Al obligar al modelo a generar tokens intermedios de razonamiento, cada paso condiciona el siguiente. Es como si el modelo "pensara en voz alta", reduciendo drásticamente los errores en tareas matemáticas y lógicas.

### Tree-of-Thought (ToT) {#sec-tot}

El Tree-of-Thought extiende CoT: en lugar de un único camino de razonamiento, el modelo explora múltiples ramas y elige la mejor. Es útil para problemas con múltiples soluciones posibles (planificación, puzles, creatividad).

::: {#fig-tot}
```{mermaid}

    A --> B2[Idea 2]
    A --> B3[Idea 3]
    B1 --> C1[Desarrollo 1A]
    B1 --> C2[Desarrollo 1B]
    B2 --> C3[Desarrollo 2A]
    B3 --> C4[Desarrollo 3A]
    B3 --> C5[Desarrollo 3B]
    C1 --> D{Evaluar<br/>mejor rama}
    C3 --> D
    C4 --> D
    D --> E[Solución<br/>óptima]

    style A fill:#4B8BBE,color:#fff
    style E fill:#2e7d32,color:#fff
    style D fill:#e65100,color:#fff
```
:::

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    prompt_tot = """
    Quiero organizar una jornada de team building de 4 horas para 20 personas de un equipo de Data Science.

    Genera 3 enfoques distintos y para cada uno:
    - Describe brevemente la actividad principal
    - Evalúa pros y contras (coste, engagement, logística)
    - Elige el mejor y justifica por qué

    Al final, desarrolla en detalle solo la opción elegida.
    """

    respuesta = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": prompt_tot}]
    )
    print(respuesta.choices[0].message.content)
```

::: {.callout-note}
ToT requiere más tokens (y por tanto más coste) que CoT simple, ya que se generan y evalúan múltiples ramas. En la práctica, se implementa con múltiples llamadas al LLM o agentes que evalúan cada rama.
:::

### Output Structuring con JSON Schema {#sec-output-structuring}

Forzar que el modelo devuelva JSON nos permite integrar el LLM en pipelines automatizados. La API de OpenAI ofrece el parámetro `response_format` para garantizar JSON válido:

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    texto_a_analizar = """
    Reunión del 15/03/2026. Asistentes: Ana (Data), Carlos (ML), Bea (Product).
    Se acordó migrar el pipeline ETL a Spark antes del Q2.
    Presupuesto estimado: 45.000€. Carlos se encarga de la POC.
    """

    system_prompt = f"""Eres un extractor de datos de actas de reunión.
Devuelve ÚNICAMENTE un JSON válido con esta estructura exacta, sin texto adicional:
{{
  "fecha": "string (formato YYYY-MM-DD)",
  "asistentes": ["lista de nombres"],
  "decisiones": ["lista de decisiones tomadas"],
  "presupuesto_euros": 0.0,
  "responsables": [{{"nombre": "string", "tarea": "string"}}]
}}"""

    respuesta = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": texto_a_analizar}
        ],
    )

    try:
        resultado = parse_json_response(respuesta.choices[0].message.content)
        print(json.dumps(resultado, indent=2, ensure_ascii=False))
    except json.JSONDecodeError:
        print("⚠️ El modelo no devolvió JSON válido. Intenta de nuevo o usa un modelo con soporte nativo de structured output.")
        print(respuesta.choices[0].message.content[:200])
```

::: {.callout-important}
## JSON vía prompt vs. structured output nativo

Pedir JSON en el prompt funciona con cualquier modelo, pero no garantiza que el JSON sea válido (por eso añadimos `try/except`). Algunos modelos como Qwen 3 ofrecen `response_format` nativo que fuerza la estructura desde la API. La ventaja del prompting es que es model-agnostic: funciona con Gemma, Llama, Mistral, etc.
:::

### De JSON Schema a datos sintéticos: el enfoque intuitivo {#sec-json-schema-datos-sint}

Lo que acabas de hacer —extraer 1 registro JSON de un texto— es el mismo mecanismo que permite generar datasets sintéticos completos. La diferencia es de escala: en lugar de pedir 1 registro, pides N. En lugar de extraer de un texto real, pides al modelo que *invente* datos verosímiles.

La receta es simple:

1. **Define el schema** de tus datos (igual que en la sección anterior)
2. **Añade few-shot examples** para que el modelo entienda el dominio y los rangos esperados
3. **Controla la diversidad** con temperatura: baja produce datos conservadores, alta inyecta variedad
4. **Itera en batch** para generar cientos o miles de registros

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    import pandas as pd

    system_prompt = """Eres un generador de datos sintéticos de clientes españoles.
Devuelve ÚNICAMENTE un JSON válido con esta estructura exacta, sin texto adicional:
{
  "clientes": [
    {
      "id": 1,
      "edad": 34,
      "ingresos_anuales": 42000.0,
      "provincia": "Madrid",
      "segmento": "premium"
    }
  ]
}
Reglas:
- Edad entre 18 y 80 años
- Ingresos entre 12000 y 120000, correlacionados con la edad
- Provincias: Madrid, Barcelona, Valencia, Sevilla, Bilbao, Málaga, Zaragoza
- Segmentos: premium, estandar, basic
- Genera variedad realista"""

    respuesta = client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        temperature=0.8,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": "Genera 10 clientes sintéticos. Usa variedad realista en edades, ingresos y provincias."}
        ],
    )

    try:
        datos = parse_json_response(respuesta.choices[0].message.content)
        df = pd.DataFrame(datos["clientes"])
        print(df.to_string(index=False))
        print(f"\n{len(df)} registros generados")
        print(f"   Edad: {df['edad'].min()}-{df['edad'].max()} (media {df['edad'].mean():.0f})")
        print(f"   Ingresos: {df['ingresos_anuales'].min():.0f}-{df['ingresos_anuales'].max():.0f} (media {df['ingresos_anuales'].mean():.0f})")
    except (json.JSONDecodeError, KeyError) as e:
        print(f"⚠️ Error al parsear respuesta: {e}")
        print(respuesta.choices[0].message.content[:200])
```

::: {.callout-tip}
## ¿Por qué funciona?

El LLM no "conoce" clientes reales, pero ha visto millones de patrones en sus datos de entrenamiento: distribuciones de edad, rangos de ingresos típicos, provincias españolas. El prompt con el schema, el few-shot y la temperatura controlan estructura, dominio y diversidad. Algunos modelos (Qwen, OpenAI) ofrecen además `response_format` nativo para forzar la estructura desde la API.

**Este es el enfoque más intuitivo y accesible para datos sintéticos:**
- Sin entrenar modelos adicionales
- Sin GPU
- En menos de 20 líneas de código
- Funciona con cualquier modelo (Gemma, Qwen, Llama, etc.)
- Ideal para prototipado, testing y aumento rápido de datasets pequeños
:::

::: {.callout-warning}
## Limitaciones del enfoque intuitivo

- No garantiza correlaciones realistas entre columnas (p. ej. ingresos frente a edad pueden no seguir la relación esperada)
- Puede generar valores atípicos no representativos
- Depende de la calidad del prompt y los ejemplos
- No hay garantía de privacidad diferencial

Para datasets de producción donde la fidelidad estadística es crítica, necesitarás modelos generativos especializados (CTGAN, TVAE, TabDDPM) que veremos en el Bloque 3 con SDV.
:::

### Role Prompting {#sec-role-prompting}

Asignar un rol al modelo en el mensaje `system` cambia radicalmente su comportamiento. No es magia: el modelo, entrenado con textos de diversos perfiles, "activa" los patrones asociados a ese rol.

```{python}
#| echo: true

def consultar_como(rol, pregunta):
    return client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[
            {"role": "system", "content": rol},
            {"role": "user", "content": pregunta}
        ]
    ).choices[0].message.content

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    # Sin rol (genérico)
    print("=== SIN ROL ===")
    print(consultar_como("Eres un asistente útil.", "¿Qué opinas de usar la media en datos con outliers?"))

    # Con rol de analista senior
    print("\n=== ANALISTA SENIOR ===")
    print(consultar_como(
        "Eres un analista de datos senior con 15 años de experiencia en finanzas. "
        "Respondes con rigor estadístico, mencionas alternativas robustas y das ejemplos concretos.",
        "¿Qué opinas de usar la media en datos con outliers?"
    ))

    # Con rol de profesor divulgador
    print("\n=== PROFESOR DIVULGADOR ===")
    print(consultar_como(
        "Eres un profesor de estadística que explica conceptos a estudiantes de primero de carrera. "
        "Usas analogías cotidianas, evitas jerga innecesaria y pones ejemplos sencillos.",
        "¿Qué opinas de usar la media en datos con outliers?"
    ))
```

### Técnicas adicionales {#sec-tecnicas-adicionales}

: Técnicas avanzadas de prompting y cuándo aplicarlas {#tbl-prompt-tecnicas}

| Técnica | Descripción | Cuándo usarla |
|---|---|---|
| **Self-consistency** | Ejecutar CoT varias veces y votar la respuesta mayoritaria | Razonamiento matemático/lógico |
| **Generated knowledge** | Pedir al modelo que genere contexto antes de responder | Preguntas que requieren conocimiento factual |
| **Re-reading (RE2)** | Hacer que el modelo lea la pregunta dos veces | Mejora comprensión en tareas largas |
| **Emotion prompting** | Añadir estímulos emocionales al prompt | Tareas creativas o subjetivas |
| **Step-back prompting** | Preguntar primero por principios generales | Problemas muy específicos |

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    prompt_step_back = """
    Pregunta original: ¿Es 17 un número primo de Mersenne?

    Antes de responder, contesta:
    1. ¿Qué es un número primo de Mersenne? (definición general)
    2. ¿Cómo se comprueba si un número es primo de Mersenne? (método)
    3. Ahora aplica el método a 17 y concluye.
    """

    print(client.chat.completions.create(
        model=os.getenv("LLM_MODEL", "gemma4:26b"),
        max_tokens=2048,
        messages=[{"role": "user", "content": prompt_step_back}]
    ).choices[0].message.content)
```

### Buenas prácticas resumen {#sec-buenas-practicas-prompt}

1. **Sé específico**: "analiza los datos" → malo. "calcula media, mediana y desviación típica de la columna 'ventas' agrupada por 'región'" → bueno
2. **Muestra, no solo digas**: incluye ejemplos del formato que esperas (few-shot)
3. **Divide y vencerás**: tareas complejas → CoT, desglosa en pasos
4. **Formato forzado**: usa `response_format` / JSON Schema cuando integres con código
5. **Itera**: el primer prompt casi nunca es el óptimo. Prueba, compara, mejora
6. **System prompt**: define el tono, rol y restricciones al inicio
