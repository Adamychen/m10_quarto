Prompt Engineering Avanzado

¿Qué es un prompt?

Un prompt es la instrucción textual que le damos a un LLM. Piensa en ello como la pregunta o la orden que le das a un asistente muy capaz pero muy literal: si la instrucción es ambigua, la respuesta será imprecisa. Si es clara y con contexto, la respuesta será mucho mejor.

El Prompt Engineering consiste en diseñar estas instrucciones de forma sistemática para obtener respuestas fiables, estructuradas y útiles, no solo “texto bonito”.

Primer contacto: llamada a un LLM

Antes de profundizar, veamos cómo invocar un LLM desde Python con la API de OpenAI (compatible con Llamus US, Ollama local, etc.):

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    respuesta = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[{"role": "user", "content": "Explica qué es la desviación estándar en una frase."}]
    )
    print(respuesta.choices[0].message.content)
La desviación estándar es una medida que indica cuánto se dispersan o varían los datos alrededor de su promedio.

Este es el patrón base para todo lo que veremos: model + messages → respuesta. Los messages pueden tener varios roles:

Few-shot prompting

El few-shot consiste en incluir ejemplos dentro del prompt para que el modelo entienda exactamente qué formato y estilo esperamos. Es como enseñarle con el ejemplo.

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    prompt_few_shot = """
    Clasifica el sentimiento de cada frase como POSITIVO, NEGATIVO o NEUTRAL.

    Ejemplos:
    Frase: "El producto llegó roto y la atención fue pésima" → NEGATIVO
    Frase: "Todo perfecto, entrega rápida y bien embalado" → POSITIVO
    Frase: "El paquete llegó ayer por la tarde" → NEUTRAL

    Ahora clasifica:
    Frase: "El diseño es bonito pero la batería no dura nada"
    """

    respuesta = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[{"role": "user", "content": prompt_few_shot}]
    )
    print(respuesta.choices[0].message.content)
NEGATIVO

¿Por qué funciona? Los LLMs son excelentes reconociendo patrones. Al darles 2-3 ejemplos, el modelo “aprende” el patrón en contexto (in-context learning) sin necesidad de fine-tuning.

TipRegla de oro del few-shot
  • 2-3 ejemplos suelen bastar
  • Los ejemplos deben cubrir los casos extremos (edge cases)
  • Mantén consistencia exacta en el formato de los ejemplos

Chain-of-Thought (CoT)

El Chain-of-Thought consiste en pedir al modelo que razone paso a paso antes de dar la respuesta final. La clave está en añadir algo como “pensemos paso a paso” o incluir ejemplos donde se muestra el razonamiento.

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    problema = """
    Un tren sale de Madrid a las 08:00 hacia Barcelona (620 km) a 120 km/h.
    Otro tren sale de Barcelona a las 09:00 hacia Madrid a 150 km/h.
    ¿A qué hora se cruzan?
    """

    prompt_cot = f"""
    {problema}

    Resuelve paso a paso:
    1. Calcula cuánto ha avanzado el primer tren cuando sale el segundo
    2. Calcula la distancia restante entre ambos en ese momento
    3. Calcula el tiempo hasta que se cruzan
    4. Suma el tiempo a la hora de salida
    """

    respuesta_cot = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[{"role": "user", "content": prompt_cot}]
    )
    print(respuesta_cot.choices[0].message.content)
Este es un problema de movimiento relativo. Utilizaremos las indicaciones paso a paso que se solicitan para resolverlo.

**Datos iniciales:**
*   Distancia total: $620 \text{ km}$
*   Tren 1 (Madrid $\rightarrow$ Barcelona): Sale a las 08:00, velocidad $V_1 = 120 \text{ km/h}$.
*   Tren 2 (Barcelona $\rightarrow$ Madrid): Sale a las 09:00, velocidad $V_2 = 150 \text{ km/h}$.

---

### 1. Calcula cuánto ha avanzado el primer tren cuando sale el segundo (a las 09:00).

El primer tren sale a las 08:00 y el segundo a las 09:00, por lo tanto, el primer tren ha viajado durante 1 hora.

Distancia recorrida por el Tren 1 = Velocidad $\times$ Tiempo
$$D_1 = 120 \text{ km/h} \times 1 \text{ h} = 120 \text{ km}$$

**Al momento en que sale el segundo tren (a las 09:00), el Tren 1 está a $120 \text{ km}$ de Barcelona.**

---

### 2. Calcula la distancia restante entre ambos en ese momento (a las 09:00).

La distancia total es $620 \text{ km}$.
Distancia restante = Distancia total - Distancia recorrida por el Tren 1
$$D_{\text{restante}} = 620 \text{ km} - 120 \text{ km} = 500 \text{ km}$$

**A las 09:00, la distancia que deben recorrer juntos es de $500 \text{ km}$.**

Para calcular el tiempo de encuentro, usamos la velocidad relativa (sumando sus velocidades ya que se mueven uno hacia el otro).
Velocidad relativa ($V_{\text{relativa}}$) = $120 \text{ km/h} + 150 \text{ km/h} = 270 \text{ km/h}$.

---

### 3. Calcula el tiempo hasta que se cruzan (a partir de las 09:00).

Tiempo ($T$) = Distancia restante / Velocidad relativa
$$T = \frac{500 \text{ km}}{270 \text{ km/h}} = \frac{50}{27} \text{ horas}$$

Para convertir $\frac{50}{27}$ horas a minutos y segundos:
$$\frac{50}{27} \times 60 \text{ minutos} = \frac{3000}{27} \text{ minutos} = \frac{1000}{9} \text{ minutos} \approx 111.11 \text{ minutos}$$

Convertimos $111$ minutos:
$$111 \text{ minutos} = 1 \text{ hora } 51 \text{ minutos}$$

El tiempo es **1 hora, 51 minutos y $\frac{1}{9}$ minuto** (o aproximadamente 1 hora, 51 minutos).

---

### 4. Suma el tiempo a la hora de salida.

El cálculo del tiempo se realiza a partir de las 09:00.

Hora de encuentro = Hora de salida + Tiempo transcurrido
$$09:00 \text{h} + 1 \text{ hora } 51 \frac{1}{9} \text{ minutos}$$
$$= 10:51 \frac{1}{9} \text{ (o } 10 \text{ horas, } 51 \text{ minutos y } 6.67 \text{ segundos)}$$

---

### Respuesta final:

Los trenes se cruzan a las **10:51** (aproximadamente).

¿Por qué funciona? Al obligar al modelo a generar tokens intermedios de razonamiento, cada paso condiciona el siguiente. Es como si el modelo “pensara en voz alta”, reduciendo drásticamente los errores en tareas matemáticas y lógicas.

Tree-of-Thought (ToT)

El Tree-of-Thought extiende CoT: en lugar de un único camino de razonamiento, el modelo explora múltiples ramas y elige la mejor. Es útil para problemas con múltiples soluciones posibles (planificación, puzzles, creatividad).

## 💡 3 Enfoques Distintos para Team Building (Data Science)

### Enfoque 1: El Desafío Analítico (Analytical Challenge)
**Foco:** Resolución de problemas complejos, pensamiento lógico y toma de decisiones basada en datos.
Este enfoque aprovecha la mentalidad del equipo de Data Science, poniendo a prueba su capacidad para analizar información ambigua y llegar a conclusiones.

| Aspecto | Descripción |
| :--- | :--- |
| **Actividad Principal** | Un caso de estudio (un "problema real" o simulado) que el equipo debe desglosar en fases: 1. Definir la pregunta. 2. Recopilar datos/hipótesis. 3. Proponer soluciones y priorizar (simulando un *MVP*). |
| **Pros** | Alta relevancia para el equipo técnico, fomenta el pensamiento estructurado, resultados claros y medibles, fortalece la comunicación de ideas técnicas. |
| **Contras** | Puede ser percibido como demasiado serio o tedioso si no se gestiona bien, requiere una preparación exhaustiva del caso. Puede generar frustración si el tiempo es muy limitado. |
| **Coste/Logística** | Bajo (solo materiales y tiempo). Logística sencilla: solo necesita un espacio de trabajo cómodo y pizarras/post-its. |

### Enfoque 2: El Hackathon de Ideas (Idea Hackathon)
**Foco:** Creatividad, ideación rápida, pensamiento fuera de la caja y presentación de propuestas.
Este enfoque se centra en la fase inicial del proceso: generar muchas ideas y construir un consenso.

| Aspecto | Descripción |
| :--- | :--- |
| **Actividad Principal** | Dividir al equipo en subgrupos pequeños. Cada grupo recibe un tema (ej: "Cómo mejorar la experiencia del usuario X") y tiene 90 minutos para idear, diseñar una solución o un producto, y 30 minutos para presentar su propuesta. |
| **Pros** | Alto engagement, fomenta el trabajo en equipo diverso, rompe barreras jerárquicas (todos tienen voz), estimula la innovación. Ideal para sesiones dinámicas. |
| **Contras** | Riesgo de que la sesión se desvíe demasiado de los objetivos. Requiere una excelente facilitación para mantener el enfoque y evitar que las ideas sean demasiado abstractas. Puede ser menos "técnico". |
| **Coste/Logística** | Medio (materiales: tarjetas, marcadores, cronómetros). Logística moderada: se necesita un espacio para grupos pequeños. |

### Enfoque 3: El Juego de Roles y Estrategia (Role-Playing & Strategy Game)
**Foco:** Comunicación bajo presión, gestión emocional y estrategia colaborativa.
Este enfoque simula situaciones complejas en entornos de negocios o crisis, enfocándose en el *cómo* interactuar más que en el *qué*.

| Aspecto | Descripción |
| :--- | :--- |
| **Actividad Principal** | Juegos simulados donde cada miembro del equipo representa un rol específico (ej: Stakeholder, Cliente, Desarrollador, Analista). Deben negociar recursos o resolver un conflicto siguiendo reglas específicas. |
| **Pros** | Excelente para mejorar la inteligencia emocional del equipo, fortalece las habilidades de negociación y manejo de conflictos. Alto engagement interpersonal. |
| **Contras** | Puede ser incómodo si el equipo no está acostumbrado a la dinámica; si se gestiona mal, puede llevar a discusiones personales en lugar de la estrategia. Requiere una excelente gestión del facilitador. |
| **Coste/Logística** | Bajo (solo material para roles y escenarios). Logística simple: ideal para un espacio con buena interacción cara a cara. |

---

## 🏆 Selección y Justificación

**Opción Elegida:** **Enfoque 1: El Desafío Analítico (Analytical Challenge)**

### Justificación
Para un equipo de Data Science, la actividad debe resonar con su identidad profesional. El Enfoque 1 es el más adecuado porque obliga al equipo a utilizar sus habilidades naturales (análisis, lógica, modelado) en un entorno lúdico. No solo se trata de "trabajar juntos", sino de **"trabajar inteligentemente juntos"**.

*   **Relevancia:** Conecta directamente las dinámicas del trabajo diario (definir problemas, analizar datos, proponer soluciones).
*   **Estructura:** El formato estructurado (Fase 1: Definición, Fase 2: Análisis, Fase 3: Decisión) garantiza que el tiempo de 4 horas se utilice de manera productiva y lógica.
*   **Resultado:** Genera un alto valor de aprendizaje práctico sobre cómo la presión afecta la toma de decisiones en un entorno real (ej. desarrollo de producto, implementación de modelos).

---

## 🎯 Plan Detallado: El Desafío Analítico (4 Horas)

**Tema Central:** "Diseñando el Futuro: Estrategia para una Plataforma X"
**(Asume que la plataforma X es un proyecto hipotético relevante para su área.)**

### Objetivo de la Jornada
Que el equipo aplique metodologías analíticas para definir, priorizar y proponer la estrategia para resolver un problema complejo simulado en 4 horas.

### Recursos Necesarios
1. Pizarra o rotafolio/flipchart.
2 Post-its (varios colores).
3 Cronómetro visible.
4 Material impreso con el "Caso de Estudio" (el problema).
5 Hojas de trabajo para cada subgrupo.

### Estructura de la Jornada (4 Horas)

#### Fase 1: Introducción y Contextualización (30 min)

*   **Bienvenida (10 min):** Presentación del objetivo: No es un juego, es una simulación profesional.
*   **Reglas (10 min):** Explicar la dinámica de grupo, el rol del facilitador y el concepto de "aprender juntos".
*   **Presentación del Caso (10 min):** Mostrarles el escenario simulado: El problema que deben resolver (ejemplo: "La plataforma X tiene una tasa de abandono baja. ¿Cómo la solucionamos?").

#### Fase 2: Desglose y Análisis (90 min) - La Base de la Ciencia (Focus en Logística y Proceso)

*   **División de Grupos (5 min):** Dividir el equipo de 20 personas en 4 subgrupos de 5 personas cada uno.
*   **Análisis Inicial (30 min):** Cada grupo recibe un set de Post-its. Deben enfocarse en:
    1.  Identificar los síntomas/puntos de dolor (Pain Points).
    2.  Proponer hipótesis sobre la causa raíz del problema.
*   **Construcción de la Solución (60 min):** Utilizando el análisis anterior, el grupo debe diseñar 3 posibles caminos a seguir para mitigar el problema, justificando cada camino con lógica (usar su mentalidad de DS: ¿Qué datos necesitaríamos? ¿Cuál es el riesgo?).

* **Role del Facilitador:** Circular por los grupos. Preguntar: "¿Cómo llegaste a esa conclusión?", "¿Podrías respaldar esto con un dato?".

#### Fase 3: Presentación y Decisión (60 min) - La Conclusión (Focus en Comunicación)

*   **Pitch (30 min):** Cada grupo presenta su mejor solución o propuesta de estrategia en 5-7 minutos. Deben enfocarse en: El Problema, la Hipótesis principal y el Plan de Acción.
    * *Recomendación:* Al final de cada pitch, se abre un breve espacio para preguntas cruzadas entre grupos.
*   **Debate Final (30 min):** El equipo completo vota o debate las 3 soluciones propuestas. Se discute: ¿Cuál es la solución más viable y por qué?

#### Fase 4: Debriefing y Cierre (120 min) - Aprendizaje (Focus en Team Building)

*   **Reflexión Estructurada (60 min):** Esta es la parte crucial para el team building.
    * **Preguntas Clave:**
        * ¿Qué aprendimos sobre nuestra forma de trabajar en equipo?
        * ¿Cómo la presión afectó nuestra comunicación?
        * ¿Qué habilidad técnica/no técnica usamos mejor en este desafío?
        * ¿Cómo podemos aplicar esta metodología analítica a nuestros proyectos reales?
    * *El facilitador debe guiar la conversación para que las conclusiones se traduzcan en acciones concretas.*
*   **Cierre (60 min):** Agradecimiento y compromiso final.

### Resumen de Tiempos

| Fase | Duración | Enfoque principal | Resultado esperado |
| :--- | :--- | :--- | :--- |
| 1. Introducción | 30 min | Contextualización | Todos comprenden el objetivo. |
| 2. Análisis | 90 min | Lógica y Pensamiento Crítico | Soluciones estructuradas. |
| 3. Presentación | 60 min | Comunicación y Pitch | Visión clara de las alternativas. |
| 4. Debriefing | 120 min | Team Building y Reflexión | Compromisos para el futuro del equipo. |
| **TOTAL** | **4 horas (240 min)** | | |
Note

ToT requiere más tokens (y por tanto más coste) que CoT simple, ya que se generan y evalúan múltiples ramas. En la práctica, se implementa con múltiples llamadas al LLM o agentes que evalúan cada rama.

Output Structuring con JSON Schema

Forzar que el modelo devuelva JSON nos permite integrar el LLM en pipelines automatizados. La API de OpenAI ofrece el parámetro response_format para garantizar JSON válido:

else:

    Se acordó migrar el pipeline ETL a Spark antes del Q2.
    Presupuesto estimado: 45.000€. Carlos se encarga de la POC.
    """

    system_prompt = f"""Eres un extractor de datos de actas de reunión.
Devuelve ÚNICAMENTE un JSON válido con esta estructura exacta, sin texto adicional:
{{
  "fecha": "string (formato YYYY-MM-DD)",
  "asistentes": ["lista de nombres"],
  "decisiones": ["lista de decisiones tomadas"],
  "presupuesto_euros": 0.0,
  "responsables": [{{"nombre": "string", "tarea": "string"}}]

    respuesta = client.chat.completions.create(

ImportantJSON vía prompt vs. structured output nativo

Pedir JSON en el prompt funciona con cualquier modelo, pero no garantiza que el JSON sea válido (por eso añadimos try/except). Algunos modelos como Qwen 3 ofrecen response_format nativo que fuerza la estructura desde el API. La ventaja del prompting es que es model-agnostic: funciona con Gemma, Llama, Mistral, etc.

De JSON Schema a datos sintéticos: el enfoque intuitivo

Lo que acabas de hacer —extraer 1 registro JSON de un texto— es el mismo mecanismo que permite generar datasets sintéticos completos. La diferencia es de escala: en lugar de pedir 1 registro, pides N. En lugar de extraer de un texto real, pides al modelo que invente datos verosímiles.

La receta es simple:

  1. Define el schema de tus datos (igual que en la sección anterior)
  2. Añade few-shot examples para que el modelo entienda el dominio y los rangos esperados
  3. Controla la diversidad con temperatura: baja produce datos conservadores, alta inyecta variedad
  4. Itera en batch para generar cientos o miles de registros

Esta es una excelente pregunta, ya que toca un punto fundamental en el análisis estadístico: la elección de la medida de tendencia central adecuada para diferentes tipos de datos.

La opinión sobre usar la mediana frente a los valores atípicos (outliers) no es binaria (sí o no), sino contextual. **En general, la mediana es una herramienta muy robusta contra los outliers, pero no es la solución universal.**

A continuación, te presento un análisis detallado de las ventajas, desventajas y cuándo debes priorizarla.

---

## 1. ¿Qué es la Mediana y por qué es útil para Outliers?

La mediana es el valor central de un conjunto de datos ordenados. A diferencia de la media (promedio), **no se ve afectada por los valores extremos**. Si tienes un conjunto de 10 números, la mediana es el número que está justo en medio (el quinto valor). Un valor extremadamente alto o bajo no cambia su posición relativa, solo afecta la distribución general del conjunto.

### 👍 Ventajas de usar la Mediana con Outliers:

1. **Robustez (Resistencia):** Esta es su principal fortaleza. Si tu conjunto de datos contiene valores extremos que podrían sesgar el promedio, la mediana te dará una representación más fiel del "centro" típico de tus datos.
2. **No Sensibilidad a Valores Extremos:** En distribuciones sesgadas (skewed distributions), donde hay muchos valores muy grandes o muy pequeños, la media será engañada. La mediana ignora estos extremos y se centra en la mitad de los datos.
3. **Representación del "Típico":** Si tu objetivo es entender cuál es el valor central o típico de tu población (por ejemplo, el salario medio, el tiempo promedio de respuesta), la mediana ofrece una imagen más equilibrada que el promedio.

## 2. ¿Cuándo NO es suficiente usar solo la Mediana?

Aunque la mediana es robusta, tiene limitaciones importantes que debes considerar:

### 👎 Desventajas de la Mediana (Limitaciones):

1. **Pérdida de Información:** Al ser solo un valor posicional, la mediana ignora toda la información sobre la magnitud de los datos. Si tienes una distribución perfectamente simétrica y quieres conocer el promedio real, la mediana podría no ser útil.
2. **No Maneja Bien las Relaciones:** La mediana te dice "qué valor es el medio", pero no te dice nada sobre la dispersión o la forma de la distribución (¿está sesgada?, ¿son normales?).
3. **Cuando los Outliers son Error:** Si un outlier es causado por un error de medición, y no por una fenómeno real, usar la mediana puede "suavizar" el problema, ocultando la necesidad de investigar esos datos atípicos.

## 3. Conclusión: La Estrategia Recomendada

La mejor práctica en el análisis de datos es **no confiar en una única medida**. Debes usar un enfoque combinado:

| Situación | ¿Qué Medida Usar? | Por qué |
| :--- | :--- | :--- |
| **Datos con Outliers Claros y Sesgados** (Salarios, Ingresos) | **Mediana** | Para obtener la medida de tendencia central que no se vea distorsionada por los valores extremos. |
| **Datos Simétricos o Normales** (Distribución en campanas) | **Media (Promedio)** | La media es más eficiente y refleja mejor el valor central si la distribución es equilibrada. |
| **Necesidad de Visualización** | **Histogramas / Diagramas de Caja (Box Plots)** | Siempre usa estas herramientas para *identificar* los outliers antes de decidir qué medida usar. |
| **Análisis de Dispersión** | **Desviación Estándar** | La mediana te dice el centro, la desviación estándar te dice qué tan dispersos están los datos alrededor de ese centro. |

### Resumen final:

**Sí, es muy recomendable usar la mediana cuando esperas o tienes evidencia de que tus datos contienen valores extremos (outliers) que podrían distorsionar al promedio.**

Sin embargo, no debe ser el *único* criterio. Debes siempre examinar la forma de tu distribución y considerar otras medidas para obtener una imagen completa y robusta de tus datos.

La pregunta original es: ¿Es 17 un número primo de Mersenne?

A continuación, se presenta el análisis solicitado para responder la pregunta.

---

### 1. ¿Qué es un número primo de Mersenne? (Definición general)

Un **Número Primo de Mersenne** ($M_p$) es un número primo que también puede expresarse en la forma $2^p - 1$, donde $p$ es otro número primo.

Formalmente, el proceso es el siguiente:
1. Se toma un número primo $p$.
2. Se calcula el Número de Mersenne: $M_p = 2^p - 1$.
3. Se comprueba si el resultado $M_p$ es también un número primo.

*Ejemplos:*
Si $p=2$, $M_2 = 2^2 - 1 = 3$. (3 es primo, por lo tanto, 3 es un Número Primo de Mersenne).
Si $p=3$, $M_3 = 2^3 - 1 = 7$. (7 es primo, por lo tanto, 7 es un Número Primo de Mersenne).
Si $p=5$, $M_5 = 2^5 - 1 = 31$. (31 es primo, por lo tanto, 31 es un Número Primo de Mersenne).

---

### 2. ¿Cómo se comprueba si un número es primo de Mersenne? (Método)

Para determinar si un número $N$ es un Número Primo de Mersenne, se sigue el método de dos pasos:

**Paso A: Identificar si N es un Número de Mersenne.**
Se verifica si existe un número primo $p$ tal que $N = 2^p - 1$. (Es decir, se comprueba si $N + 1$ es una potencia de 2).

*Método de comprobación:*
1. Calcula $N + 1$.
2. Verifica si el número $N + 1$ es una potencia de 2 ($2^p$). Esto se hace dividiendo $N+1$ por 2 repetidamente hasta que no sea divisible, o usando logaritmos para verificar la base (es decir, $N+1$ debe ser una potencia de 2).
3. Si $N+1 = 2^p$, y si $p$ es un número primo, entonces $N$ es un Número de Mersenne.

**Paso B: Comprobar si el resultado es Primo.**
Si se cumple el Paso A, se comprueba que el número $N$ resultante es un número primo (usando la prueba de divisibilidad).

---

### 3. Ahora aplica el método a 17 y concluye.

Aplicaremos el método a $N = 17$.

#### Paso A: ¿Es 17 un Número de Mersenne?
Comprobamos si $17 + 1$ es una potencia de 2.

$$17 + 1 = 18$$

Verificamos si 18 es una potencia de 2.
Las potencias de 2 son: $2^1=2$, $2^2=4$, $2^3=8$, $2^4=16$, $2^5=32$.

Como 18 no es una potencia entera de 2, **17 NO es un Número de Mersenne.**

(Alternativamente, si hubiéramos buscado el exponente $p$: Si $2^p = 18$, entonces $p$ no existe como entero, por lo tanto, 17 no cumple la condición para ser un número de Mersenne).

#### Paso B: Comprobar si el resultado es Primo.
Dado que 17 no satisface la condición para ser un Número de Mersenne (Paso A), este paso se omite. Sin embargo, notamos que 17 *sí* es un número primo.

### Conclusión

**No**, 17 **no** es un Número Primo de Mersenne.

Aunque 17 es un número primo, no cumple la condición necesaria para ser considerado un Número de Mersenne ($2^p - 1$).

## Prompt Engineering Avanzado {#sec-prompt-engineering}

### ¿Qué es un prompt? {#sec-que-es-prompt}

Un **prompt** es la instrucción textual que le damos a un LLM. Piensa en ello como la pregunta o la orden que le das a un asistente muy capaz pero muy literal: si la instrucción es ambigua, la respuesta será imprecisa. Si es clara y con contexto, la respuesta será mucho mejor.

El Prompt Engineering consiste en diseñar estas instrucciones de forma sistemática para obtener respuestas fiables, estructuradas y útiles, no solo "texto bonito".

El **few-shot** consiste en incluir ejemplos dentro del prompt para que el modelo entienda exactamente qué formato y estilo esperamos. Es como enseñarle con el ejemplo.

- 2-3 ejemplos suelen bastar
- Los ejemplos deben cubrir los casos extremos (edge cases)
- Mantén consistencia exacta en el formato de los ejemplos

### Zero-shot vs Few-shot vs One-shot {#sec-zero-one-few-shot}

: Comparativa de estrategias de prompting por número de ejemplos {#tbl-prompt-estrategias}

| Estrategia | Ejemplos en el prompt | Cuándo usarlo |
|---|---|---|
| **Zero-shot** | 0 — solo la instrucción | Tareas sencillas, modelos muy capaces |
| **One-shot** | 1 ejemplo | Cuando necesitas mostrar el formato exacto |
| **Few-shot** | 2-5 ejemplos | Tareas complejas, formatos muy específicos |

```python
    # ZERO-SHOT: sin ejemplos
    respuesta_zero = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[{"role": "user", "content": "Traduce al inglés: 'El gato está en el tejado'"}]
    )

    # ONE-SHOT: un ejemplo
    respuesta_one = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[{"role": "user", "content": """
    Traduce español → inglés.
    Ejemplo: "Hola mundo" → "Hello world"
    Ahora traduce: "El gato está en el tejado"
    """}]
    )

    print("Zero-shot:", respuesta_zero.choices[0].message.content)
    print("One-shot:", respuesta_one.choices[0].message.content)
```

### Chain-of-Thought (CoT) {#sec-cot}

El **Chain-of-Thought** consiste en pedir al modelo que razone paso a paso antes de dar la respuesta final. La clave está en añadir algo como _"pensemos paso a paso"_ o incluir ejemplos donde se muestra el razonamiento.

quarto-executable-code-5450563D

```python
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    problema = """
    Un tren sale de Madrid a las 08:00 hacia Barcelona (620 km) a 120 km/h.
    Otro tren sale de Barcelona a las 09:00 hacia Madrid a 150 km/h.
    ¿A qué hora se cruzan?
    """

    prompt_cot = f"""
    {problema}

    Resuelve paso a paso:
    1. Calcula cuánto ha avanzado el primer tren cuando sale el segundo
    2. Calcula la distancia restante entre ambos en ese momento
    3. Calcula el tiempo hasta que se cruzan
    4. Suma el tiempo a la hora de salida
    """

    respuesta_cot = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[{"role": "user", "content": prompt_cot}]
    )
    print(respuesta_cot.choices[0].message.content)
```


**¿Por qué funciona?** Al obligar al modelo a generar tokens intermedios de razonamiento, cada paso condiciona el siguiente. Es como si el modelo "pensara en voz alta", reduciendo drásticamente los errores en tareas matemáticas y lógicas.

### Tree-of-Thought (ToT) {#sec-tot}

El **Tree-of-Thought** extiende CoT: en lugar de un único camino de razonamiento, el modelo explora múltiples ramas y elige la mejor. Es útil para problemas con múltiples soluciones posibles (planificación, puzzles, creatividad).

### Output Structuring con JSON Schema {#sec-output-structuring}

Forzar que el modelo devuelva JSON nos permite integrar el LLM en pipelines automatizados. La API de OpenAI ofrece el parámetro `response_format` para garantizar JSON válido:

quarto-executable-code-5450563D

```python
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    texto_a_analizar = """
    Reunión del 15/03/2026. Asistentes: Ana (Data), Carlos (ML), Bea (Product).
    Se acordó migrar el pipeline ETL a Spark antes del Q2.
    Presupuesto estimado: 45.000€. Carlos se encarga de la POC.
    """

    system_prompt = f"""Eres un extractor de datos de actas de reunión.
Devuelve ÚNICAMENTE un JSON válido con esta estructura exacta, sin texto adicional:
{{
  "fecha": "string (formato YYYY-MM-DD)",
  "asistentes": ["lista de nombres"],
  "decisiones": ["lista de decisiones tomadas"],
  "presupuesto_euros": 0.0,
  "responsables": [{{"nombre": "string", "tarea": "string"}}]
}}"""

    respuesta = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": texto_a_analizar}
        ],
    )

    try:
        resultado = parse_json_response(respuesta.choices[0].message.content)
        print(json.dumps(resultado, indent=2, ensure_ascii=False))
    except json.JSONDecodeError:
        print("⚠️ El modelo no devolvió JSON válido. Intenta de nuevo o usa un modelo con soporte nativo de structured output.")
        print(respuesta.choices[0].message.content[:200])
```

::: {.callout-important}
## JSON vía prompt vs. structured output nativo

Pedir JSON en el prompt funciona con **cualquier modelo**, pero **no garantiza** que el JSON sea válido (por eso añadimos `try/except`). Algunos modelos como Qwen 3 ofrecen `response_format` nativo que fuerza la estructura desde el API. La ventaja del prompting es que es **model-agnostic**: funciona con Gemma, Llama, Mistral, etc.
:::

### De JSON Schema a datos sintéticos: el enfoque intuitivo {#sec-json-schema-datos-sint}

Lo que acabas de hacer —extraer 1 registro JSON de un texto— es el mismo mecanismo que permite **generar datasets sintéticos completos**. La diferencia es de escala: en lugar de pedir 1 registro, pides N. En lugar de extraer de un texto real, pides al modelo que *invente* datos verosímiles.

La receta es simple:

1. **Define el schema** de tus datos (igual que en la sección anterior)
2. **Añade few-shot examples** para que el modelo entienda el dominio y los rangos esperados
3. **Controla la diversidad** con temperatura: baja produce datos conservadores, alta inyecta variedad
4. **Itera en batch** para generar cientos o miles de registros

quarto-executable-code-5450563D

```python
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    import pandas as pd

    system_prompt = """Eres un generador de datos sintéticos de clientes españoles.
Devuelve ÚNICAMENTE un JSON válido con esta estructura exacta, sin texto adicional:
{
  "clientes": [
    {
      "id": 1,
      "edad": 34,
      "ingresos_anuales": 42000.0,
      "provincia": "Madrid",
      "segmento": "premium"
    }
  ]
}
Reglas:
- Edad entre 18 y 80 años
- Ingresos entre 12000 y 120000, correlacionados con la edad
- Provincias: Madrid, Barcelona, Valencia, Sevilla, Bilbao, Málaga, Zaragoza
- Segmentos: premium, estandar, basic
- Genera variedad realista"""

    respuesta = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        temperature=0.8,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": "Genera 10 clientes sintéticos. Usa variedad realista en edades, ingresos y provincias."}
        ],
    )

    try:
        datos = parse_json_response(respuesta.choices[0].message.content)
        df = pd.DataFrame(datos["clientes"])
        print(df.to_string(index=False))
        print(f"\n{len(df)} registros generados")
        print(f"   Edad: {df['edad'].min()}-{df['edad'].max()} (media {df['edad'].mean():.0f})")
        print(f"   Ingresos: {df['ingresos_anuales'].min():.0f}-{df['ingresos_anuales'].max():.0f} (media {df['ingresos_anuales'].mean():.0f})")
    except (json.JSONDecodeError, KeyError) as e:
        print(f"⚠️ Error al parsear respuesta: {e}")
        print(respuesta.choices[0].message.content[:200])
```

::: {.callout-tip}
## ¿Por qué funciona?

El LLM no "conoce" clientes reales, pero ha visto millones de patrones en sus datos de entrenamiento: distribuciones de edad, rangos de ingresos típicos, provincias españolas. El **prompt con el schema**, el **few-shot** y la **temperatura** controlan estructura, dominio y diversidad. Algunos modelos (Qwen, OpenAI) ofrecen además `response_format` nativo para forzar la estructura desde el API.

**Este es el enfoque más intuitivo y accesible para datos sintéticos:**
- Sin entrenar modelos adicionales
- Sin GPU
- En menos de 20 líneas de código
- Funciona con cualquier modelo (Gemma, Qwen, Llama, etc.)
- Ideal para prototipado, testing y aumento rápido de datasets pequeños
:::

::: {.callout-warning}
## Limitaciones del enfoque intuitivo

- No garantiza **correlaciones realistas** entre columnas (ej. ingresos vs. edad pueden no seguir la relación esperada)
- Puede generar **valores atípicos** no representativos
- Depende de la **calidad del prompt** y los ejemplos
- **No hay garantía de privacidad** diferencial

Para datasets de producción donde la fidelidad estadística es crítica, necesitarás modelos generativos especializados (CTGAN, TVAE, TabDDPM) que veremos en el **Bloque 3** con SDV.
:::

### Role Prompting {#sec-role-prompting}

Asignar un **rol** al modelo en el mensaje `system` cambia radicalmente su comportamiento. No es magia: el modelo, entrenado con textos de diversos perfiles, "activa" los patrones asociados a ese rol.

### Técnicas adicionales {#sec-tecnicas-adicionales}

: Técnicas avanzadas de prompting y cuándo aplicarlas {#tbl-prompt-tecnicas}

| Técnica | Descripción | Cuándo usarla |
|---|---|---|
| **Self-consistency** | Ejecutar CoT varias veces y votar la respuesta mayoritaria | Razonamiento matemático/lógico |
| **Generated knowledge** | Pedir al modelo que genere contexto antes de responder | Preguntas que requieren conocimiento factual |
| **Re-reading (RE2)** | Hacer que el modelo lea la pregunta dos veces | Mejora comprensión en tareas largas |
| **Emotion prompting** | Añadir estímulos emocionales al prompt | Tareas creativas o subjetivas |
| **Step-back prompting** | Preguntar primero por principios generales | Problemas muy específicos |

```python
#| echo: true
```

### Buenas prácticas resumen {#sec-buenas-practicas-prompt}

1. **Sé específico**: "analiza los datos" → malo. "calcula media, mediana y desviación típica de la columna 'ventas' agrupada por 'región'" → bueno
2. **Muestra, no solo digas**: incluye ejemplos del formato que esperas (few-shot)
3. **Divide y vencerás**: tareas complejas → CoT, desglosa en pasos
4. **Formato forzado**: usa `response_format` / JSON Schema cuando integres con código
5. **Itera**: el primer prompt casi nunca es el óptimo. Prueba, compara, mejora
6. **System prompt**: define el tono, rol y restricciones al inicio
