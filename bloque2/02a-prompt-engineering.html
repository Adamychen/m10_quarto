Prompt Engineering Avanzado

¿Qué es un prompt?

Un prompt es la instrucción textual que le damos a un LLM. Piensa en ello como la pregunta o la orden que le das a un asistente muy capaz pero muy literal: si la instrucción es ambigua, la respuesta será imprecisa. Si es clara y con contexto, la respuesta será mucho mejor.

El Prompt Engineering consiste en diseñar estas instrucciones de forma sistemática para obtener respuestas fiables, estructuradas y útiles, no solo “texto bonito”.

Primer contacto: llamada a un LLM

Antes de profundizar, veamos cómo invocar un LLM desde Python con la API de OpenAI (compatible con Llamus US, Ollama local, etc.):

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    respuesta = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[{"role": "user", "content": "Explica qué es la desviación estándar en una frase."}]
    )
    print(respuesta.choices[0].message.content)
La desviación estándar es una medida que indica cuánto se dispersan o varían los datos respecto a su promedio.

Este es el patrón base para todo lo que veremos: model + messages → respuesta. Los messages pueden tener varios roles:

Rol Propósito Ejemplo
system Instrucción global de comportamiento “Eres un analista de datos experto”
user Pregunta o instrucción del usuario “Analiza este CSV…”
assistant Respuestas previas del modelo (historial) “La media es 42.3…”

Few-shot prompting

El few-shot consiste en incluir ejemplos dentro del prompt para que el modelo entienda exactamente qué formato y estilo esperamos. Es como enseñarle con el ejemplo.

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    prompt_few_shot = """
    Clasifica el sentimiento de cada frase como POSITIVO, NEGATIVO o NEUTRAL.

    Ejemplos:
    Frase: "El producto llegó roto y la atención fue pésima" → NEGATIVO
    Frase: "Todo perfecto, entrega rápida y bien embalado" → POSITIVO
    Frase: "El paquete llegó ayer por la tarde" → NEUTRAL

    Ahora clasifica:
    Frase: "El diseño es bonito pero la batería no dura nada"
    """

    respuesta = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[{"role": "user", "content": prompt_few_shot}]
    )
    print(respuesta.choices[0].message.content)
NEGATIVO

¿Por qué funciona? Los LLMs son excelentes reconociendo patrones. Al darles 2-3 ejemplos, el modelo “aprende” el patrón en contexto (in-context learning) sin necesidad de fine-tuning.

TipRegla de oro del few-shot
  • 2-3 ejemplos suelen bastar
  • Los ejemplos deben cubrir los casos extremos (edge cases)
  • Mantén consistencia exacta en el formato de los ejemplos

Zero-shot vs Few-shot vs One-shot

Estrategia Ejemplos en el prompt Cuándo usarlo
Zero-shot 0 — solo la instrucción Tareas sencillas, modelos muy capaces
One-shot 1 ejemplo Cuando necesitas mostrar el formato exacto
Few-shot 2-5 ejemplos Tareas complejas, formatos muy específicos

Chain-of-Thought (CoT)

El Chain-of-Thought consiste en pedir al modelo que razone paso a paso antes de dar la respuesta final. La clave está en añadir algo como “pensemos paso a paso” o incluir ejemplos donde se muestra el razonamiento.

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    problema = """
    Un tren sale de Madrid a las 08:00 hacia Barcelona (620 km) a 120 km/h.
    Otro tren sale de Barcelona a las 09:00 hacia Madrid a 150 km/h.
    ¿A qué hora se cruzan?
    """

    prompt_cot = f"""
    {problema}

    Resuelve paso a paso:
    1. Calcula cuánto ha avanzado el primer tren cuando sale el segundo
    2. Calcula la distancia restante entre ambos en ese momento
    3. Calcula el tiempo hasta que se cruzan
    4. Suma el tiempo a la hora de salida
    """

    respuesta_cot = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[{"role": "user", "content": prompt_cot}]
    )
    print(respuesta_cot.choices[0].message.content)
Este es un problema de movimiento relativo. Para resolverlo, seguiremos los pasos propuestos para determinar la hora exacta en que se cruzan los trenes.

**Datos iniciales:**
* **Tren Madrid $\to$ Barcelona (Tren 1):** Sale a las 08:00. Velocidad = $120 \text{ km/h}$.
* **Tren Barcelona $\to$ Madrid (Tren 2):** Sale a las 09:00. Velocidad = $150 \text{ km/h}$.
* **Distancia total:** $620 \text{ km}$.

---

### 1. Calcula cuánto ha avanzado el primer tren cuando sale el segundo (al momento en que sale el Tren 2)

El Tren 1 sale a las 08:00 y el Tren 2 sale a las 09:00. Esto significa que el Tren 1 viaja durante 1 hora.

* **Tiempo de viaje del Tren 1:** $1 \text{ hora}$
* **Distancia recorrida por el Tren 1:** $120 \text{ km/h} \times 1 \text{ h} = 120 \text{ km}$.

**Respuesta Paso 1:** Cuando sale el segundo tren (a las 09:00), el primer tren ya ha avanzado $120 \text{ km}$.

---

### 2. Calcula la distancia restante entre ambos en ese momento

La distancia total es $620 \text{ km}$. Ya han recorrido $120 \text{ km}$.

* **Distancia restante:** $620 \text{ km} - 120 \text{ km} = 500 \text{ km}$.

**Respuesta Paso 2:** A las 09:00, la distancia restante entre ambos trenes es de $500 \text{ km}$.

---

### 3. Calcula el tiempo hasta que se cruzan (a partir de las 09:00)

A partir de las 09:00, ambos trenes están en movimiento simultáneo y deben cubrir la distancia restante ($500 \text{ km}$) al unirse. Usaremos la velocidad relativa (la suma de sus velocidades).

* **Velocidad Relativa:** $120 \text{ km/h} + 150 \text{ km/h} = 270 \text{ km/h}$.
* **Tiempo para cruzarse ($T$):** $\frac{\text{Distancia restante}}{\text{Velocidad relativa}} = \frac{500 \text{ km}}{270 \text{ km/h}}$

$$T = \frac{500}{270} = \frac{50}{27} \text{ horas}$$

Para convertir este tiempo a minutos y segundos:
$$\frac{50}{27} \times 60 \text{ minutos} = \frac{3000}{27} \text{ minutos} = \frac{1000}{9} \text{ minutos}$$
$$1000 \div 9 = 111 \text{ con un resto de } 1.$$
Esto significa que el tiempo es $111$ minutos y $\frac{1}{9}$ minuto.

* **Conversión:** $111$ minutos $= 1$ hora y $51$ minutos.
* El resto es $\frac{1}{9}$ de un minuto. $(\frac{1}{9} \times 60 \text{ segundos}) = 6.67 \text{ segundos}$.

**Tiempo total:** 1 hora, 51 minutos y aproximadamente $6.67$ segundos.

---

### 4. Suma el tiempo a la hora de salida para encontrar la hora de cruce

El tiempo se suma a la hora en que ambos trenes comenzaron su viaje simultáneo (las 09:00).

* **Hora de inicio del cálculo:** 09:00
* **Tiempo de espera:** 1 hora, 51 minutos, 6.67 segundos

$$09:00:00 + 01:51:06 = 10:51:06$$

---

### Respuesta final

Los trenes se cruzarán aproximadamente a las **10:51** (con unos 6 segundos de diferencia).

¿Por qué funciona? Al obligar al modelo a generar tokens intermedios de razonamiento, cada paso condiciona el siguiente. Es como si el modelo “pensara en voz alta”, reduciendo drásticamente los errores en tareas matemáticas y lógicas.

Tree-of-Thought (ToT)

El Tree-of-Thought extiende CoT: en lugar de un único camino de razonamiento, el modelo explora múltiples ramas y elige la mejor. Es útil para problemas con múltiples soluciones posibles (planificación, puzzles, creatividad).

## 🎯 ENFOQUE 1: La Simulación Estratégica (The Strategy Simulation)

Este enfoque apela directamente a la mentalidad analítica del equipo, obligándolos a tomar decisiones basadas en datos y estrategias en un entorno competitivo.

### Descripción de la Actividad Principal
**Simulación Empresarial o "Shark Tank" Analítico.** Se divide al grupo en equipos pequeños (4-5 personas). Cada equipo recibe un caso complejo (ej. un desafío de negocio, un mercado emergente) con recursos limitados y un tiempo definido para desarrollar una estrategia, justificar sus decisiones y presentarla a un "jurado". El objetivo es no solo ganar, sino entender cómo el equipo colaboró y qué funcionó en su proceso de toma de decisiones.

### Evaluación (Pros y Contras)
| Aspecto | Pros (+) | Contras (-) |
| :--- | :--- | :--- |
| **Engagement** | 🔥 Alto. Estimula la competencia sana y el debate intelectual. Ideal para un equipo de Data Science que disfruta del desafío lógico. | Puede generar ansiedad si los participantes son muy introvertidos o no disfrutan de la confrontación directa. |
| **Logística** | ✅ Moderada. Requiere materiales sencillos (pizarras, plantillas) y tiempo definido. Fácil de adaptar al espacio de oficina. | ⏱ Necesita un anfitrión fuerte para gestionar el tiempo y asegurar que las reglas sean claras. |
| **Coste** | 💰 Bajo. Principalmente requiere tiempo y material impreso/digital. No se necesitan instalaciones externas. | El coste principal es el tiempo del facilitador. |

### ENFOQUE 2: El Diseño Colaborativo (The Collaborative Design)

Este enfoque se centra en la creatividad, la comunicación no verbal y la capacidad de construir algo complejo a partir de ideas abstractas.

### Descripción de la Actividad Principal
**Construcción de un "MVP" (Minimum Viable Product) o Storytelling.** Se divide al equipo en grupos. Cada grupo recibe un problema o una idea vaga y debe diseñar, crear un prototipo (físico o digital simple) o desarrollar una narrativa convincente en un tiempo limitado, utilizando los recursos disponibles (cartones, post-its, marcadores, etc.). El foco está en la **iteración rápida** y la **adaptación**.

### Evaluación (Pros y Contras)
| Aspecto | Pros (+) | Contras (-) |
| :--- | :--- | :--- |
| **Engagement** | ✨ Alto. Fomenta la creatividad, el pensamiento lateral y la comunicación fluida. Excelente para romper el hielo. | Puede ser menos intenso para quienes prefieren estructuras rígidas o resultados muy cuantificables. |
| **Logística** | ✅ Baja. Requiere materiales comunes (material de arte, post-its). Flexible para cualquier espacio. | 📏 El resultado final es subjetivo, lo que puede requerir una discusión posterior más profunda. |
| **Coste** | 💰 Muy bajo. Materiales de papelería y suministros básicos. | No hay coste monetario significativo. |

### ENFOQUE 3: El Desafío Físico/Lógico (The Physical & Logical Challenge)

Este enfoque busca romper la rutina, utilizando el movimiento físico para mejorar la conexión entre los miembros del equipo a través de desafíos que requieren coordinación y comunicación física.

### Descripción de la Actividad Principal
**Desafíos de Coordinación en Equipo (Ej. "El Nudo Humano" o "Construcción por Sentido").** Se plantean una serie de retos físicos sencillos donde todos los miembros deben trabajar sincronizadamente sin usar la lógica de Data Science, sino su comunicación y confianza para resolver el problema. El objetivo es poner a prueba la **confianza mutua** y la capacidad de escuchar en situaciones de presión física.

### Evaluación (Pros y Contras)
| Aspecto | Pros (+) | Contras (-) |
| :--- | :--- | :--- |
| **Engagement** | 💪 Alto. Energizante, ayuda a liberar tensiones y mejora el *rapport* personal rápidamente. | Puede ser demasiado "casual" para un equipo que opera en entornos muy formales o intelectuales. |
| **Logística** | ✅ Moderada. Requiere un espacio despejado (puede ser en una oficina grande o un área de esparcimiento). Necesita seguridad y supervisión. | 🚧 Requiere un manejo cuidadoso si hay personas con limitaciones físicas. |
| **Coste** | 💰 Bajo. Solo se necesitan los espacios y, posiblemente, algún material de seguridad. | El riesgo logístico es ligeramente mayor que en las otras opciones. |

---

## 🏆 Elección del Mejor Enfoque y Justificación

**Opción Elegida: ENFOQUE 1 - La Simulación Estratégica (The Strategy Simulation)**

### Justificación
Para un equipo de Data Science, la **Simulación Estratégica** es el enfoque más adecuado porque capitaliza su mayor fortaleza: **el pensamiento lógico, la toma de decisiones basada en evidencia y el análisis de escenarios**. Esta actividad no solo fomenta la colaboración y la comunicación, sino también refuerza sus habilidades profesionales (estrategia, modelado de escenarios, justificación de resultados) en un ambiente lúdico. Es una inversión que tiene un retorno directo en su capacidad para trabajar mejor juntos bajo presión.

* **Beneficios Específicos:**
1. **Relevancia Profesional:** La actividad se siente como un ejercicio profesional disfrazado de juego.
2. **Compromiso Intelectual:** Asegura que el tiempo invertido sea productivo y estimulante.
3. **Adaptabilidad:** Puede ser adaptada a cualquier tema (marketing, finanzas, tecnología) para mantenerla fresca.

---

## 📋 Desarrollo Detallado de la Opción Elegida: Simulación Estratégica

**Título del Evento:** Data Strategy Challenge: Decidiendo el Futuro

**Duración total:** 4 horas (240 minutos)
**Participantes:** 20 personas
**Materiales necesarios:** Pizarras blancas o rotafolios, marcadores de colores, hojas de caso impresas.

### Estructura de la Jornada (4 Horas)

#### Fase 1: Introducción y Formación de Equipos (30 min)

1. **Bienvenida y Contexto (10 min):** El facilitador explica el objetivo del Team Building (mejorar la toma de decisiones bajo presión, no solo ganar) y las reglas. Se enfatiza que el enfoque es la colaboración y el proceso, no solo el resultado final.
2. **Formación de Equipos (10 min):** Dividir a los 20 participantes en 4 equipos de 5 personas cada uno. Asignar un nombre estratégico para cada equipo (ej. "Team Alpha", "Equipo Insight", etc.).
3. **Presentación del Caso (10 min):** Presentar el escenario principal que enfrentarán los equipos. *Sugerencia de tema:* Un caso sobre la implementación de una nueva tecnología disruptiva en un mercado específico, o cómo optimizar un proceso interno para lograr un objetivo ambicioso con recursos limitados.

#### Fase 2: Desarrollo Estratégico (120 min)

1. **Análisis del Caso (30 min):** Los equipos tienen tiempo para discutir el caso, identificar variables clave, establecer hipótesis y determinar sus opciones estratégicas. Deben definir: ¿Cuál es el problema real? ¿Cuáles son los riesgos?
2. **Desarrollo de la Estrategia (60 min):** Los equipos deben crear un plan de acción detallado. Esto incluye la justificación de por qué eligieron ciertas acciones, cómo se distribuirán los recursos y cuáles serán sus métricas de éxito. Deben documentar su lógica en la pizarra o rotafolio.
3. **Preparación de la Presentación (30 min):** Los equipos preparan un resumen conciso de su estrategia para poder defenderla ante el jurado.

#### Fase 3: Presentación y Debate (60 min)

1. **Presentación (25 min por equipo):** Cada equipo presenta su propuesta estratégica (máximo 5 minutos). Deben explicar su problema, sus decisiones clave y la justificación de sus supuestos.
2. **Debate y Evaluación (35 min):** El facilitador modera un debate constructivo. Se pide a los equipos que hagan preguntas críticas a otros equipos para poner a prueba sus estrategias. Finalmente, el equipo de facilitadores o el grupo vota (o hace una evaluación cualitativa) sobre: la lógica aplicada, la colaboración y el proceso de toma de decisiones.

#### Fase 4: Cierre y Reflexión (30 min)

1. **Debriefing Grupal (15 min):** Sesión de reflexión guiada. Preguntas clave:
    * ¿Qué aprendimos sobre cómo colaboramos en esta simulación?
    * ¿Cómo se relaciona este proceso con la toma de decisiones en nuestro trabajo diario (Data Science)?
    * ¿Qué estrategia o herramienta de comunicación funcionó mejor para el equipo?
2. **Cierre (15 min):** Agradecer la participación y vincular las lecciones aprendidas a los objetivos del equipo.

### Checklist Logístico Detallado

| Elemento | Descripción | Responsable | Notas Importantes |
| :--- | :--- | :--- | :--- |
| **Tiempo (4h)** | 30 min Setup / 120 min Desarrollo / 60 min Presentación / 30 min Debrief. | Facilitador Principal | El control del tiempo es crucial para mantener el ritmo y la presión. |
| **Materiales** | Casos impresos, Pizarras/rotafolios, Marcadores. | Logística/ Apoyo | Asegurar que haya suficientes hojas de trabajo por equipo (4x5=20). |
| **Espacio** | Sala grande o espacio con mesas redondas para facilitar el debate. | Logística | Se necesita un área visible para la presentación final. |
| **Roles** | Facilitador, Moderador de tiempo. | Facilitador Principal | El facilitador debe ser firme al mantener las reglas y enfocar el debate en la colaboración. |
| **Resultado Esperado** | Entender cómo se toman decisiones bajo presión, mejorar la comunicación, y fomentar un pensamiento estratégico dentro del equipo. | - | Este es el objetivo de una simulación profesionalizada. |
Note

ToT requiere más tokens (y por tanto más coste) que CoT simple, ya que se generan y evalúan múltiples ramas. En la práctica, se implementa con múltiples llamadas al LLM o agentes que evalúan cada rama.

Output Structuring con JSON Schema

Forzar que el modelo devuelva JSON nos permite integrar el LLM en pipelines automatizados. La API de OpenAI ofrece el parámetro response_format para garantizar JSON válido:

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    texto_a_analizar = """
    Reunión del 15/03/2026. Asistentes: Ana (Data), Carlos (ML), Bea (Product).
    Se acordó migrar el pipeline ETL a Spark antes del Q2.
    Presupuesto estimado: 45.000€. Carlos se encarga de la POC.
    """

    system_prompt = f"""Eres un extractor de datos de actas de reunión.
Devuelve ÚNICAMENTE un JSON válido con esta estructura exacta, sin texto adicional:
{{
  "fecha": "string (formato YYYY-MM-DD)",
  "asistentes": ["lista de nombres"],
  "decisiones": ["lista de decisiones tomadas"],
  "presupuesto_euros": 0.0,
  "responsables": [{{"nombre": "string", "tarea": "string"}}]
}}"""

    respuesta = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": texto_a_analizar}
        ],
    )

    try:
        resultado = parse_json_response(respuesta.choices[0].message.content)
        print(json.dumps(resultado, indent=2, ensure_ascii=False))
    except json.JSONDecodeError:
        print("⚠️ El modelo no devolvió JSON válido. Intenta de nuevo o usa un modelo con soporte nativo de structured output.")
        print(respuesta.choices[0].message.content[:200])

  ]

ImportantJSON vía prompt vs. structured output nativo

Pedir JSON en el prompt funciona con cualquier modelo, pero no garantiza que el JSON sea válido (por eso añadimos try/except). Algunos modelos como Qwen 3 ofrecen response_format nativo que fuerza la estructura desde el API. La ventaja del prompting es que es model-agnostic: funciona con Gemma, Llama, Mistral, etc.

De JSON Schema a datos sintéticos: el enfoque intuitivo

Lo que acabas de hacer —extraer 1 registro JSON de un texto— es el mismo mecanismo que permite generar datasets sintéticos completos. La diferencia es de escala: en lugar de pedir 1 registro, pides N. En lugar de extraer de un texto real, pides al modelo que invente datos verosímiles.

La receta es simple:

  1. Define el schema de tus datos (igual que en la sección anterior)
  2. Añade few-shot examples para que el modelo entienda el dominio y los rangos esperados
  3. Controla la diversidad con temperatura: baja produce datos conservadores, alta inyecta variedad
  4. Itera en batch para generar cientos o miles de registros

Este es el enfoque más intuitivo y accesible para datos sintéticos: - Sin entrenar modelos adicionales - Sin GPU - En menos de 20 líneas de código - Funciona con cualquier modelo (Gemma, Qwen, Llama, etc.) - Ideal para prototipado, testing y aumento rápido de datasets pequeños

  • Puede generar valores atípicos no representativos
  • Depende de la calidad del prompt y los ejemplos
  • No hay garantía de privacidad diferencial

Esta es una pregunta interesante que requiere la revisión de la definición de los números de Mersenne. Para responderla correctamente, seguiremos el proceso solicitado.

---

### 1. ¿Qué es un número primo de Mersenne? (Definición general)

Un **Número de Mersenne** es un número generado por la fórmula $M_p = 2^p - 1$, donde $p$ debe ser un número primo.

Un **Número Primo de Mersenne** es un Número de Mersenne ($M_p$) que, además de ser generado por la fórmula, también es un número primo.

*Ejemplos:*
Si $p=2$, $M_2 = 2^2 - 1 = 3$ (3 es primo). $\rightarrow 3$ es un primo de Mersenne.
Si $p=3$, $M_3 = 2^3 - 1 = 7$ (7 es primo). $\rightarrow 7$ es un primo de Mersenne.
Si $p=5$, $M_5 = 2^5 - 1 = 31$ (31 es primo). $\rightarrow 31$ es un primo de Mersenne.

### 2. ¿Cómo se comprueba si un número es primo de Mersenne? (Método)

Para determinar si un número dado $N$ es un primo de Mersenne, debemos seguir dos pasos cruciales:

**Paso A: Verificar la forma de Mersenne.**
Se debe intentar encontrar un exponente primo $p$ tal que $N = 2^p - 1$. Esto implica despejar $2^p$:
$$2^p = N + 1$$
Luego, se calcula $p$ (usando logaritmos base 2) y se verifica si el resultado es un número primo.

**Paso B: Verificar la primalidad.**
Una vez que se encuentra un exponente primo $p$, se debe verificar si el número generado ($M_p$) es efectivamente un número primo. (Para números muy grandes, se usa el Test de Lucas-Lehmer). Para números pequeños, basta con realizar una prueba de división por números primos hasta $\sqrt{N}$.

---

### 3. Aplicación del método a 17 y conclusión

Vamos a aplicar el método a $N = 17$. Queremos saber si 17 es un primo de Mersenne, es decir, si existe un primo $p$ tal que $2^p - 1 = 17$.

**Paso A: Verificar la forma de Mersenne.**

Despejamos $2^p$:
$$2^p = 17 + 1$$
$$2^p = 18$$

Para encontrar el exponente $p$, necesitamos determinar qué potencia de 2 es igual a 18.

* $2^1 = 2$
* $2^2 = 4$
* $2^3 = 8$
* $2^4 = 16$
* $2^5 = 32$

Dado que 18 no es una potencia entera de 2, **no existe un exponente entero $p$** tal que $2^p = 18$.

**Paso B: Verificar la primalidad (Implícito).**

Como el número 17 no puede expresarse en la forma $2^p - 1$, no es un Número de Mersenne. Por lo tanto, no puede ser un primo de Mersenne. (Nota: El número 17 sí es un número primo, pero no cumple con la condición estructural para pertenecer a la secuencia de Mersenne).

---

### Conclusión

**No**, el número 17 **no es un número primo de Mersenne**.

Esto se debe a que 17 no puede ser expresado en la forma $2^p - 1$ donde $p$ es un número primo, ya que $17 + 1 = 18$, y 18 no es una potencia de 2.

Buenas prácticas resumen

  1. Sé específico: “analiza los datos” → malo. “calcula media, mediana y desviación típica de la columna ‘ventas’ agrupada por ‘región’” → bueno
  2. Muestra, no solo digas: incluye ejemplos del formato que esperas (few-shot)
  3. Divide y vencerás: tareas complejas → CoT, desglosa en pasos
  4. Formato forzado: usa response_format / JSON Schema cuando integres con código
  5. Itera: el primer prompt casi nunca es el óptimo. Prueba, compara, mejora
  6. System prompt: define el tono, rol y restricciones al inicio

## Prompt Engineering Avanzado

### ¿Qué es un prompt?

Un **prompt** es la instrucción textual que le damos a un LLM. Piensa en ello como la pregunta o la orden que le das a un asistente muy capaz pero muy literal: si la instrucción es ambigua, la respuesta será imprecisa. Si es clara y con contexto, la respuesta será mucho mejor.

El Prompt Engineering consiste en diseñar estas instrucciones de forma sistemática para obtener respuestas fiables, estructuradas y útiles, no solo "texto bonito".

```{mermaid}
    C -->|No| E[Respuesta<br/>ambigua o incorrecta]
```

Antes de profundizar, veamos cómo invocar un LLM desde Python con la API de OpenAI (compatible con Llamus US, Ollama local, etc.):


| `user` | Pregunta o instrucción del usuario | "Analiza este CSV..." |
| `assistant` | Respuestas previas del modelo (historial) | "La media es 42.3..." |

### Few-shot prompting

El **few-shot** consiste en incluir ejemplos dentro del prompt para que el modelo entienda exactamente qué formato y estilo esperamos. Es como enseñarle con el ejemplo.

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    prompt_few_shot = """
    Clasifica el sentimiento de cada frase como POSITIVO, NEGATIVO o NEUTRAL.

    Ejemplos:
    Frase: "El producto llegó roto y la atención fue pésima" → NEGATIVO
    Frase: "Todo perfecto, entrega rápida y bien embalado" → POSITIVO
    Frase: "El paquete llegó ayer por la tarde" → NEUTRAL

    Ahora clasifica:
    Frase: "El diseño es bonito pero la batería no dura nada"
    """

    respuesta = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[{"role": "user", "content": prompt_few_shot}]
    )
    print(respuesta.choices[0].message.content)
```

**¿Por qué funciona?** Los LLMs son excelentes reconociendo patrones. Al darles 2-3 ejemplos, el modelo "aprende" el patrón en contexto (*in-context learning*) sin necesidad de fine-tuning.

::: {.callout-tip}
## Regla de oro del few-shot
- 2-3 ejemplos suelen bastar
- Los ejemplos deben cubrir los casos extremos (edge cases)
- Mantén consistencia exacta en el formato de los ejemplos
:::

### Zero-shot vs Few-shot vs One-shot

| Estrategia | Ejemplos en el prompt | Cuándo usarlo |
|---|---|---|
| **Zero-shot** | 0 — solo la instrucción | Tareas sencillas, modelos muy capaces |
| **One-shot** | 1 ejemplo | Cuando necesitas mostrar el formato exacto |
| **Few-shot** | 2-5 ejemplos | Tareas complejas, formatos muy específicos |

### Chain-of-Thought (CoT)

El **Chain-of-Thought** consiste en pedir al modelo que razone paso a paso antes de dar la respuesta final. La clave está en añadir algo como _"pensemos paso a paso"_ o incluir ejemplos donde se muestra el razonamiento.

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    problema = """
    Un tren sale de Madrid a las 08:00 hacia Barcelona (620 km) a 120 km/h.
    Otro tren sale de Barcelona a las 09:00 hacia Madrid a 150 km/h.
    ¿A qué hora se cruzan?
    """

    prompt_cot = f"""
    {problema}

    Resuelve paso a paso:
    1. Calcula cuánto ha avanzado el primer tren cuando sale el segundo
    2. Calcula la distancia restante entre ambos en ese momento
    3. Calcula el tiempo hasta que se cruzan
    4. Suma el tiempo a la hora de salida
    """

    respuesta_cot = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[{"role": "user", "content": prompt_cot}]
    )
    print(respuesta_cot.choices[0].message.content)
```

**¿Por qué funciona?** Al obligar al modelo a generar tokens intermedios de razonamiento, cada paso condiciona el siguiente. Es como si el modelo "pensara en voz alta", reduciendo drásticamente los errores en tareas matemáticas y lógicas.

### De JSON Schema a datos sintéticos: el enfoque intuitivo

Lo que acabas de hacer —extraer 1 registro JSON de un texto— es el mismo mecanismo que permite **generar datasets sintéticos completos**. La diferencia es de escala: en lugar de pedir 1 registro, pides N. En lugar de extraer de un texto real, pides al modelo que *invente* datos verosímiles.

La receta es simple:

1. **Define el schema** de tus datos (igual que en la sección anterior)
2. **Añade few-shot examples** para que el modelo entienda el dominio y los rangos esperados
3. **Controla la diversidad** con temperatura: baja produce datos conservadores, alta inyecta variedad
4. **Itera en batch** para generar cientos o miles de registros

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    import pandas as pd

    system_prompt = """Eres un generador de datos sintéticos de clientes españoles.
Devuelve ÚNICAMENTE un JSON válido con esta estructura exacta, sin texto adicional:
{
  "clientes": [
    {
      "id": 1,
      "edad": 34,
      "ingresos_anuales": 42000.0,
      "provincia": "Madrid",
      "segmento": "premium"
    }
  ]
}
Reglas:
- Edad entre 18 y 80 años
- Ingresos entre 12000 y 120000, correlacionados con la edad
- Provincias: Madrid, Barcelona, Valencia, Sevilla, Bilbao, Málaga, Zaragoza
- Segmentos: premium, estandar, basic
- Genera variedad realista"""

    respuesta = client.chat.completions.create(
        model="gemma4:e2b-mlx",
        temperature=0.8,
        messages=[
            {"role": "system", "content": system_prompt},
            {"role": "user", "content": "Genera 10 clientes sintéticos. Usa variedad realista en edades, ingresos y provincias."}
        ],
    )

    try:
        datos = parse_json_response(respuesta.choices[0].message.content)
        df = pd.DataFrame(datos["clientes"])
        print(df.to_string(index=False))
        print(f"\n{len(df)} registros generados")
        print(f"   Edad: {df['edad'].min()}-{df['edad'].max()} (media {df['edad'].mean():.0f})")
        print(f"   Ingresos: {df['ingresos_anuales'].min():.0f}-{df['ingresos_anuales'].max():.0f} (media {df['ingresos_anuales'].mean():.0f})")
    except (json.JSONDecodeError, KeyError) as e:
        print(f"⚠️ Error al parsear respuesta: {e}")
        print(respuesta.choices[0].message.content[:200])
```

::: {.callout-tip}
## ¿Por qué funciona?

El LLM no "conoce" clientes reales, pero ha visto millones de patrones en sus datos de entrenamiento: distribuciones de edad, rangos de ingresos típicos, provincias españolas. El **prompt con el schema**, el **few-shot** y la **temperatura** controlan estructura, dominio y diversidad. Algunos modelos (Qwen, OpenAI) ofrecen además `response_format` nativo para forzar la estructura desde el API.

**Este es el enfoque más intuitivo y accesible para datos sintéticos:**
- Sin entrenar modelos adicionales
- Sin GPU
- En menos de 20 líneas de código
- Funciona con cualquier modelo (Gemma, Qwen, Llama, etc.)
- Ideal para prototipado, testing y aumento rápido de datasets pequeños
:::

::: {.callout-warning}
## Limitaciones del enfoque intuitivo

- No garantiza **correlaciones realistas** entre columnas (ej. ingresos vs. edad pueden no seguir la relación esperada)
- Puede generar **valores atípicos** no representativos
- Depende de la **calidad del prompt** y los ejemplos
- **No hay garantía de privacidad** diferencial

Para datasets de producción donde la fidelidad estadística es crítica, necesitarás modelos generativos especializados (CTGAN, TVAE, TabDDPM) que veremos en el **Bloque 3** con SDV.
:::

### Role Prompting

Asignar un **rol** al modelo en el mensaje `system` cambia radicalmente su comportamiento. No es magia: el modelo, entrenado con textos de diversos perfiles, "activa" los patrones asociados a ese rol.

```{python}
#| echo: true

def consultar_como(rol, pregunta):
    return client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[
            {"role": "system", "content": rol},
            {"role": "user", "content": pregunta}
        ]
    ).choices[0].message.content

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    # Sin rol (genérico)
    print("=== SIN ROL ===")
    print(consultar_como("Eres un asistente útil.", "¿Qué opinas de usar la media en datos con outliers?"))

    # Con rol de analista senior
    print("\n=== ANALISTA SENIOR ===")
    print(consultar_como(
        "Eres un analista de datos senior con 15 años de experiencia en finanzas. "
        "Respondes con rigor estadístico, mencionas alternativas robustas y das ejemplos concretos.",
        "¿Qué opinas de usar la media en datos con outliers?"
    ))

    # Con rol de profesor divulgador
    print("\n=== PROFESOR DIVULGADOR ===")
    print(consultar_como(
        "Eres un profesor de estadística que explica conceptos a estudiantes de primero de carrera. "
        "Usas analogías cotidianas, evitas jerga innecesaria y pones ejemplos sencillos.",
        "¿Qué opinas de usar la media en datos con outliers?"
    ))
```

### Técnicas adicionales

| Técnica | Descripción | Cuándo usarla |
|---|---|---|
| **Self-consistency** | Ejecutar CoT varias veces y votar la respuesta mayoritaria | Razonamiento matemático/lógico |
| **Generated knowledge** | Pedir al modelo que genere contexto antes de responder | Preguntas que requieren conocimiento factual |
| **Re-reading (RE2)** | Hacer que el modelo lea la pregunta dos veces | Mejora comprensión en tareas largas |
| **Emotion prompting** | Añadir estímulos emocionales al prompt | Tareas creativas o subjetivas |
| **Step-back prompting** | Preguntar primero por principios generales | Problemas muy específicos |

```{python}
#| echo: true

if not LLM_KEY:
    print("⚠️  Configura LLM_API_KEY en .env para ver el output de esta celda.")
else:
    prompt_step_back = """
    Pregunta original: ¿Es 17 un número primo de Mersenne?

    Antes de responder, contesta:
    1. ¿Qué es un número primo de Mersenne? (definición general)
    2. ¿Cómo se comprueba si un número es primo de Mersenne? (método)
    3. Ahora aplica el método a 17 y concluye.
    """

    print(client.chat.completions.create(
        model="gemma4:e2b-mlx",
        messages=[{"role": "user", "content": prompt_step_back}]
    ).choices[0].message.content)
```

### Buenas prácticas resumen

1. **Sé específico**: "analiza los datos" → malo. "calcula media, mediana y desviación típica de la columna 'ventas' agrupada por 'región'" → bueno
2. **Muestra, no solo digas**: incluye ejemplos del formato que esperas (few-shot)
3. **Divide y vencerás**: tareas complejas → CoT, desglosa en pasos
4. **Formato forzado**: usa `response_format` / JSON Schema cuando integres con código
5. **Itera**: el primer prompt casi nunca es el óptimo. Prueba, compara, mejora
6. **System prompt**: define el tono, rol y restricciones al inicio
