HPD 1 — Pipeline de embeddings y búsqueda semántica

TipObjetivos

Note¿Por qué necesitas esto?

Imagina que trabajas en un despacho de abogados buscando cláusulas de confidencialidad en 500 contratos. O en una multinacional filtrando currículums por habilidades, no por palabras clave exactas. O en un hospital recuperando historiales clínicos con síntomas parecidos. Los tres problemas se resuelven con la misma arquitectura: convertir documentos en vectores y buscar por similitud semántica.

Al final de este taller sabrás construir ese pipeline de principio a fin y, sobre todo, medir si funciona. Y lo mejor: cambiar de dominio (legal, médico, financiero) solo requiere cambiar los documentos de entrada — el código es el mismo.

Del recorrido histórico al pipeline

El panorama histórico del Bloque 1 termina en la idea de que un documento y una consulta pueden situarse en un mismo espacio semántico. Este taller convierte esa idea en un sistema ejecutable: ingesta de documentos, chunking, embeddings, indexación, recuperación y evaluación. El objetivo no es solo llamar a un modelo, sino comprobar qué calidad tiene la representación cuando se utiliza para recuperar información.

Note¿Qué es un embedding?

Un embedding convierte un texto en una lista de números (384 en nuestro caso). La clave está en que textos con significado parecido producen números parecidos, aunque usen palabras distintas.

Imagina un mapa donde cada documento es un punto. Los documentos que hablan de lo mismo quedan cerca. Cuando haces una pregunta, el modelo la sitúa en ese mismo mapa y busca los vecinos más próximos.

El modelo que usamos, e5-small-v2, tiene solo 33 millones de parámetros: ligero para ejecutar en local pero con muy buena calidad para búsqueda semántica.

NoteSimilitud coseno vs. distancia coseno

Chroma devuelve distancias, no similitudes. La relación es:

\[\text{distancia} = 1 - \text{similitud}\]

Con embeddings normalizados (lo habitual), la similitud coseno equivale al producto escalar y oscila en \([0, 1]\). La distancia, por tanto, está en \([0, 1]\). Cuanto menor es la distancia, más relevante es el chunk.

Para muchos casos de búsqueda por descripción (buscar empleados por perfil, productos por características, registros por texto libre) el texto concatenado es un buen punto de partida; para filtros por cifras, no.

1.7 Evaluación: recall@k, hit@k y MRR

Note¿Cómo se mide si la búsqueda funciona?

Necesitamos preguntas de prueba y saber qué chunks son relevantes para cada una (el ground truth). Con ellos:

  • recall@k: de todos los chunks relevantes, ¿qué fracción aparece entre los \(k\) primeros?
  • hit@k: ¿hay al menos un relevante entre los \(k\) primeros? (sí/no)
  • MRR: \(1/\text{posición}\) del primer relevante, promediado.

Si una pregunta tiene 5 chunks relevantes y \(k=1\), el recall@1 solo puede valer 0,2 como máximo aunque el sistema sea perfecto. Por eso con \(k\) pequeño y varios relevantes conviene mirar también hit@k.

¿Cómo decidimos qué chunk es relevante? Por su contenido: un chunk es relevante para una pregunta si pertenece al documento correcto y contiene alguna de las frases clave que anotamos a mano. Así el ground truth sigue siendo válido aunque cambies CHUNK_SIZE (si lo definiéramos con identificadores como doc_chunk_3, cada cambio de troceado lo invalidaría).

def hit_at_k(retrieved_ids, relevant_ids, k):
    """1.0 si algún relevante aparece entre los k primeros, 0.0 si no."""
    return float(any(r in relevant_ids for r in retrieved_ids[:k]))


def reciprocal_rank(retrieved_ids, relevant_ids):
    """1/posición del primer relevante (0.0 si no aparece)."""
    for pos, r in enumerate(retrieved_ids, start=1):
        if r in relevant_ids:
            return 1.0 / pos
    return 0.0

    print(f"    recall@{k} medio: {np.mean(recalls):.3f} · hit@{k} medio: {np.mean(hits):.2f} · MRR: {np.mean(rrs):.3f}")

Con pocos chunks por documento, recall@1 es bajo porque cada pregunta tiene varios chunks relevantes y solo miras uno. Compáralo con hit@1 y con recall@5. Estas dos lecturas juntas dicen algo distinto: ¿el primer resultado es bueno? frente a ¿he encontrado todo lo relevante?

2.5 Línea base léxica y búsqueda híbrida

Una evaluación solo vale en comparación. Construimos una línea base léxica (BM25, explicado en 01e) y una búsqueda híbrida que fusiona los rankings de BM25 y del modelo denso con Reciprocal Rank Fusion. La implementación está dada: tu trabajo es interpretarla.

import math
import re
from collections import Counter

def tokenizar(texto):
    return re.findall(r"[a-z0-9\-]+", texto.lower())

class BM25:
    """BM25 con índice invertido (rápido incluso con ~1.300 chunks)."""
    def __init__(self, documentos, ids, k1=1.5, b=0.75):
        self.ids = ids
        self.tf = [Counter(tokenizar(d)) for d in documentos]
        self.largo = [sum(t.values()) for t in self.tf]
        self.avgdl = sum(self.largo) / len(self.largo)
        self.df = Counter(w for t in self.tf for w in t)
        self.inv = {}
        for i, t in enumerate(self.tf):
            for w in t:
                self.inv.setdefault(w, []).append(i)
        self.k1, self.b, self.N = k1, b, len(documentos)

    def ranking(self, consulta):
        puntos = Counter()
        for w in set(tokenizar(consulta)):
            if w not in self.inv:
                continue
            idf = math.log(1 + (self.N - self.df[w] + 0.5) / (self.df[w] + 0.5))
            for i in self.inv[w]:
                f = self.tf[i][w]
                puntos[i] += idf * f * (self.k1 + 1) / (f + self.k1 * (1 - self.b + self.b * self.largo[i] / self.avgdl))
        return [self.ids[i] for i, _ in puntos.most_common()]        # solo chunks con alguna coincidencia

datos = collection_real.get(include=["documents"])
bm25 = BM25(datos["documents"], datos["ids"])

def ranking_bm25(query):
    return bm25.ranking(query)

def ranking_hibrido(query, c=60):
    puntos = Counter()
    for ranking in (ranking_bm25(query), ranking_denso(query)):
        for pos, cid in enumerate(ranking, start=1):
            puntos[cid] += 1 / (c + pos)
    return [cid for cid, _ in puntos.most_common()]

METODOS = [("Denso", ranking_denso), ("BM25", ranking_bm25), ("Híbrido", ranking_hibrido)]

En nuestra ejecución (las cifras varían ligeramente con la versión del extractor de PDF) el método denso encontró algo relevante entre los 5 primeros en las 10 consultas (hit@5 = 1,00) y BM25 solo en 8, pero cuando BM25 acertaba lo colocaba antes (MRR 0,74 frente a 0,68). La tabla consulta a consulta explica por qué:

  • BM25 acierta a la primera en consultas que usan palabras del propio texto (“frozen”, “square root”, “RAG-Token”) y en dos de ellas supera al denso.
  • BM25 falla en preguntas formuladas con otras palabras (“How is BERT pre-trained?” → posición 31; “How does RAG combine retrieval and generation?” → posición 21).
  • El híbrido queda en medio y no mejora al mejor de los dos.

Con 10 consultas cualquier diferencia pequeña es ruido. Lo que debes sacar de este ejercicio no es “gana el método X”, sino el método de trabajo: un conjunto de consultas, un ground truth por contenido, una línea base y mirar consulta a consulta dónde falla cada método.

2.6 Evaluación MTEB — Validación profesional del modelo

Note

Esta sección descarga benchmarks públicos y evalúa el modelo. No es necesaria para completar el entregable del HPD 1, pero te da criterio profesional para comparar modelos de embeddings en tu proyecto final.

Note¿Cómo sabemos si el modelo de embeddings es bueno?

MTEB (Massive Text Embedding Benchmark) es el examen estándar: una colección de tareas que miden distintas habilidades (clasificar, agrupar, recuperar, medir similitud) (Muennighoff et al., 2023).

Aquí nos centramos en STS (Semantic Textual Similarity): el modelo recibe pares de frases y les asigna una puntuación de parecido. El benchmark compara esas puntuaciones con las que daría un humano. Por ejemplo:

Par de frases ¿Similares?
El gato duerme en el sofá ↔︎ Un felino descansa en el sillón Muy similares
El gato duerme ↔︎ Mañana lloverá Nada similares

La métrica es Spearman rank: una correlación de rankings entre lo que dice el modelo y lo que dice el humano. Va de 0 (aleatorio) a 1 (perfecto). Un 0,89 significa que el modelo coincide muy bien con el criterio humano.

Usamos dos tareas complementarias: BIOSSES (100 pares, dominio biomédico, rapidísima) y STS12 (621 pares, dominio general). Juntas dan una foto rápida del modelo en menos de 1 minuto.

WarningSTS no es recuperación

Estas tareas miden si el modelo puntúa bien pares de frases parecidas. Una buena nota en STS no garantiza que el modelo recupere bien documentos largos para una pregunta, que es lo que hacemos en este taller. MTEB incluye también tareas de Retrieval (basadas en el benchmark BEIR (Thakur et al., 2021), por ejemplo FiQA2018 o NFCorpus) que son mucho más relevantes para un sistema de búsqueda; consulta la pestaña Retrieval del leaderboard de MTEB y, sobre todo, mide con tus propias consultas, como acabas de hacer en las secciones 2.4 y 2.5.

## ¿Qué es un embedding?

Un embedding convierte un texto en una lista de números (384 en nuestro caso). La clave está en que textos con significado parecido producen números parecidos, aunque usen palabras distintas.

Imagina un mapa donde cada documento es un punto. Los documentos que hablan de lo mismo quedan cerca. Cuando haces una pregunta, el modelo la sitúa en ese mismo mapa y busca los vecinos más próximos.

El modelo que usamos, `e5-small-v2`, tiene solo 33 millones de parámetros: ligero para ejecutar en local pero con muy buena calidad para búsqueda semántica.

## Similitud coseno vs. distancia coseno

Chroma devuelve distancias, no similitudes. La relación es:

$$\text{distancia} = 1 - \text{similitud}$$

: Comparativa entre similitud coseno y distancia coseno {#tbl-similitud-distancia}

| Métrica | Rango | Interpretación |
|---|---|---|
| **Similitud coseno** | $[-1, 1]$ | $1$ = idénticos, $0$ = ortogonales, $-1$ = opuestos |
| **Distancia coseno** | $[0, 2]$ | $0$ = idénticos, $1$ = ortogonales, $2$ = opuestos |

Con embeddings normalizados (lo habitual), la similitud coseno equivale al producto escalar y oscila en $[0, 1]$. La distancia, por tanto, está en $[0, 1]$. Cuanto menor es la distancia, más relevante es el chunk.

## 1.7 Evaluación: recall@k, hit@k y MRR {#sec-hpd1-1-7-recall}

::: {.callout-note icon=false}

## ¿Cómo se mide si la búsqueda funciona?

Necesitamos preguntas de prueba y saber qué chunks son **relevantes** para cada una (el *ground truth*). Con ellos:

- **recall@k:** de todos los chunks relevantes, ¿qué fracción aparece entre los $k$ primeros?
- **hit@k:** ¿hay al menos un relevante entre los $k$ primeros? (sí/no)
- **MRR:** $1/\text{posición}$ del primer relevante, promediado.

Si una pregunta tiene 5 chunks relevantes y $k=1$, el recall@1 solo puede valer 0,2 como máximo aunque el sistema sea perfecto. Por eso con $k$ pequeño y varios relevantes conviene mirar también hit@k.

**¿Cómo decidimos qué chunk es relevante?** *Por su contenido*: un chunk es relevante para una pregunta si pertenece al documento correcto y contiene alguna de las frases clave que anotamos a mano. Así el ground truth sigue siendo válido aunque cambies `CHUNK_SIZE` (si lo definiéramos con identificadores como `doc_chunk_3`, cada cambio de troceado lo invalidaría).

:::

Con pocos chunks por documento, recall@1 es bajo porque cada pregunta tiene varios chunks relevantes y solo miras uno. Compáralo con hit@1 y con recall@5. Estas dos lecturas juntas dicen algo distinto: *¿el primer resultado es bueno?* frente a *¿he encontrado todo lo relevante?*
:::

        recalls.append(recall_at_k(ranking, relevantes, 5))

## 2.5 Línea base léxica y búsqueda híbrida {#sec-hpd1-2-5-hibrida}

Una evaluación solo vale en comparación. Construimos una **línea base léxica** (BM25, explicado en [01e](01e-recuperacion.qmd#sec-bm25)) y una **búsqueda híbrida** que fusiona los rankings de BM25 y del modelo denso con *Reciprocal Rank Fusion*. La implementación está dada: tu trabajo es interpretarla.

```{python}
#| echo: true
#| eval: false

import math
import re
from collections import Counter

def tokenizar(texto):
    return re.findall(r"[a-z0-9\-]+", texto.lower())

class BM25:
    """BM25 con índice invertido (rápido incluso con ~1.300 chunks)."""
    def __init__(self, documentos, ids, k1=1.5, b=0.75):
        self.ids = ids
        self.tf = [Counter(tokenizar(d)) for d in documentos]
        self.largo = [sum(t.values()) for t in self.tf]
        self.avgdl = sum(self.largo) / len(self.largo)
        self.df = Counter(w for t in self.tf for w in t)
        self.inv = {}
        for i, t in enumerate(self.tf):
            for w in t:
                self.inv.setdefault(w, []).append(i)
        self.k1, self.b, self.N = k1, b, len(documentos)

    def ranking(self, consulta):
        puntos = Counter()
        for w in set(tokenizar(consulta)):
            if w not in self.inv:
                continue
            idf = math.log(1 + (self.N - self.df[w] + 0.5) / (self.df[w] + 0.5))
            for i in self.inv[w]:
                f = self.tf[i][w]
                puntos[i] += idf * f * (self.k1 + 1) / (f + self.k1 * (1 - self.b + self.b * self.largo[i] / self.avgdl))
        return [self.ids[i] for i, _ in puntos.most_common()]        # solo chunks con alguna coincidencia

datos = collection_real.get(include=["documents"])
bm25 = BM25(datos["documents"], datos["ids"])

def ranking_bm25(query):
    return bm25.ranking(query)

def ranking_hibrido(query, c=60):
    puntos = Counter()
    for ranking in (ranking_bm25(query), ranking_denso(query)):
        for pos, cid in enumerate(ranking, start=1):
            puntos[cid] += 1 / (c + pos)
    return [cid for cid, _ in puntos.most_common()]

METODOS = [("Denso", ranking_denso), ("BM25", ranking_bm25), ("Híbrido", ranking_hibrido)]

print(f"{'Método':<10} {'hit@5':>6} {'recall@5':>9} {'MRR':>6}")
for nombre, f in METODOS:
    h, r, m = evaluar_ranking(f, QUERIES_REAL, collection_real)
    print(f"{nombre:<10} {h:>6.2f} {r:>9.3f} {m:>6.3f}")

# Consulta a consulta: posición del PRIMER chunk relevante (None = no aparece)
print(f"\n{'Posición del primer relevante':<68} {'Denso':>6} {'BM25':>6} {'Híbr.':>6}")
for query, (fuente_id, frases) in QUERIES_REAL.items():
    relevantes = set(ids_relevantes(collection_real, fuente_id, frases))
    posiciones = []
    for _, f in METODOS:
        ranking = f(query)
        posiciones.append(next((i + 1 for i, cid in enumerate(ranking) if cid in relevantes), None))
    print(f"{query[:66]:<68} {str(posiciones[0]):>6} {str(posiciones[1]):>6} {str(posiciones[2]):>6}")
```

## Cómo leer el resultado (y cómo no)

En nuestra ejecución (las cifras varían ligeramente con la versión del extractor de PDF) el método denso encontró algo relevante entre los 5 primeros en las 10 consultas (hit@5 = 1,00) y BM25 solo en 8, pero **cuando BM25 acertaba lo colocaba antes** (MRR 0,74 frente a 0,68). La tabla consulta a consulta explica por qué:

- BM25 acierta a la primera en consultas que usan palabras del propio texto ("frozen", "square root", "RAG-Token") y en dos de ellas supera al denso.
- BM25 falla en preguntas formuladas con otras palabras ("How is BERT pre-trained?" → posición 31; "How does RAG combine retrieval and generation?" → posición 21).
- El híbrido queda en medio y **no mejora al mejor de los dos**.

Con 10 consultas cualquier diferencia pequeña es ruido. Lo que debes sacar de este ejercicio no es "gana el método X", sino el método de trabajo: un conjunto de consultas, un ground truth por contenido, una línea base y mirar consulta a consulta *dónde* falla cada método.

::: {.callout-note icon=false}

## ¿Cómo sabemos si el modelo de embeddings es bueno?

MTEB (Massive Text Embedding Benchmark) es el examen estándar: una colección de tareas que miden distintas habilidades (clasificar, agrupar, recuperar, medir similitud) [@muennighoff2023mteb].

Aquí nos centramos en STS (Semantic Textual Similarity): el modelo recibe pares de frases y les asigna una puntuación de parecido. El benchmark compara esas puntuaciones con las que daría un humano. Por ejemplo:

| Par de frases | ¿Similares? |
|---|---|
| *El gato duerme en el sofá* ↔ *Un felino descansa en el sillón* | Muy similares |
| *El gato duerme* ↔ *Mañana lloverá* | Nada similares |

La métrica es Spearman rank: una correlación de rankings entre lo que dice el modelo y lo que dice el humano. Va de 0 (aleatorio) a 1 (perfecto). Un 0,89 significa que el modelo coincide muy bien con el criterio humano.

Usamos dos tareas complementarias: BIOSSES (100 pares, dominio biomédico, rapidísima) y STS12 (621 pares, dominio general). Juntas dan una foto rápida del modelo en menos de 1 minuto.

::: {.callout-warning icon=false}
## STS no es recuperación

Estas tareas miden si el modelo puntúa bien *pares de frases* parecidas. Una buena nota en STS **no garantiza** que el modelo recupere bien documentos largos para una pregunta, que es lo que hacemos en este taller. MTEB incluye también tareas de **Retrieval** (basadas en el benchmark BEIR [@thakur2021beir], por ejemplo FiQA2018 o NFCorpus) que son mucho más relevantes para un sistema de búsqueda; consulta la pestaña *Retrieval* del leaderboard de MTEB y, sobre todo, **mide con tus propias consultas**, como acabas de hacer en las secciones 2.4 y 2.5.
:::

:::
